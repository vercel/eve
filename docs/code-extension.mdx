`eve/extensions/code` (eve-code) turns an eve agent into a coding agent. It ships inside the `eve` package, so you mount it without installing anything else. The extension adds coding instructions that steer the model toward eve's default [file tools](/docs/concepts/built-in-tools#default-tools), the project's `AGENTS.md`, coding skills, and helpers that install coding tools in the sandbox. GitHub and pull request work lives in the companion [`eve/extensions/git`](#publish-with-the-git-extension) extension.

- An attempt passes only when the verifier passes.
- A crash or a timeout is a failure.

<details>
<summary>How the results update</summary>

1. The `eve-code` workflow runs on `main` with the `deepswe-lean` dataset every Monday at 06:00 UTC. A maintainer can also start it manually on `main`.
2. The workflow runs eve-code, opencode, pi, and [fx](https://fx.sh) on each benchmark model, one model at a time. It saves each complete result in the eve-bench result store.
3. The workflow opens a pull request with a summary of the default Anthropic model's result. This page shows only that model.
4. After a maintainer approves and merges the pull request, the next docs deployment shows the new results.

The workflow skips incomplete runs, single-task runs, and pull request runs. Results can be a week or more older than `main`, because the workflow runs weekly and each refresh waits for review. Select a harness name to open the GitHub Actions run for that result.

## Mount the extension

Create an extension file in your agent. The file name sets the prefix of every skill the extension adds, such as `code__investigate`:

```ts title="agent/extensions/code.ts"
import code from "eve/extensions/code";

export default code({});
```

`code({})` mounts the extension without Vercel authentication.

## Configure the extension

| Option             | Required      | Effect                                                                                         |
| ------------------ | ------------- | ---------------------------------------------------------------------------------------------- |
| `vercel.connector` | With `vercel` | Vercel Connect connector that gets a Vercel token for the app, not for a user                  |
| `vercel.delivery`  | No            | `"firewall"` (default) or `"command"`                                                          |
| `broker`           | No            | `broker(sandbox, rules)` callback that merges Vercel credential rules into your network policy |
| `repositories`     | No            | Configure repository discovery, post-clone rules, scoped subdirectory instructions, and limits |

```ts title="agent/extensions/code.ts"
import code from "eve/extensions/code";

export default code({
  vercel: { connector: "vercel/acme-bot" },
});
```

### Credentials stay outside the sandbox

With firewall delivery, Vercel tokens never enter sandbox processes. Firewall delivery needs a top-level `broker` or a sandbox provider with `setNetworkPolicy()`. For other providers, set `vercel.delivery: "command"`.

To use a personal access token or another credential provider, omit the connector. Call `authenticateGitHub` or `authenticateVercel` from `eve/extensions/code/sandbox` in your own sandbox setup code. These helpers authenticate commands you run yourself, not the `gh` tool.

## Project instructions

The extension discovers git repositories in the sandbox and adds each repository's `AGENTS.md` (or `CLAUDE.md` when there is no `AGENTS.md`) as user-role instructions. Discovery covers pre-seeded sandboxes, channel checkouts, subagents, worktrees, submodules, and repositories cloned mid-turn through `git__gh` or `bash`. When the workspace root is not a git repository, the extension reads `AGENTS.md` or `CLAUDE.md` from the workspace root.

Discovery runs at the start of each turn and after completed commands that clone, fetch, switch refs, unpack archives, or run in a new directory. Each repository and directory scope joins the conversation under its own instruction key, so newly entered repositories append without changing earlier history. Root instruction files refresh whenever they change on subsequent reconciliations (skipping re-transmission when unchanged), and matching rule files refresh when `HEAD`, repository metadata, default instructions, or rule specs change, or when a previously unavailable or overflowed rule file needs retry. When a repository's `HEAD` commit changes, the extension also clears cached subdirectory instructions for that repository. Deleted repositories are removed along with their subdirectory scopes and rule skills.

For each configured instruction file in a repository, the extension reads in three tiers:

1. **Worktree.** Reads the checked-out file when it is non-empty and its resolved path stays inside the repository root.
2. **Git `HEAD`.** When a sparse or partial checkout excludes the file from the working tree, reads `HEAD:<path>` from the local object store or fetches it over HTTPS with a 5-second timeout.
3. **Unavailable directive.** When the file exists at `HEAD` but cannot be fetched, adds a note naming the path so the model reads it before editing or opening a pull request.

As `read_file`, `edit_file`, `write_file`, `glob`, or `grep` touch files inside nested directories, the extension loads `AGENTS.md` (or `CLAUDE.md`) from each newly entered ancestor directory. A file over `maxFileBytes` (default `64_000`) is truncated with a note naming the path. When total instructions exceed `maxTotalBytes` (default `256_000`), an overflow note lists the remaining paths for `read_file`.

### Repositories and post-clone rules

Configure `repositories` on `code()` to customize discovery roots, instruction files, start-of-turn sandbox behavior, and per-repository rules:

| Option               | Default                        | Effect                                                                                                                                                                                                                                                                |
| -------------------- | ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `roots`              | `["."]`                        | Workspace-relative directories scanned up to depth 3 for repositories                                                                                                                                                                                                 |
| `instructions`       | `[["AGENTS.md", "CLAUDE.md"]]` | Repository-relative paths or fallback tuples where the first present file wins; pass `[]` to disable                                                                                                                                                                  |
| `scopedInstructions` | `true`                         | Load matching instruction files from ancestor directories as file tools enter subdirectories                                                                                                                                                                          |
| `discoverOnStart`    | `"eager"`                      | `"eager"` opens the sandbox at turn start when needed; `"on-sandbox-use"` checks via `ctx.getSandbox({ create: false })` (skips creating a new sandbox before first use, and resumes an idle-stopped persisted sandbox on later turns if the session already has one) |
| `rules`              | `[]`                           | Rules (`{ match?, files?, onEnter? }`) applied when matching repositories are discovered                                                                                                                                                                              |
| `syncAfter`          | `[]`                           | Additional `ToolDefinition` values whose completed calls trigger repository discovery                                                                                                                                                                                 |
| `maxFileBytes`       | `64_000`                       | Maximum UTF-8 bytes read per instruction file before truncation                                                                                                                                                                                                       |
| `maxTotalBytes`      | `256_000`                      | Maximum total UTF-8 bytes across emitted repository and scoped instructions                                                                                                                                                                                           |

Each entry in `rules` accepts:

- `match`: `"owner/name"` (case-insensitive exact slug), `"owner/*"` (wildcard prefix), `"*"`, a `RegExp` tested against `repo.slug` or `repo.root`, or a predicate `(repo) => boolean`. Omit `match` to match every discovered repository.
- `files`: Extra repository-relative paths or fallback tuples to load alongside `instructions`.
- `onEnter(repo, ctx)`: Runs once per session when a matching repository is first discovered. `repo` provides `root`, `slug`, `remote`, `head`, `branch`, `sparse`, `instructions`, and `repo.readFile(relativePath)`. `ctx` provides `sandbox`, `session`, `channel`, `conversation`, and `trigger` (`"turn.started"` or `"call.settled"`). Return `{ instructions?, skills? }` to attach extra user-role instructions or dynamic skills for the session. If a rule throws, eve logs a warning and skips it without failing the turn or suppressing default instructions or other rules. Contributed skills use the extension namespace (such as `code__<name>`), require keys matching `/^[a-zA-Z0-9][a-zA-Z0-9_-]{0,57}$/` without an `eve__` prefix (invalid keys are skipped with a warning), and keep the first-entered repository's skill on name collisions.

```ts title="agent/extensions/code.ts"
import code from "eve/extensions/code";
import { defineSkill } from "eve/skills";

export default code({
  repositories: {
    discoverOnStart: "on-sandbox-use",
    rules: [
      {
        match: "acme/*",
        files: [".github/PULL_REQUEST_TEMPLATE.md"],
        async onEnter(repo) {
          const guide = await repo.readFile("CONTRIBUTING.md");
          return {
            instructions: guide?.content ? [guide.content] : undefined,
            skills: {
              repo_verify: defineSkill({
                description: "Run repository verification checks before opening a PR.",
                content: `Run tests and checks for ${repo.slug ?? repo.root} before publishing.`,
              }),
            },
          };
        },
      },
    ],
  },
});
```

### Repository sandbox helpers

`eve/extensions/code/sandbox` exports `discoverRepositories(sandbox, options?)` and `readRepositoryFile(sandbox, repoRoot, relativePath, options?)` for custom sandbox scripts and tools:

```ts
import { discoverRepositories, readRepositoryFile } from "eve/extensions/code/sandbox";

const repos = await discoverRepositories(sandbox, {
  roots: ["."],
  instructions: [["AGENTS.md", "CLAUDE.md"]],
  maxFileBytes: 64_000,
});
const readme = repos[0] ? await readRepositoryFile(sandbox, repos[0].root, "README.md") : null;
```

`readRepositoryFile` validates relative POSIX paths, keeps symlinks inside `repoRoot`, falls back to `HEAD:<relativePath>`, and applies `maxFileBytes`.

## Publish with the git extension

`eve/extensions/git` adds the GitHub instructions and the `pr` skill. Mount it next to the code extension when the agent should open pull requests. `code()` rejects a `github` option, so configure GitHub here. Import `gh` and the GitHub sandbox helpers from `eve/extensions/git/tools` and `eve/extensions/git/sandbox`:

```ts title="agent/extensions/git.ts"
import git from "eve/extensions/git";

export default git({});
```

`git({})` adds no tool and assumes the agent's shell already has GitHub credentials. The agent uses the `gh` and `git` CLIs in `bash`, and `git__pr` commits, pushes, and opens a draft with `gh pr create --draft`.

Configure `github` to get GitHub tokens through Vercel Connect instead. The extension then adds the authenticated `git__gh` tool and tells the agent to use it for every authenticated GitHub operation. `git__pr` switches to `gh-signed-commit` for repositories that require verified signatures.

`gh-signed-commit` adds or updates non-executable regular files and deletes tracked entries. It rejects additions or updates involving executable files, symlinks, submodules, or file-mode changes before contacting GitHub. Your staged changes remain intact. For those changes, use native `git commit -S` with a configured signing key, then `git push` through the authenticated tool.

| Option                 | Required      | Effect                                                                                                                                                       |
| ---------------------- | ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `github.connector`     | With `github` | Connector that mints a GitHub token                                                                                                                          |
| `github.broker`        | With `github` | `broker(sandbox, rules)` callback that installs, then removes, the GitHub credential rules                                                                   |
| `github.principalType` | With `github` | `"app"` for GitHub App installation tokens, or `"user"` for the caller's own token                                                                           |
| `github.authorize`     | With `github` | `authorize(request)` returns `true` to let a `gh` call run                                                                                                   |
| `github.attribution`   | No            | `attribution(ctx)` returns the current turn's `{ name, email }` co-author, or `null`                                                                         |
| `github.permissions`   | No            | With `"app"`, the installation permissions each token carries, such as `"contents:write"`                                                                    |
| `github.prefetchFiles` | No            | Relative file paths prefetched into `.git/objects` on partial clones while the lease is open. Defaults to `["AGENTS.md", "CLAUDE.md"]`; pass `[]` to disable |

With `"app"`, each token carries every permission the App holds unless `github.permissions` lists the ones it needs. Set it to keep tokens narrower than the App's installation without rewriting the credential rules in your broker.

After a successful `git clone`, `gh repo clone`, `git fetch`, `git pull`, `git checkout`, `git switch`, or `git sparse-checkout` on a partial clone inside the workspace, eve prefetches `github.prefetchFiles` into `.git/objects` before closing the GitHub credential lease. Prefetching leaves the working tree untouched so `eve/extensions/code` can read those files from `HEAD` after the lease ends. Pass `prefetchFiles: []` to disable prefetching.

Each `gh` call runs one `gh`, `git`, or `gh-signed-commit` command. Processes in the sandbox see only a placeholder `GH_TOKEN`. The sandbox firewall replaces it with the real token on GitHub requests. Your `github.broker` callback receives the header rules before the command runs, then `null` after it to remove them. The callback must keep your other network rules. GitHub authentication has no `"command"` delivery option.

### Control access with `authorize`

`github.authorize` is the agent's only access control. A command runs only when it returns `true`; otherwise the token never reaches the sandbox. It runs before every `gh` call and receives the parsed `argv`, the caller's `auth`, `repository`, and the minted `token`. What the token can reach depends on `principalType`:

| `principalType` | Token                                                                                                                                                          | `authorize` also receives      |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------ |
| `"app"`         | A GitHub App installation token for the declared repository, or for the whole installation when the call declares only an owner.                               | `owner`                        |
| `"user"`        | The caller's own token, which reaches everything the caller can reach on GitHub. eve asks the caller to sign in when needed and when GitHub rejects the token. | `repository: null`, no `owner` |

With `"user"`, `authorize` always receives `repository: null`, even when the command declares a repository. Repository allowlists therefore deny user-token calls. Use `"app"` with a full `owner/name` declaration when your policy restricts repository access. Use `"user"` only when your policy permits the caller's full GitHub access, and authorize the caller through `auth`.

In app-installation mode the token is shared, so `authorize` is the only check on the caller. While another person's message steers the turn, eve asks the caller before a `gh` command runs; see [A turn runs as one principal](/docs/concepts/security-model#a-turn-runs-as-one-principal). User mode uses the caller's own token, which eve holds instead.

```ts title="agent/extensions/git.ts"
import git from "eve/extensions/git";

import { brokerGitHubLease } from "../lib/github";

export default git({
  github: {
    connector: "github/my-agent",
    broker: brokerGitHubLease,
    principalType: "app",
    authorize: ({ owner }) => owner.toLowerCase() === "acme",
  },
});
```

### Credit the person behind a turn

The GitHub App is the author of commits that the `gh` tool makes. Return a verified user from
`github.attribution` to add that person's `Co-authored-by` trailer. eve adds it to
`gh-signed-commit` messages and to `gh pr create` bodies passed through `--body` or `--body-file`.
The callback receives the tool context, including `ctx.session.auth.current` and `ctx.getToken`.
Return `null` to omit attribution. eve keeps existing co-author trailers. Commands without a body
flag and direct `gh api` calls get no attribution.

For example, resolve the author through your application's user mapping:

```ts title="agent/extensions/git.ts"
import git from "eve/extensions/git";
import { brokerGitHubLease, coAuthorFor } from "../lib/github";

export default git({
  github: {
    connector: "github/my-agent",
    broker: brokerGitHubLease,
    principalType: "app",
    authorize: ({ owner }) => owner.toLowerCase() === "acme",
    attribution: (ctx) => coAuthorFor(ctx.session.auth.current),
  },
});
```

For a custom GitHub command tool, `eve/extensions/git/sandbox` exports `executeGitHubShell(input, config, dependencies)` and `githubShellApproval(input)`. `executeGitHubShell` parses the command, calls `authorize`, and installs the credential rules. `dependencies` supply the session ID and sandbox access. Use `githubShellApproval` as the tool's approval policy so invalid commands are still rejected. When the command's own input is refused before it runs, such as shell syntax, a `workingDirectory` outside the workspace, a `gh-signed-commit` directory that is not a repository root, or a missing `--body-file`, `executeGitHubShell` throws `GitHubCommandInputError`; detect it with `isGitHubCommandInputError(error)` to tell the agent's mistakes apart from configuration, Connect, and sandbox failures.

## Prepare the sandbox

Install the CLI tooling in your sandbox environment's `prepare` callback:

```ts title="agent/sandbox.ts"
import { defineSandbox } from "eve/sandbox";
import { VercelSandbox } from "eve/sandbox/vercel";
import { installCodeTooling } from "eve/extensions/code/sandbox";

export const environment = VercelSandbox.environment({
  prepare: async (sandbox) => {
    await installCodeTooling(sandbox, { vercel: true });
  },
});

export default defineSandbox(() => environment.open());
```

Preparation installs `gh` and wrappers for `gh`, `vc`, and `gh-signed-commit`. With the git extension's `github` configured, repositories that require verified signatures can use `gh-signed-commit` through the `gh` tool after staging changes.

eve rebuilds a prepared environment only when the sandbox file or environment options change. A change to an imported helper or to the eve version doesn't rebuild it.

## Troubleshooting

| What you see                                                                                                        | What to do                                                                                                                            |
| ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `eve-code firewall credential delivery requires a sandbox provider with mutable network policy (setNetworkPolicy).` | Set `vercel.delivery: "command"`, or pass a top-level `broker` callback.                                                              |
| `The current caller is not authorized to access <repository>.`                                                      | Your `github.authorize` callback returned `false` for that caller and repository. Check the callback's rule.                          |
| `Invalid extension config: eve-code no longer ships a worker subagent; ...`                                         | Remove the `worker` option from `code()`. To delegate work, use the [built-in `agent` tool](/docs/subagents#the-built-in-agent-tool). |
