`eve/extensions/code` (eve-code) turns an eve agent into a coding agent. It ships inside the `eve` package, so you mount it without installing anything else. The extension adds file-editing and search tools, coding skills, a read-only worker subagent, and helpers that install coding tools in the sandbox. GitHub and pull request work lives in the companion [`eve/extensions/git`](#publish-with-the-git-extension) extension.

<summary>How the benchmark works</summary>

The benchmark uses eve-bench and the DeepSWE-lean dataset. DeepSWE-lean has 12 feature and bug-fix tasks from DeepSWE v1.1.

- All harnesses use the same model and the same tasks.
- Each harness does each task 3 times.
- Each attempt runs in a new Vercel Sandbox.
- Each attempt has a limit of 20 minutes.
- The DeepSWE verifier examines the files that the agent leaves.
- An attempt passes only when the verifier passes.
- A crash or a timeout is a failure.

The line on each correctness row shows the 95% interval. When the lines of two harnesses overlap, the benchmark does not show a difference between them.

<details>
<summary>How the results update</summary>

1. A maintainer runs the `eve-code` workflow on `main` with the `deepswe-lean` dataset.
2. The workflow runs eve-code, opencode, and pi. It saves each complete result in the eve-bench result store.
3. The workflow commits a summary of the result to `main`.
4. The next docs deployment shows the new results.

The workflow skips incomplete runs, single-task runs, and pull request runs. Results can be older than `main`, because a maintainer starts each run. Select a harness name to open the GitHub Actions run for that result.

## Mount the extension

Create an extension file in your agent. The file name sets the prefix of every tool and subagent the extension adds, such as `code__grep`:

```ts title="agent/extensions/code.ts"
import code from "eve/extensions/code";

export default code({});
```

`code({})` mounts the extension without Vercel authentication. Omit `worker` to run the `worker` subagent on `openai/gpt-5.6-terra-fast` with `xhigh` reasoning.

## Configure the extension

| Option                         | Required      | Effect                                                                                         |
| ------------------------------ | ------------- | ---------------------------------------------------------------------------------------------- |
| `vercel.connector`             | With `vercel` | Vercel Connect connector that gets a Vercel token for the app, not for a user                  |
| `vercel.delivery`              | No            | `"firewall"` (default) or `"command"`                                                          |
| `broker`                       | No            | `broker(sandbox, rules)` callback that merges Vercel credential rules into your network policy |
| `worker.model`                 | With `worker` | Model for the `worker` subagent                                                                |
| `worker.reasoning`             | With `worker` | Reasoning level for the `worker` subagent                                                      |
| `worker.openaiReasoningEffort` | No            | Passed to OpenAI models as `reasoningEffort`                                                   |

```ts title="agent/extensions/code.ts"
import code from "eve/extensions/code";

export default code({
  vercel: { connector: "vercel/acme-bot" },
  worker: { model: "openai/gpt-5.6-terra-fast", reasoning: "high" },
});
```

### Credentials stay outside the sandbox

With firewall delivery, Vercel tokens never enter sandbox processes. Firewall delivery needs a top-level `broker` or a sandbox provider with `setNetworkPolicy()`. For other providers, set `vercel.delivery: "command"`.

To use a personal access token or another credential provider, omit the connector. Call `authenticateGitHub` or `authenticateVercel` from `eve/extensions/code/sandbox` in your own sandbox setup code. These helpers authenticate commands you run yourself, not the `gh` tool.

## Publish with the git extension

`eve/extensions/git` adds the GitHub instructions and the `pr` skill. Mount it next to the code extension when the agent should open pull requests. `code()` rejects a `github` option, so configure GitHub here. Import `gh` and the GitHub sandbox helpers from `eve/extensions/git/tools` and `eve/extensions/git/sandbox`:

```ts title="agent/extensions/git.ts"
import git from "eve/extensions/git";

export default git({});
```

`git({})` adds no tool and assumes the agent's shell already has GitHub credentials. The agent uses the `gh` and `git` CLIs in `bash`, and `git__pr` commits, pushes, and opens a draft with `gh pr create --draft`.

Configure `github` to get GitHub tokens through Vercel Connect instead. The extension then adds the authenticated `git__gh` tool and tells the agent to use it for every authenticated GitHub operation. `git__pr` switches to `gh-signed-commit` for repositories that require verified signatures.

| Option                 | Required      | Effect                                                                                     |
| ---------------------- | ------------- | ------------------------------------------------------------------------------------------ |
| `github.connector`     | With `github` | Connector that mints a GitHub token                                                        |
| `github.broker`        | With `github` | `broker(sandbox, rules)` callback that installs, then removes, the GitHub credential rules |
| `github.principalType` | With `github` | `"app"` for GitHub App installation tokens, or `"user"` for the caller's own token         |
| `github.authorize`     | With `github` | `authorize(request)` returns `true` to let a `gh` call run                                 |
| `github.attribution`   | No            | `attribution(ctx)` returns the current turn's `{ name, email }` co-author, or `null`       |

Each `gh` call runs one `gh`, `git`, or `gh-signed-commit` command. Processes in the sandbox see only a placeholder `GH_TOKEN`. The sandbox firewall replaces it with the real token on GitHub requests. Your `github.broker` callback receives the header rules before the command runs, then `null` after it to remove them. The callback must keep your other network rules. GitHub authentication has no `"command"` delivery option.

### Control access with `authorize`

`github.authorize` is the agent's only access control. A command runs only when it returns `true`; otherwise the token never reaches the sandbox. It runs before every `gh` call and receives the parsed `argv`, the caller's `auth`, the declared `repository` (or `null`), and the minted `token`. What the token can reach depends on `principalType`:

| `principalType` | Token                                                                                                                                                          | `authorize` also receives |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------- |
| `"app"`         | A GitHub App installation token for the declared repository, or for the whole installation when the call declares only an owner.                               | `owner`                   |
| `"user"`        | The caller's own token, which reaches everything the caller can reach on GitHub. eve asks the caller to sign in when needed and when GitHub rejects the token. | No `owner`                |

With `"user"`, `repository` is only what the model declared, and nothing ties it to the command. Treat it as a hint, not a boundary, and check `auth` instead, for example `({ auth }) => auth !== null`.

```ts title="agent/extensions/git.ts"
import git from "eve/extensions/git";

import { brokerGitHubLease } from "../lib/github";

export default git({
  github: {
    connector: "github/my-agent",
    broker: brokerGitHubLease,
    principalType: "app",
    authorize: ({ owner }) => owner.toLowerCase() === "acme",
  },
});
```

### Credit the person behind a turn

The GitHub App is the author of commits that the `gh` tool makes. Return a verified user from
`github.attribution` to add that person's `Co-authored-by` trailer. eve adds it to
`gh-signed-commit` messages and to `gh pr create` bodies passed through `--body` or `--body-file`.
The callback receives the tool context, including `ctx.session.auth.current` and `ctx.getToken`.
Return `null` to omit attribution. eve keeps existing co-author trailers. Commands without a body
flag and direct `gh api` calls get no attribution.

For example, resolve the author through your application's user mapping:

```ts title="agent/extensions/git.ts"
import git from "eve/extensions/git";
import { brokerGitHubLease, coAuthorFor } from "../lib/github";

export default git({
  github: {
    connector: "github/my-agent",
    broker: brokerGitHubLease,
    principalType: "app",
    authorize: ({ owner }) => owner.toLowerCase() === "acme",
    attribution: (ctx) => coAuthorFor(ctx.session.auth.current),
  },
});
```

## Override bundled tools

`eve/extensions/code/tools` exports the `apply_patch` and `grep` tool definitions. Import one in an override to change its approval or other options without copying the implementation. With the file mount above, name the override after the qualified tool, `code__apply_patch`:

```ts title="agent/tools/code__apply_patch.ts"
import { apply_patch } from "eve/extensions/code/tools";
import { defineTool } from "eve/tools";
import { always } from "eve/tools/approval";

export default defineTool({ ...apply_patch, approval: always() });
```

`agent/extensions/code/tools/apply_patch.ts` works only when the mount is a directory, `agent/extensions/code/extension.ts`.

For a custom GitHub command tool, `eve/extensions/git/sandbox` exports `executeGitHubShell(input, config, dependencies)` and `githubShellApproval(input)`. `executeGitHubShell` parses the command, calls `authorize`, and installs the credential rules. `dependencies` supply the session ID and sandbox access. Use `githubShellApproval` as the tool's approval policy so invalid commands are still rejected.

## Prepare the sandbox

Install the CLI tooling in your sandbox environment's `prepare` callback:

```ts title="agent/sandbox.ts"
import { defineSandbox } from "eve/sandbox";
import { VercelSandbox } from "eve/sandbox/vercel";
import { installCodeTooling } from "eve/extensions/code/sandbox";

export const environment = VercelSandbox.environment({
  prepare: async (sandbox) => {
    await installCodeTooling(sandbox, { vercel: true });
  },
});

export default defineSandbox(() => environment.open());
```

Preparation installs `gh`, wrappers for `gh`, `vc`, and `gh-signed-commit`, and TypeScript diagnostics. With the git extension's `github` configured, repositories that require verified signatures can use `gh-signed-commit` through the `gh` tool after staging changes.

eve rebuilds a prepared environment only when the sandbox file or environment options change. A change to an imported helper or to the eve version doesn't rebuild it.

## Troubleshooting

| What you see                                                                                                        | What to do                                                                                                   |
| ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `eve-code firewall credential delivery requires a sandbox provider with mutable network policy (setNetworkPolicy).` | Set `vercel.delivery: "command"`, or pass a top-level `broker` callback.                                     |
| `The current caller is not authorized to access <repository>.`                                                      | Your `github.authorize` callback returned `false` for that caller and repository. Check the callback's rule. |
