This page documents every part of `chatSdkChannel` from `eve/channels/chat-sdk`. For setup and common tasks, start with [Chat SDK](/docs/channels/chat-sdk).

The Chat SDK channel connects your agent to any [Vercel Chat SDK](https://chat-sdk.dev) adapter, such as `@chat-adapter/slack` or `@resend/chat-sdk-adapter`. It lives in a file under `agent/channels/`, such as `agent/channels/resend.ts`. You register handlers for the messages you care about, and call `send` to hand each one to eve. Use it for a surface without a built-in eve channel, or to manage credentials and state with Chat SDK instead of [Vercel Connect](/docs/guides/auth-and-route-protection).

The adapter handles provider auth, webhook verification, and posting messages, and you supply its state store. eve handles sessions, streaming, typing indicators, and human-in-the-loop prompts. Built-in channels such as [Slack](/docs/channels/slack) have their own APIs and take credentials from Vercel Connect or environment variables.

## Install

Add eve, the Chat SDK core (`chat`), an adapter, and a state adapter. The example below uses the Resend email adapter with the in-memory state store:

```bash
npm install eve@latest chat @resend/chat-sdk-adapter @chat-adapter/state-memory
```

Any Chat SDK adapter works, such as `@chat-adapter/slack`, `@chat-adapter/discord`, or `@chat-adapter/telegram`.

## Add the channel

`chatSdkChannel` returns `{ bot, channel, send }`. Register Chat SDK handlers on `bot`, and call `send` from those handlers to start or resume an eve session. Export `channel` as the module default:

```ts title="agent/channels/resend.ts"
import { createMemoryState } from "@chat-adapter/state-memory";
import { createResendAdapter } from "@resend/chat-sdk-adapter";
import type { Message, Thread } from "chat";
import { chatSdkChannel } from "eve/channels/chat-sdk";

export const { bot, channel, send } = chatSdkChannel({
  userName: "Resend Bot",
  // One webhook per adapter, at /eve/v1/<name>.
  adapters: {
    resend: createResendAdapter({
      fromAddress: "hello@example.com",
      fromName: "Resend Bot",
    }),
  },
  // In-memory state is for local development only.
  state: createMemoryState(),
  // Email can't edit a sent message, so post each reply once.
  streaming: false,
});

bot.onNewMention(async (thread: Thread, message: Message) => {
  await thread.subscribe();
  await send(message.text, { thread });
});

bot.onSubscribedMessage(async (thread: Thread, message: Message) => {
  await send(message.text, { thread });
});

export default channel;
```

- `state` takes any Chat SDK state adapter. In production, use a persistent adapter such as Redis or Upstash, so thread subscriptions and duplicate checks survive restarts.
- `send` accepts a string or an array of message parts. Call it inside a Chat SDK handler, because it starts the turn on the running webhook.
- Pass `idempotencyKey: message.id` to `send` so a retried message reaches the agent once within the session's [recent-key window](/docs/channels/custom#retried-deliveries). Chat SDK can mark a message as seen before eve accepts it, so a shared state adapter alone doesn't guarantee the agent gets it.

Deploy to Vercel production, linking the project if needed:

```bash
eve deploy
```

## Configure the webhook route

Each adapter serves `GET` and `POST` at `/eve/v1/{adapterName}`, so the `resend` adapter above is at `/eve/v1/resend`. Point your provider's webhook, such as the Resend inbound address or the Slack Event Subscriptions URL, at that path. The adapter handles each method. For example, X sends its verification challenge with `GET` and events with `POST`.

Set `route` to change the base path for every adapter, or `routes` to pin one adapter's path:

```ts
export const { bot, channel, send } = chatSdkChannel({
  userName: "Resend Bot",
  adapters: { resend: createResendAdapter({ fromAddress: "hello@example.com" }) },
  state: createMemoryState(),
  route: "/webhooks", // resend mounts at /webhooks/resend
  routes: { resend: "/webhooks/inbound-email" }, // …or pin it exactly
});
```

Use `routes` when a provider requires a fixed URL, or to keep an existing endpoint without changing the provider's settings.

## Dispatch

A turn starts when a handler you register on `bot` calls `send`:

- `bot.onNewMention(thread, message)` fires on a new `@mention`, or a new inbound thread on surfaces like email. Call `thread.subscribe()` so later replies in the thread keep reaching the agent.
- `bot.onSubscribedMessage(thread, message)` fires on later messages in a subscribed thread.
- `bot.onAction`, `bot.onReaction`, and `bot.onSlashCommand` fire for adapters that emit them.
- `bot.onModalSubmit`, `bot.onModalClose`, and `bot.onOptionsLoad` handle forms and dynamic selects. See [Cards and modals](#cards-and-modals).

`send(message, options)` starts or resumes the eve session. The `thread` you pass picks the session, so replies land on that thread:

```ts
bot.onNewMention(async (thread, message) => {
  // `title` sets the session's display title without changing the model message.
  await send(message.text, { thread, title: "Support request" });
});
```

`options` accepts `thread` and `adapterName`, plus the channel send options `auth`, `context`, `outputSchema`, `title`, `callback`, `turnPolicy`, and `idempotencyKey`. `auth` names who the turn runs as. Omit it for `null`, an anonymous turn.

To answer open approvals and questions from controls you render yourself, call `respond(answers, { thread, auth?, context? })`. It never creates a session. This example answers a custom button whose `value` carries the request's `interactionId`:

```ts
export const { bot, channel, send, respond } = chatSdkChannel({/* ... */});

bot.onAction("approve_deploy", async (event) => {
  if (!event.thread || !event.value) return;
  await respond([{ interactionId: event.value, optionId: "approve" }], { thread: event.thread });
});
```

## Cards and modals

`bot` is a Chat SDK `Chat` instance, not a separate eve handler API. Register Chat SDK handlers directly, and import card and modal builders from `chat`. eve serves the adapter's webhook and keeps its background work alive; the adapter handles interactive callbacks and acknowledgement responses.

| Chat SDK API                             | Use                                                                           |
| ---------------------------------------- | ----------------------------------------------------------------------------- |
| `bot.onAction(actionId, handler)`        | Handle a button or select action. `event.raw` preserves the platform payload. |
| `event.openModal(modal)`                 | Open a form from an action or slash command, using its short-lived trigger.   |
| `bot.onModalSubmit(callbackId, handler)` | Validate a submitted form and accept it or return a modal response.           |
| `bot.onModalClose(callbackId, handler)`  | Handle cancellation or closing when the modal sets `notifyOnClose: true`.     |
| `bot.onOptionsLoad(actionId, handler)`   | Supply options for an external select from `event.query`.                     |

These handlers also accept an array of IDs, or a handler without an ID filter. Availability and controls depend on the adapter. See the [Chat SDK documentation](https://chat-sdk.dev/docs) for its full UI API.

### Open and validate a Slack form

For a Slack app with custom forms, use `chatSdkChannel` with `@chat-adapter/slack`:

```bash
npm install eve@latest chat @chat-adapter/slack @chat-adapter/state-memory
```

This example posts a review button when mentioned, opens a modal on click, and previews the submitted text. It does not start an eve turn, save a review, or send an email.

```ts title="agent/channels/slack.ts"
import { createMemoryState } from "@chat-adapter/state-memory";
import { createSlackAdapter } from "@chat-adapter/slack";
import { Actions, Button, Card, CardText, Modal, TextInput } from "chat";
import { chatSdkChannel } from "eve/channels/chat-sdk";

export const { bot, channel, send, respond } = chatSdkChannel({
  userName: "Review Bot",
  adapters: {
    slack: createSlackAdapter({
      botToken: process.env.SLACK_BOT_TOKEN,
      signingSecret: process.env.SLACK_SIGNING_SECRET,
    }),
  },
  state: createMemoryState(), // Use a persistent state adapter in production.
});

bot.onNewMention(async (thread) => {
  await thread.post(
    Card({
      children: [
        CardText("Alice's follow-up draft is ready for review."),
        Actions([Button({ id: "edit_draft", label: "Edit", value: "draft-123" })]),
      ],
    }),
  );
});

bot.onAction("edit_draft", async (event) => {
  await event.openModal(
    Modal({
      callbackId: "sales_review",
      title: "Review draft",
      privateMetadata: event.value,
      notifyOnClose: true,
      children: [TextInput({ id: "line", label: "Follow-up line", multiline: true })],
    }),
  );
});

bot.onModalSubmit("sales_review", async (event) => {
  const line = event.values.line;
  if (!line?.trim()) {
    return { action: "errors", errors: { line: "Enter a follow-up line." } };
  }
  return {
    action: "update",
    modal: Modal({
      callbackId: "sales_review",
      title: "Review preview",
      privateMetadata: event.privateMetadata,
      notifyOnClose: true,
      children: [TextInput({ id: "line", label: "Follow-up line", initialValue: line })],
    }),
  };
});

export default channel;
```

Set the Slack app's **Event Subscriptions** and **Interactivity & Shortcuts** Request URLs to `/eve/v1/slack` on your deployment. Enable the `app_mention` event and the `app_mentions:read` and `chat:write` bot scopes, then install the app. The adapter manages credentials and signature verification; this configuration does not automatically inherit the first-class Slack channel's Vercel Connect setup. Do not mount both channels at the same webhook path. See [Slack setup](/docs/channels/slack/reference#manage-slack-credentials-yourself) for app settings.

### Submission responses and context

A modal submit handler returns Chat SDK's response shape, not Slack's `response_action` payload:

| Return value                                           | Effect on Slack                              |
| ------------------------------------------------------ | -------------------------------------------- |
| Nothing or `{ action: "close" }`                       | Closes the submitted modal.                  |
| `{ action: "errors", errors: { [inputId]: message } }` | Keeps the modal open and shows field errors. |
| `{ action: "update", modal }`                          | Replaces the modal view.                     |
| `{ action: "push", modal }`                            | Adds a modal view to the stack.              |
| `{ action: "clear" }`                                  | Closes the modal stack.                      |

Finish validation within Slack's three-second acknowledgement deadline. Handle expected failures by returning errors rather than throwing: Chat SDK logs modal-handler exceptions, and a thrown exception does not reliably keep a form open.

`event.openModal(...)` records the originating conversation in your state adapter. A later submission can include `event.relatedThread`, `event.relatedMessage`, and `event.relatedChannel` while that saved context is available. `event.privateMetadata` carries your own review ID. A modal opened outside this helper can still reach `onModalSubmit`, but it has no automatically restored conversation. For a native Slack view created outside Chat SDK, read its `private_metadata` from `event.raw.view.private_metadata`; `event.privateMetadata` expects Chat SDK's metadata encoding.

To hand the result to eve, use `send(message, { thread: event.relatedThread, auth })` to start or continue a turn. Use `respond(answers, { thread: event.relatedThread, auth })` to answer a pending question or approval instead. Check that `relatedThread` exists first. Authorize `event.user` against the stored review, persist accepted changes, and reject stale or repeated decisions before sending an email. A private metadata ID identifies a review; it does not authorize access.

### Native Block Kit state

Chat SDK's normalized `event.values` is a string map keyed by input ID. It is not the full Slack form state. For native controls such as checkboxes, multi-selects, and time pickers, validate and read the complete payload from `event.raw.view.state.values`. The same raw-payload escape hatch is available on action events for forms whose state arrives with a button click.

Keep native payload parsing in your app's Slack-specific code. Slack field-error keys are block IDs; Chat SDK's modal builders use each input ID as its block ID. Do not assume every Block Kit control has a Chat SDK builder or a normalized value. Chat SDK's modal context also depends on its state adapter; use persistent storage for production review flows.

## Steering

By default, a message that arrives while the agent is answering joins the running turn (`turnPolicy: "steer"`). The turn keeps its ID and completed tool work. [Message delivery and steering](/docs/concepts/execution-model-and-durability#message-delivery-and-steering) says when it applies. With no active turn, the message starts one.

Set `turnPolicy: "queue"` to let the active turn finish first:

```ts
bot.onSubscribedMessage(async (thread, message) => {
  await send(message.text, {
    thread,
    turnPolicy: "queue",
  });
});
```

Set the policy on `chatSdkChannel({ turnPolicy })` or per `send(...)`. `turnPolicy` governs overlapping eve turns, and Chat SDK's `concurrency` option governs overlapping webhook handlers. Use `concurrency: "concurrent"` so each new message reaches the running turn at once.

## Delivery

The default handlers post the agent's reply to the thread as markdown (`{ markdown: … }`), so adapters render rich text and email HTML.

By default the channel streams. It posts a message and edits it as text arrives (`content.delta`), at most once per `streamingEditIntervalMs`. A last edit adds the full text if needed, and the channel never posts the streamed reply again. If the final edit fails, the channel logs the error and posts a short notice with the error id. On the next message, it tells the model that the user hasn't seen its reply.

Set `streaming: false` for surfaces that send one message per turn or can't edit messages, such as email and WhatsApp. The reply then posts once, when the turn completes.

Where the adapter supports typing indicators, the channel shows `Working…` when a turn starts. On each tool call, it shows the call's [label](/docs/tools#label-tool-activity) or readable name, except for `eve__task_wait`, `eve__task_cancel`, and tools with `label: false`.

## Optional capabilities degrade gracefully

When an adapter's `startTyping` throws a `NotImplementedError`, or an error with code `NOT_IMPLEMENTED`, the channel skips typing indicators. An unsupported `editMessage` turns off streaming edits for the rest of the session, so later replies post once at the end. A reply that already has a streamed message still gets the final edit attempt, and a failure is reported as above. Use the same check in custom `events` with `isNotImplemented`:

```ts
import { isNotImplemented } from "eve/channels/chat-sdk";
```

Override any default by passing `events`. Handlers receive `(event, ctx)`, with the rebuilt Chat SDK thread on `ctx.channel.thread`:

```ts
chatSdkChannel({
  userName: "Resend Bot",
  adapters: { resend: createResendAdapter({ fromAddress: "hello@example.com" }) },
  state: createMemoryState(),
  events: {
    "content.completed"(event, ctx) {
      const { kind, phase, value } = event.data;
      if (kind !== "text" || phase !== "reply" || typeof value !== "string" || !ctx.channel.thread)
        return;
      return ctx.channel.thread.post({ markdown: value });
    },
  },
});
```

## Human-in-the-loop (HITL)

Approvals and questions render as a Chat SDK `Card` with buttons, and the channel wires `bot.onAction` to `respond`, so clicks resume the session. Adapters that can't render cards, such as Photon iMessage, get text with numbered options:

- A reply sent through `send` with an option's number or label answers the request. For example, `1` or `approve` runs an approval-gated tool, and `2` or `deny` stops it.
- If the question allows a custom answer or has no options, any other text is the answer.

Set `inputActionPrefix` if your app already uses the default `eve_input:` prefix. Set `resolveInputAuth` to keep user or tenant auth when a click resumes the session:

```ts
chatSdkChannel({
  userName: "Support Bot",
  adapters: { slack: createSlackAdapter() },
  state: createMemoryState(),
  resolveInputAuth: (event) => ({
    authenticator: "slack",
    principalType: "user",
    principalId: event.user?.userId ?? "unknown",
    attributes: {},
  }),
});
```

## Sign-ins

When a tool needs a connection the person hasn't authorized, eve shows a sign-in prompt with the connection's link, code, or instructions. In a direct message, eve posts the prompt in the thread and edits it once the sign-in completes.

Elsewhere, the prompt is a credential, so eve sends it only to the person signing in. It uses an ephemeral message where the adapter supports one, and otherwise a direct message. The thread gets a status without the link, which eve edits once the sign-in completes.

eve finds that person by matching the turn's `auth` user to the author of the message you passed to `send`. Private sign-ins need both of these:

- per-person `auth` on each `send`, so each `auth` names one person; and
- the handler's `Thread` object as `thread`, rather than a thread id string, so eve sees who wrote the message.

```ts
bot.onSubscribedMessage(async (thread, message) => {
  await send(message.text, {
    thread,
    auth: {
      authenticator: "slack",
      principalType: "user",
      principalId: message.author.userId,
      attributes: {},
    },
  });
});
```

Without both, including with the default `auth: null`, the thread gets only a notice to continue in a direct message, and the prompt isn't shown anywhere. The same happens when several people share one `auth`, such as tenant auth, or when the adapter has neither ephemerals nor `openDM`.

## Proactive sessions

To start a session without an incoming webhook, call `to(channel, target).send(message, { auth })` from a schedule `run` handler, or `ctx.to(channel, target).send(message, { auth })` from another channel. The target is a serialized Chat SDK thread, or `{ threadId, adapterName }` when you have only a provider-native thread id:

```ts
await to(channel, { adapterName: "resend", threadId: "resend:user@example.com" }).send(
  "Your weekly digest is ready.",
  { auth: null },
);
```

## Attachments

To forward a Chat SDK message's attachments, convert it with `messageContentOf`. It returns `message.text` when there are no attachments. Otherwise it returns message parts: the text, plus one part per attachment:

```ts
import { messageContentOf } from "eve/channels/chat-sdk";

bot.onNewMention(async (thread, message) => {
  await send(messageContentOf(message), { thread });
});
```

When the adapter sets `fetchData`, as the Slack, Google Chat, WhatsApp, and Twilio adapters do, eve downloads the attachment when the turn runs. It uses the adapter's credentials and `rehydrateAttachment`, and passes the file bytes, because the model provider can't open platform URLs that need credentials. An attachment with only a URL is downloaded when the URL is public `https:`.

Every other attachment reaches the agent as a short note, so the agent still knows a file was sent. This covers:

- an attachment from an adapter without `rehydrateAttachment`;
- a non-public URL or a failed download;
- a file over 25 MB; and
- an attachment with neither a download nor a URL.

Audio attachments, such as voice notes, reach the model as a file label, not as sound. To answer them, give the agent a transcription tool; see [Voice notes](/docs/patterns/voice-notes).

See [File uploads](/docs/channels/custom#file-uploads) for how eve prepares remote file URLs before the model call.

## Audience

Workspace-visible threads are `public`, DMs and private or external threads are `private`, and threads of unknown visibility are `unknown`. The audience controls which message content observability records, not who can access the thread. See [Audience](/docs/channels#audience).

## Options

| Option                    | Default      | Purpose                                                                  |
| ------------------------- | ------------ | ------------------------------------------------------------------------ |
| `adapters`                | —            | Map of adapter name to Chat SDK adapter instance. One webhook per entry. |
| `state`                   | —            | Chat SDK state adapter for subscriptions, locks, and dedupe.             |
| `userName`                | —            | Display name for the bot (a standard Chat SDK `ChatConfig` field).       |
| `route`                   | `/eve/v1`    | Base path for generated adapter webhooks (`{route}/{adapter}`).          |
| `routes`                  | —            | Per-adapter path overrides for fixed or migrated webhook URLs.           |
| `turnPolicy`              | `"steer"`    | `"steer"` or `"queue"`. `send(...)` can override it per message.         |
| `streaming`               | `true`       | Post-then-edit streaming. Set `false` for one-message-per-turn surfaces. |
| `streamingEditIntervalMs` | `1000`       | Minimum interval between streaming edits.                                |
| `events`                  | built-in     | Per-event handlers. A supplied handler replaces that built-in default.   |
| `inputActionPrefix`       | `eve_input:` | Prefix for default HITL button action ids.                               |
| `resolveInputAuth`        | `null`       | Auth resolver applied when a HITL button click resumes a session.        |
| `webhook`                 | —            | Extra Chat SDK webhook options (eve owns `waitUntil`).                   |

Any other Chat SDK `ChatConfig` field (for example `concurrency`) is accepted and passed through.
