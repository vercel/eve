The Slack channel connects your agent to a Slack workspace through `agent/channels/slack.ts`. It answers mentions, DMs, slash commands, shortcuts, and button clicks, replies in threads, and shows approvals and questions as buttons. See [Channels](./overview) for what every channel shares.

[Vercel Connect](https://vercel.com/kb/guide/vercel-connect) holds the bot token, rotates it, verifies requests, and supports installs in several workspaces, so no Slack secrets go into your project environment. Without Connect, you provide the bot token and signing secret yourself.

## Add the channel

Run the guided setup from your agent project:

```bash
eve add channel/slack
```

With Vercel Connect, setup does these steps:

1. Signs you in to Vercel and links a project.
2. Reuses or creates a Slack app (a Connect connector) and prompts you to install it in a workspace.
3. Routes the app's events to `/eve/v1/slack`.
4. Writes the channel file:

```ts title="agent/channels/slack.ts"
import { connectSlackCredentials } from "@vercel/connect/eve";
import { slackChannel } from "eve/channels/slack";

export default slackChannel({
  credentials: connectSlackCredentials("slack/my-agent"),
});
```

Deploy with `eve deploy` once setup finishes.

### Resume setup

Run `eve add channel/slack` again if setup stops partway or Slack events stop reaching the agent. Setup runs only the missing steps, and finishes the connector that `agent/channels/slack.ts` names without prompting. It never runs `vercel connect detach`, which would remove the project's token access and trigger destinations.

### Manage Slack credentials yourself

Choose **Use portable credentials** when the agent doesn't run on Vercel or you can't use Vercel Connect. eve adds `SLACK_BOT_TOKEN` and `SLACK_SIGNING_SECRET` to `.env.example` but doesn't create the Slack app. In [Slack app settings](https://api.slack.com/apps):

1. Add the `app_mentions:read` and `chat:write` bot scopes, plus `im:history` for DMs, `files:read` for inbound attachments, and `files:write` for long-response snippets.
2. Install the app, then set `SLACK_BOT_TOKEN` to its Bot User OAuth Token and `SLACK_SIGNING_SECRET` to the signing secret from **Basic Information**. Put both in `.env.local` for local development or in the deployed runtime's environment.
3. Set the Request URL to `https://your-agent.example/eve/v1/slack` under **Event Subscriptions** (subscribe to `app_mention`, plus `message.im` for DMs), **Interactivity & Shortcuts**, and each **Slash Command**.

For an app installed in several workspaces, pass a function as `botToken`. It receives the installation workspace as `{ teamId }`: `credentials: { botToken: ({ teamId }) => loadInstallationToken(teamId) }`. Reject a missing `teamId` instead of falling back to a default installation.

## How the channel handles inbound events

Without hooks, the channel answers app mentions and DMs and ignores other messages. Add hooks to `slackChannel(...)` to decide who can start a turn and which messages reach the agent.

### Message hooks

A message hook decides whether a Slack message starts a turn:

- Return `{ auth }` to start a turn, or `null` to drop the message.
- Add `context` to put background in history.
- Add `history` to bring in prior conversation; see [Start from prior history](./eve#start-from-prior-history).
- Add `title` to set the run title. Public conversations otherwise use the message text; DMs and private channels always use `Private message`.

| Incoming event                    | Handler order                                                       |
| --------------------------------- | ------------------------------------------------------------------- |
| App mention                       | `onAppMention` → `onMessage` → `onEvent` → built-in mention default |
| Direct message                    | `onDirectMessage` → `onMessage` → `onEvent` → built-in DM default   |
| Un-mentioned code channel message | `onMessage` → `onAppMention` → `onEvent` → built-in default         |
| Other Slack message               | `onMessage` → `onEvent` → ignore                                    |
| Other Events API event            | `onEvent` → ignore                                                  |

Only the first defined handler runs. A hook that returns `null` drops the message instead of passing it down the table.

- `onAppMention(ctx, message)` handles `app_mention`. By default, it identifies the sender within their workspace.
- `onDirectMessage(ctx, message)` handles DMs, which need `message.im` and `im:history`. It never receives bot messages or edits.
- `onMessage(ctx, message)` handles other posted messages. `ctx.isBotMentioned()` and `ctx.isSubscribed()` let you answer only mentions or active threads.

eve drops the app's own messages before any hook runs. Other bots' messages reach `onMessage`; check `message.author?.isBot` to ignore them.

Hooks don't post anything. eve still acknowledges the message, shows progress, and posts the reply. To change what the agent posts, add [renderers](#customize-rendering).

`onInteraction(action, ctx)` handles clicks on your own buttons and selects (`block_actions`). Clicks on eve's approval and question controls go to `onAnswers(ctx, submission)` instead. To open a modal from a button, pass `action.triggerId` to `ctx.slack.request("views.open", { trigger_id, view })` within about 3 seconds. eve adds the clicking user's Slack ID to the model message.

`onShortcut(shortcut, ctx)` handles message and global shortcuts configured under **Interactivity & Shortcuts**. It receives the callback ID, user, workspace, and trigger ID, plus the message and channel for a message shortcut.

`onSlashCommand(command, ctx)` handles **Slash Commands**. It receives the command, argument text, user, channel, workspace, trigger ID, and response URL. Both handlers can call the Slack API for the workspace. eve acknowledges the request immediately while the handler runs in the background:

```ts title="agent/channels/slack.ts"
import { slackChannel } from "eve/channels/slack";

export default slackChannel({
  async onSlashCommand(command, ctx) {
    if (command.command !== "/ask") return;
    await ctx.slack.request("chat.postEphemeral", {
      channel: command.channelId,
      user: command.user.id,
      text: `Received: ${command.text}`,
    });
  },
});
```

The model sees each message as a `<slack_message>`. Its metadata blocks are `<sender>` with the sender's `type` and `id`, `<bot>` with the receiving app's `id` and `mentioned` (inbound messages only), and `<thread>`:

```text
<slack_message>
<sender>
type: user
id: U01234567
</sender>
<bot>
id: U07654321
mentioned: true
</bot>
<thread>
team_id: T01234567
channel_id: C01234567
thread_ts: 1700000000.000001
message_ts: 1700000000.000004
</thread>
<content>
<@U07654321> Who owns the deploy?
</content>
</slack_message>
```

`<content>` converts mrkdwn to Markdown but keeps `<@USER_ID>` mentions intact. It also includes the text of link previews and shared messages.

#### Add sender names and emails

Slack user ids identify every sender without a lookup. When the agent should also know who someone is, enable `messageContext.users`:

```ts
import { slackChannel } from "eve/channels/slack";
import { connectSlackCredentials } from "@vercel/connect/eve";

export default slackChannel({
  credentials: connectSlackCredentials("slack/my-agent"),
  messageContext: { users: { email: true } },
});
```

eve looks up each human sender with `users.info` and adds `display_name` and `real_name` to their `<sender>` block, plus `email` with `email: true`. Set `name: false` with `email: true` to add emails only. Thread context replies get the same fields. The triggering author is also written to `message.author` (`fullName`, `displayName`, `email`) and to the `full_name` and `email` attributes of [`defaultSlackAuth`](#restrict-who-can-invoke-the-agent), so a hook can gate on them. Mentions and DMs are looked up before `onAppMention` or `onDirectMessage` runs. Other channel messages are looked up only once a hook delivers them, so their hooks see the unresolved author.

`users: true` adds names only. Results are cached in memory per workspace and user for an hour, and a failed lookup is retried after a minute. A lookup that fails or takes longer than two seconds is left out, and the message is still delivered. To use your own cache, pass `resolve`; `next()` is eve's uncached `users.info` call:

```ts
import { slackChannel } from "eve/channels/slack";
import { connectSlackCredentials } from "@vercel/connect/eve";
import { profileCache } from "../lib/profile-cache";

export default slackChannel({
  credentials: connectSlackCredentials("slack/my-agent"),
  messageContext: {
    users: {
      email: true,
      resolve: async ({ userId, teamId }, next) => {
        const key = `${teamId}:${userId}`;
        const cached = await profileCache.get(key);
        if (cached) return cached;
        const profile = await next();
        await profileCache.set(key, profile);
        return profile;
      },
    },
  },
});
```

`teamId` is the workspace whose installation received the message, so key caches on it. `messageContext.users` adds the `users:read` scope to the app manifest, and `users:read.email` with `email: true`; reinstall the Slack app after enabling it. It is off by default because names and emails then reach model context, session history, and traces.

#### Restrict who can invoke the agent

A valid Slack signature proves that Slack sent the event, not that the sender should reach your agent. Check the user and conversation in every inbound handler before returning auth. This matters most in Slack Connect channels, where external users can post:

```ts title="agent/channels/slack.ts"
import { connectSlackCredentials } from "@vercel/connect/eve";
import { defaultSlackAuth, slackChannel, type SlackMessage } from "eve/channels/slack";

const allowedConversations = new Set(["C01234567", "D01234567"]);
const allowedUsers = new Set(["U01234567"]);

function isAllowedUser(message: SlackMessage) {
  const userId = message.author?.userId;
  return Boolean(userId && allowedUsers.has(userId));
}

export default slackChannel({
  credentials: connectSlackCredentials("slack/my-agent"),
  onAppMention(ctx, message) {
    if (!isAllowedUser(message) || !allowedConversations.has(message.channelId)) {
      return null;
    }
    return { auth: defaultSlackAuth(message, ctx) };
  },
  onDirectMessage(ctx, message) {
    if (!isAllowedUser(message) || !allowedConversations.has(message.channelId)) {
      return null;
    }
    return { auth: defaultSlackAuth(message, ctx) };
  },
  onAnswers(ctx, submission) {
    if (!allowedUsers.has(submission.user.id) || !allowedConversations.has(ctx.slack.channelId)) {
      return null;
    }
    return { auth: ctx.defaultAuth };
  },
});
```

- Override every enabled inbound handler, because an omitted `onDirectMessage` keeps eve's default DM behavior.
- Apply the same policy in `onAnswers`, so someone who can't start a turn can't resume one by clicking an approval button.
- If access depends on organization membership, resolve it from Slack's shared-channel and user data.
- Keep authorization checks in sensitive tools too. The allowlist controls who starts a turn; tool checks control what that user may read or change.

`defaultSlackAuth` and `ctx.defaultAuth` identify a person as `slack:<team>:<user>`. `<team>` is the app installation workspace when Slack reports one, otherwise the event's team. A Slack Connect user keeps one identity, and one connection sign-in, across messages and button clicks.

`onAnswers` runs when someone clicks an approval or question control, before the session resumes:

- Return `{ auth }` to accept the answer.
- Return `null` or throw to reject it and keep the request and its controls open.
- `ctx.defaultAuth` identifies the person who clicked but doesn't authorize them.
- Without `onAnswers`, Slack accepts every answer with the clicking user's auth.

While `onAnswers` or `approvalChannel` is set, only the Slack controls answer a pending request. A message typed in the thread or DM reaches the agent as a new message under the [turn policy](#control-overlapping-turns). With the default `"steer"` policy, it withdraws an open question.

Post sensitive requests in conversations limited to the intended approvers. Re-check `ctx.session.auth.current` in a sensitive tool before it changes anything.

#### Continue conversations without repeated mentions

Use `onMessage` to answer explicit mentions and continue replies in threads that already have an eve session:

```ts title="agent/channels/slack.ts"
export default slackChannel({
  credentials: connectSlackCredentials("slack/my-agent"),
  async onMessage(ctx, message) {
    if (message.author?.isBot) return null;
    return (await ctx.isDMOrPrivateChannel()) || ctx.isBotMentioned() || (await ctx.isSubscribed())
      ? { auth: null }
      : null;
  },
});
```

- `isDMOrPrivateChannel()` returns `true` for DMs, group DMs, and private channels. It also returns `true` when it can't tell, such as on a missing scope or API error, so privacy-sensitive behavior fails closed.
- `isBotMentioned()` checks for an explicit mention.
- `isSubscribed()` checks whether the thread has an active eve session.

Thread replies need extra subscriptions. With Vercel Connect, open **Advanced** when creating the connector. Add `message.channels` under **Trigger Event Types** and `channels:history` under **Bot Scopes**. Private channels also need `message.groups` and `groups:history`.

`ctx.thread.listParticipants()` returns the thread's unique human Slack user IDs in the order they first posted. In a thread a person started, the first ID is that person:

```ts
async onMessage(ctx, message) {
  if (!message.author || message.author.isBot) return null;

  const participants = await ctx.thread.listParticipants();
  const isGroupFollowUpFromStarter =
    participants.length > 1 && participants[0] === message.author.userId;

  return isGroupFollowUpFromStarter ? { auth: null } : null;
}
```

It reads at most the first 50 messages and needs the matching history scope. A failed fetch is logged and returns an empty or stale list, so treat an unexpected empty list as "don't route".

#### Load prior thread messages

By default, the agent sees the triggering mention but not earlier replies in the thread. Set `threadContext` to add them, labeled with each sender's Slack user ID:

```ts
import { slackChannel } from "eve/channels/slack";
import { connectSlackCredentials } from "@vercel/connect/eve";

export default slackChannel({
  credentials: connectSlackCredentials("slack/my-agent"),
  threadContext: { since: "last-agent-reply" },
});
```

`since` sets where each mention's context starts:

- `"thread-root"` (default, same as `threadContext: {}`): every prior message in the thread.
- `"last-agent-reply"`: messages after this app's last reply, so repeated mentions add only what's new. Other bots' replies don't move the boundary.
- A predicate `(message: SlackThreadMessage) => boolean`: messages after the last one it matches.

`threadContext` requires the matching Slack history scope. Use `loadThreadContextMessages` to filter or process the raw thread messages yourself.

When the triggering message starts the thread's session, eve adds the earlier replies as session history. This app's replies become assistant turns, and other replies become user messages with their Slack user IDs. Those assistant turns hold what Slack shows, which can differ from what the model wrote. Later messages in the thread get the earlier replies as a transcript instead. A hook that returns its own `history` also gets the transcript.

#### Control overlapping turns

A Slack message sent during a running turn joins that turn by default (`turnPolicy: "steer"`). See [Overlapping messages](./overview#overlapping-messages) for when it interrupts the model. Set `turnPolicy: "queue"` to let every running turn finish first:

```ts title="agent/channels/slack.ts"
export default slackChannel({
  credentials: connectSlackCredentials("slack/my-agent"),
  turnPolicy: "queue",
});
```

Message and interaction hooks expose the thread's session operations on `ctx`:

```ts
async onAppMention(ctx) {
  // Independent examples; a handler normally calls one.
  await ctx.send("Run a separate turn."); // the only call that can create a session
  await ctx.respond(answers);
  await ctx.cancel(); // stop without sending input, as for a Stop button
  await ctx.compact();
  await ctx.clear();
  await ctx.end({ reason: "Start over" });
  const session = await ctx.resolveSession(); // pin later work to the current session ID
  return { auth: null };
}
```

`ctx.send()` uses the Slack sender's auth unless you pass `auth`. Each operation returns a `Delivery` receipt. `ctx.cancel()` does nothing on an idle session and throws `SessionNotActiveError` on a thread without a session.

#### End a conversation

`ctx.end({ reason? })` ends the thread's session, including any running turn. The next message starts a new session with fresh history, state, and sandbox:

```ts title="agent/channels/slack.ts"
export default slackChannel({
  credentials: connectSlackCredentials("slack/my-agent"),
  async onMessage(ctx, message) {
    if (message.text.trim() !== "/new") return null;

    await ctx.end({ reason: "Slack user requested /new" });
    await ctx.thread.post("Started a fresh conversation.");
    return null;
  },
});
```

- `await delivery.result()` waits until the session has ended and the thread is free for a new one.
- A thread without a session throws `SessionNotActiveError`.
- Return `null` after `ctx.end()` to treat the message as a command, or `{ auth }` to make it the first turn of the new session.
- `onInteraction` gets the same operations, so a **New conversation** button can end the session too.

### Attachments

The agent receives the files attached to the message that reaches it. A mention without files also gets the files posted in the thread since the app's previous mention. A person can share a file and then ask about it.

- The lookback covers up to 10 messages back and up to 1,000 replies into the thread, and skips the app's own messages.
- DMs and threads the app answers without a mention get no lookback.
- Files shared from services such as Google Drive or Dropbox are links, not Slack files, so they stay in the message text.
- A download that fails or takes longer than 30 seconds reaches the model as a note.
- Voice clips reach the model as an audio file label, not sound. See [Voice notes](../patterns/voice-notes) to transcribe them.

Images, PDFs, audio, video, and other files all reach the agent. See [Inbound attachments](../sandbox#inbound-attachments) for which files the model reads directly.

Private downloads use the session's app installation and need the `files:read` scope. Add it and reinstall the app before sending attachments. Downloads cover Slack's file hosts and URLs under [`api.fileBaseUrl`](#point-the-channel-at-a-different-slack-api-host), and use `api.fetch` when it's set. See [File uploads](./custom#file-uploads) for the `fetchFile` contract.

eve saves files in the session sandbox under `/workspace/.eve/attachments`, and history keeps only that path. If eve can't reattach the original sandbox, later turns get a missing-file result. Store files outside the sandbox when the agent must keep them.

## Delivery

eve shows short work, such as reasoning and tool calls, in the thread status. It shows [tasks](/docs/tools/tasks) in a [task card](#task-card). Replies post as ordinary messages.

| Moment                                            | Thread status                                                                                           |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| A mention or DM arrives                           | `Thinking...`, while the message hook decides                                                           |
| The message hook drops the message                | Cleared                                                                                                 |
| The turn starts                                   | `Thinking...`                                                                                           |
| The model reasons                                 | Its latest reasoning heading, or its latest finished sentence                                           |
| The model calls tools                             | Its narration before the calls, or the first action label, such as `Search useEveAgent`, plus `+N more` |
| A tool reports progress                           | The tool's `label.delta` text                                                                           |
| A tool finishes                                   | The tool's `label.complete` text, when it defines one                                                   |
| The model starts its next step                    | `Reviewing researcher's results...` after a task finishes, otherwise unchanged                          |
| The model streams a long reply                    | `Writing a reply...`, once the text passes 280 characters                                               |
| The turn waits on its tasks                       | `Waiting on researcher...`, or `Waiting on 3 tasks...`                                                  |
| The turn waits on an approval, answer, or sign-in | Cleared until the turn resumes                                                                          |
| A reply posts                                     | Cleared by Slack                                                                                        |

- The status always names the latest work and doesn't fall back to `Thinking...` between steps.
- Each status stays up at least three seconds and is cut to 50 characters at a word boundary.
- Action labels skip `eve__task_wait` and `eve__task_cancel`. They can include part of the call's input, such as a search query or `bash` command.

Slack clears a thread status after two minutes without a message from the app. A tool that runs longer than two minutes without reporting progress loses its status. Report progress with [`label.delta`](/docs/tools#label-tool-activity), or run the work as a [task](/docs/tools/tasks).

Replies up to 12,000 characters post inline. A longer reply uploads as an `eve-response.md` snippet, with a short note in the thread. eve also uploads a reply that Slack refuses as too large or malformed: `msg_too_long`, `msg_blocks_too_long`, `msg_blocks_too_many`, `invalid_blocks`, or `invalid_blocks_format`. Snippets need the `files:write` scope and keep any change a [renderer](#customize-rendering) made, such as a redaction. eve logs each fallback in a `Slack refused the final reply` warning, without the reply text.

The final reply can still fail: the upload fails, Slack returns another error, or a renderer throws. eve then posts this notice in the thread: `I finished, but couldn't deliver my answer in Slack (error id ...). Please ask me to resend it.`

- The error ID matches the `final reply was not delivered to Slack` line in the Vercel runtime logs.
- The notice carries no reply content. eve never re-sends the reply or retries the model.
- The next message tells the model its reply wasn't delivered.
- Other failed posts, such as status updates, are logged and skipped.

Text the model writes while its tasks keep working posts as its own message, and the reply after the results posts as another. A schedule's session posts only the final reply.

Outbound `@name` text stays literal. To mention a user, write `<@USER_ID>`, or call `ctx.channel.thread.mentionUser(userId)` in a renderer.

Approval and question cards show their prompt, tool input, and answer as literal text. eve escapes `&`, `<`, and `>` there, so `<!channel>` or `<url|label>` in a model-written prompt shows as typed instead of notifying the channel or hiding a link. `Card(...)` text, fields, and subtitles are Slack mrkdwn, so mentions and links you write there render. Escape untrusted values you put in a card yourself: `&` as `&amp;`, `<` as `&lt;`, and `>` as `&gt;`.

## Task card

When a turn starts its first task, eve posts a task card in the thread. eve updates the card in place until the turn and its tasks finish. One task shows as a Slack `task_card` block; several show as a `plan` block with one row per task. Work inside a task, including the tasks it starts, adds no rows. The card needs only the `chat:write` scope. Schedule sessions and sessions without a Slack thread get no card.

Each row shows:

- **Title:** the tool's [`label.start`](/docs/tools#label-tool-activity), or the tool name in words without its namespace, so `crm__sync_accounts` shows as `Sync accounts`. A connection call shows as `Linear: List issues`. An agent task shows the agent name plus the first sentence of its brief, as in `Researcher: Find the incidents behind the checkout spike`. Set `label.start` for exact casing, because `github` shows as `Github`.
- **Waiting:** `Waiting for approval`, or the matching text for an answer or sign-in. In a DM or private channel, the row also shows the request's prompt.
- **Done:** the first sentence of the result, cut to about 100 characters. A task that ran a second or more adds its duration: `Done in 1m 14s: Found three incidents.`
- **Failed:** `Failed`, or `Failed after 3m`. In a DM or private channel, the row adds the error's first sentence, as in `Failed: Rate limited`.
- **Stopped:** `Stopped early since it was no longer needed` when the model cancelled it with `eve__task_cancel`, `Stopped by request` when the turn was [cancelled](#message-hooks), `Stopped when the turn ended`, or `Stopped`. Only the model-cancelled row shows a success check.

The plan title summarizes the turn, from `Working on 2 tasks` and `1 of 2 tasks done` to `Finished 3 tasks in 5m 12s: 1 failed, 1 stopped`. When every task calls one of at most three declared or remote agents, the title names them: `Asking researcher and reviewer`, then `Waiting on reviewer · 1 of 2 tasks done`. Tasks the model cancelled count as finished, not stopped.

- Messages sent while tasks work continue the same turn.
- If that turn starts a task after every task on its card has finished, eve finishes that card and posts a new one.
- A resumable task continued in a later turn appears in that turn's card.
- A failed card update never fails the turn, and eve posts a deleted card again on its next change.

## Human-in-the-loop (HITL)

Approvals and questions show as Slack buttons and selects, and **Type your answer** opens a modal. Answers pass through `onAnswers` before the session resumes. Approval cards pair **Deny** with a primary **Approve** button.

Set `approvalChannel` to choose where each request appears, including tool approvals and `ctx.ask()` questions. Return `"direct-message"` to show it only to the Slack user who triggered the turn, or `"thread"` for the shared thread:

```ts title="agent/channels/slack.ts"
import { slackChannel } from "eve/channels/slack";

export default slackChannel({
  approvalChannel: (request) =>
    request.request.kind === "question" || request.call?.name === "review_answer"
      ? "direct-message"
      : "thread",
});
```

The callback receives the request (an `Interaction`) and the `SessionContext`. Omit it to keep every request in the thread. If eve can't find the Slack user for a direct message, it logs the request and posts nothing, so private requests fail closed. `onAnswers` or the tool's approval policy still decides who may answer.

Each approval, question, and budget prompt card updates as its request changes:

- Once eve accepts an answer, the card shows the answer and who gave it instead of the buttons, even while other requests from the same step wait. If a policy refuses the answer, the buttons come back.
- When several requests share one message, answering one updates only its part.
- Once the request ends, eve deletes the tool-input post after the last request it covers ends. It also updates a direct-message request's `Waiting on approval` note in the thread.
- A request that ends without a click, such as when the person replies in the thread or the request is withdrawn, reads `No longer needed`.
- A click on a request whose session has ended marks the card `No longer active`, and an ephemeral message tells the person to send a new message. A freeform answer submitted then replaces the whole message, including requests grouped with it.

To change how these cards look, use [`interactionCard`](#restyle-approval-and-question-cards).

A sign-in link or device code is a credential: whoever completes it connects their account to the session. So eve posts a status without the link in the thread. It sends the sign-in ephemerally to the Slack user it's for, and updates the status when the sign-in ends. The private prompt pairs a **Connect** button, labeled with the service name, with **Cancel**, which ends the waiting turn and updates the public status. To deliver a sign-in another way, see [Render and decode HITL controls yourself](#render-and-decode-hitl-controls-yourself).

## Audience

Public channels are `public`; DMs, group DMs, and private channels are `private`. When an event doesn't say what kind of conversation it came from, eve asks Slack. It treats an unclear or failed lookup as `private`. The audience controls what traces capture, not who can use the channel. See [Audience](./overview#audience).

## Options

Pass these to `slackChannel(...)`. Every option is optional.

| Option                                          | What it does                                                                                                                        |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `credentials`                                   | The bot token, from `connectSlackCredentials(...)` or [your own](#manage-slack-credentials-yourself).                               |
| `onAppMention`, `onDirectMessage`, `onMessage`  | Decide whether a message starts a turn. See [Message hooks](#message-hooks).                                                        |
| `onAnswers`                                     | Accepts or rejects a click on an approval or question. See [Restrict who can invoke the agent](#restrict-who-can-invoke-the-agent). |
| `onInteraction`, `onShortcut`, `onSlashCommand` | Handle your own buttons, shortcuts, and slash commands.                                                                             |
| `onEvent`                                       | Handles other [Events API callbacks](#other-events-api-callbacks).                                                                  |
| `threadContext`                                 | Adds [earlier thread replies](#load-prior-thread-messages). Omit to skip them.                                                      |
| `turnPolicy`                                    | `"steer"` (default) or `"queue"`. See [Control overlapping turns](#control-overlapping-turns).                                      |
| `approvalChannel`                               | Posts each request in the thread (default) or a DM. See [HITL](#human-in-the-loop-hitl).                                            |
| `renderers`                                     | Change what the agent posts. See [Customize rendering](#customize-rendering).                                                       |
| `api`                                           | Use [another Slack API host](#point-the-channel-at-a-different-slack-api-host) or a custom `fetch`.                                 |
| `codeChannels`                                  | Serve each [Slack code channel](#serve-slack-code-channels) as one session that answers without a mention.                          |

## Advanced use

### Serve Slack code channels

A [Slack code channel](https://docs.slack.dev/ai/slack-code) is a channel for one agent task. Set `codeChannels` to serve each code channel as one session that answers without a mention:

```ts title="agent/channels/slack.ts"
import { connectSlackCredentials } from "@vercel/connect/eve";
import { slackChannel } from "eve/channels/slack";

export default slackChannel({
  credentials: connectSlackCredentials("slack/my-agent"),
  codeChannels: true,
});
```

- Every message in the channel, top-level or in a thread, reaches the same session. Replies post top-level, or in the thread when someone writes in one.
- eve shows the Slack session status instead of the thread status line. It's `processing` while a turn runs, `suspended` while the turn waits on a person, and `active` once it ends or is cancelled.
- When someone stops the session in Slack, eve cancels the running turn, or sets the status back to `active` when no turn is running.
- Every member can start turns, with auth from each message's author, as in an ordinary thread.

Messages that don't mention the bot go to `onMessage` when you define it, else to `onAppMention`, else the default handler. So a mention handler that filters who reaches the agent also filters code channel messages. `ctx.isBotMentioned()` still returns `true` only for real mentions; check `ctx.slack.codeChannel` to tell code channel messages apart. Without `codeChannels`, eve treats a code channel like any other channel.

A code channel session has no single thread. `ctx.slack.threadTs` is empty, `SlackChannelState.threadTs` is `null`, and its Slack auth has no `thread_ts`. Instead, `ctx.slack.codeChannel`, `codeChannel: true` in state, and `codeChannel: true` in `ctx.channel.metadata` mark it. In [renderers](#customize-rendering), check `channel.state.codeChannel`. To address its session yourself, target `{ channelId, codeChannel: true }` in `onEvent` operations, or build its continuation token with `slackCodeChannelContinuationToken(channelId)`.

A code channel opened from Slack's UI starts without the original conversation. Slack posts a quote of the origin message into the channel; eve skips it, so it starts no turn and isn't added to the session. To start a code channel with the conversation so far, open it with [`openCodeChannel()`](#open-a-code-channel-from-a-thread), which copies the conversation, or with [`ctx.openCodeChannel()`](#open-a-code-channel-from-a-message-hook) and pass `history`.

eve recognizes a code channel with Slack's `conversations.info` API, so the app needs `channels:read`, plus `groups:read` for private code channels. If the lookup fails, eve logs an error, serves the channel per thread, and tries again a minute later.

With `codeChannels` set, the generated app manifest enables code channels and subscribes to the `message.session` and `agent_session_stopped` events. It adds the `code_channels:manage`, `channels:history`, `channels:read`, `groups:history`, and `groups:read` bot scopes, plus `im:read` and `mpim:read` so eve can read a DM or group DM origin. For Vercel Connect, add the same scopes and events under **Advanced** when you create the connector.

#### Open a code channel from a thread

To let the agent move multi-message work into a new code channel, give it a tool that calls `openCodeChannel()` with your Slack channel:

```ts title="agent/tools/open_code_channel.ts"
import { openCodeChannel } from "eve/channels/slack";
import { defineTool } from "eve/tools";
import { z } from "zod";
import slack from "../channels/slack";

export default defineTool({
  description: [
    "Move this Slack conversation into a new code channel for multi-step work: code changes, builds, tests, pull requests, investigations, or long output.",
    "Answer in place when one message answers the request. Call it once per request; Slack links the new channel here, so afterward reply in one short sentence at most.",
    "If it returns unavailable or Slack refuses, continue here and say why; don't retry.",
  ].join(" "),
  inputSchema: z.object({
    message: z
      .string()
      .describe("The task and where to start. The channel sees the conversation so far."),
    name: z.string().max(80).describe("A short title, such as `Fix the flaky login test`."),
  }),
  async execute({ message, name }, ctx) {
    return await openCodeChannel(ctx, slack, message, { name });
  },
});
```

`openCodeChannel(ctx, slack, message, { name })` opens a code channel from the message that started the turn. The new session starts with the conversation the model saw, then `message`. Omit `name` to let Slack name the channel from the message. The origin thread keeps its own session for quick follow-ups.

- Slack links the new channel in the origin thread, invites the origin message's author, and gives the channel the origin's privacy.
- eve asks for a private channel when the origin is private. If Slack still returns a public channel, eve archives it and doesn't copy the conversation.
- It needs `codeChannels: true` on the Slack channel you pass. Outside Slack, or inside a code channel, it returns `{ status: "unavailable", reason }` and the model continues in the thread.
- When Slack refuses, it throws Slack's error for the model to relay. Examples are a Slack Connect conversation, disabled code channels, or a missing scope. eve first retries temporary errors such as rate limits.
- Like every [`ctx.to()`](/docs/tools#start-channel-sessions-ctxto), it works only in a tool on the root agent.

One person gets one code channel per message. A retried tool call reaches the same channel and session once. A second call for the same message reaches the same channel and sends the conversation again. So a session someone started by writing in the new channel first still gets the thread's history.

#### Build your own code channel tool

To change more than the description and inputs, send to the Slack channel with a `codeChannel` target yourself. `ctx.channel.metadata` holds the `channelId` and `threadTs` of the conversation that called the tool; in a code channel, `threadTs` is `null`. The metadata doesn't depend on the session's auth, so the tool works even when a message hook returns its own `auth`:

```ts title="agent/tools/move_to_code_channel.ts"
import { defineTool } from "eve/tools";
import { z } from "zod";
import slack from "../channels/slack";

export default defineTool({
  description: "Move this request into a new Slack code channel.",
  inputSchema: z.object({ task: z.string() }),
  async execute({ task }, ctx) {
    const channelId = ctx.channel.metadata?.channelId;
    const threadTs = ctx.channel.metadata?.threadTs;
    if (typeof channelId !== "string" || typeof threadTs !== "string") {
      return { status: "unavailable" };
    }
    const session = await ctx
      .to(slack, {
        channelId,
        // Opens the channel from the thread's root message.
        codeChannel: { name: task.slice(0, 80), originThreadTs: threadTs, originTs: threadTs },
      })
      .send(task, {
        auth: ctx.session.auth.current,
        idempotencyKey: `${ctx.session.id}:${ctx.callId}`,
      });
    return { sessionId: session.id, status: "opened" };
  },
});
```

`codeChannel` takes the origin message's `originTs`, its thread's `originThreadTs`, and an optional `name`; omit `name` to let Slack name the channel from the message. The new channel gets the origin's privacy, and its session's audience follows it. A tool, route, schedule, or `onEvent` handler can open one from any message the app can see. Pass the origin of the conversation that called the tool, as `openCodeChannel()` does. Pass `history` to start the session with earlier messages; `openCodeChannel()` passes the text of `ctx.messages`.

#### Open a code channel from a message hook

To open a code channel without the model deciding, call `ctx.openCodeChannel({ name })` in `onAppMention`, `onDirectMessage`, or `onMessage`. It opens the channel from the incoming message and returns the same session operations as `ctx`, bound to the code channel's session. Send the first turn there and return `null`, so the thread gets no turn. This agent works only in code channels:

```ts title="agent/channels/slack.ts"
import { connectSlackCredentials } from "@vercel/connect/eve";
import { defaultSlackAuth, slackChannel } from "eve/channels/slack";

export default slackChannel({
  credentials: connectSlackCredentials("slack/my-agent"),
  codeChannels: true,
  async onAppMention(ctx, message) {
    // Messages in the code channel reach its session as usual.
    if (ctx.slack.codeChannel) return { auth: defaultSlackAuth(message, ctx) };
    const codeChannel = await ctx.openCodeChannel({ name: message.text.slice(0, 80) });
    await codeChannel.send(message.text);
    return null;
  },
});
```

The returned `send` uses the message author's auth by default, and moves Slack auth you pass to the code channel. Omit `name` to let Slack name the channel.

Unlike the tool, `ctx.openCodeChannel()` copies no conversation, so the session starts with only what you send. Pass `history` to `send` to include earlier messages, such as the thread's replies. It opens the channel the same way as a `codeChannel` target: one channel per author and message, with the origin's privacy and audience. It throws without `codeChannels: true`, for a message already in a code channel, and when Slack refuses to create the channel.

### Other Events API callbacks

`onEvent(ctx, event)` receives raw Slack events that no message hook handles, such as `reaction_added`, `team_join`, or `channel_created`. Call `ctx.send(message, { target, auth, ...options })` any number of times to start turns. It takes the same options as [`to().send()`](./custom#cross-channel-hand-off):

- `title` sets the run title without changing the message.
- `history` adds prior conversation; see [Start from prior history](./eve#start-from-prior-history).
- `idempotencyKey` makes a retried send reach the same session once.
- Each call returns a receipt with the `sessionId`.

```ts title="agent/channels/slack.ts"
import { connectSlackCredentials } from "@vercel/connect/eve";
import { slackChannel } from "eve/channels/slack";

const onboardingChannels = ["C0123ABC", "C0456DEF"];

export default slackChannel({
  credentials: connectSlackCredentials("slack/my-agent"),
  async onEvent(ctx, event) {
    if (event.type !== "team_join") return;

    await Promise.all(
      onboardingChannels.map((channelId) =>
        ctx.send(
          `A user joined the Slack workspace. Onboard them from this event:\n${JSON.stringify(event)}`,
          {
            target: { channelId },
            auth: null,
          },
        ),
      ),
    );
  },
});
```

The webhook request stays open while an awaited handler runs; use `ctx.waitUntil(promise)` for work that runs after it. `ctx.slack.request(operation, body)` calls the Slack Web API, and `ctx.envelope` carries `team_id`, `event_id`, and `event_time`.

An event isn't tied to one thread, so pass the target to each operation:

```ts
const target = { channelId, threadTs };

await ctx.send("Follow up", { auth: null, target });
await ctx.respond(answers, { auth: null, target });
await ctx.cancel({ target, turnId });
await ctx.compact({ target });
await ctx.clear({ target });
await ctx.end({ reason: "Start over", target });
const session = await ctx.resolveSession({ target });
```

A [code channel](#serve-slack-code-channels)'s session spans all its threads. Target it with `{ channelId, codeChannel: true }` in every operation except `send`.

`onEvent` receives JSON `event_callback` requests only, not URL verification, slash commands, or interactive payloads. Add each event and its OAuth scope to the Slack app's Event Subscriptions.

### Cards

Build typed message layouts with the card builders from `eve/channels/slack`, or pass raw Slack blocks as `{ blocks, text }`. Cards are plain data, not JSX components.

| Builders                                | Use                                          |
| --------------------------------------- | -------------------------------------------- |
| `Card`, `CardText`, `CardLink`          | Build a card with text and links.            |
| `Section`, `Divider`, `Image`           | Group content, separate it, or add an image. |
| `Fields`, `Field`, `Table`              | Display labeled values or tabular data.      |
| `Actions`, `Button`, `LinkButton`       | Group action buttons and links.              |
| `Select`, `SelectOption`, `RadioSelect` | Add fixed-choice controls inside `Actions`.  |

For example, post a review link from a message hook:

```ts title="agent/channels/slack.ts"
import { Actions, Card, CardText, LinkButton, slackChannel } from "eve/channels/slack";

export default slackChannel({
  async onAppMention(ctx) {
    await ctx.thread.post({
      card: Card({
        title: "Review ready",
        children: [
          CardText("Alice's draft is ready for review."),
          Actions([LinkButton({ label: "Open draft", url: "https://example.com/draft" })]),
        ],
      }),
      fallbackText: "Alice's draft is ready for review.",
    });
    return null;
  },
});
```

- Handle your own button and select callbacks in `onInteraction`. For eve's approval and question controls, use the [HITL helpers](#render-and-decode-hitl-controls-yourself).
- `thread.post({ card })` converts the card with `cardToBlocks(card)`, and with `cardToFallbackText(card)` unless you pass `fallbackText`.
- Message cards don't support modals, text inputs, or external selects. For a custom modal, send native Slack view data with `ctx.slack.request("views.open", ...)`.

### Proactive sessions

Start a Slack conversation from a [webhook on another channel](./custom#cross-channel-hand-off), a [schedule](../schedules#handler-form-run), or a [tool](../tools#start-channel-sessions-ctxto). To copy a conversation into a new thread or someone's DMs, see [Fork conversations into a new thread](../patterns/fork-conversations-into-new-threads). Pass `{ channelId }` as the target to start a new thread whose first message is the agent's first post. Optional target fields:

| Field                | Use                                                                                                                                                            |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `threadTs`           | Continue an existing thread.                                                                                                                                   |
| `initialMessage`     | Post a thread root before the agent runs: `{ markdown }`, `{ text }`, `{ blocks, text? }`, or `{ card, fallbackText? }`. Not with `threadTs` or `codeChannel`. |
| `installationTeamId` | Select the app installation workspace for a function-form bot token.                                                                                           |
| `codeChannel`        | Open a [code channel](#build-your-own-code-channel-tool) from a message in `channelId` and start the session there. Needs `codeChannels: true`.                |
| `audience`           | Set the destination's visibility. Defaults to `unknown`.                                                                                                       |

A send with an `idempotencyKey` and no `threadTs` or `initialMessage` picks the new thread's session from the key. A retry with the same key then reaches the same session instead of starting a second thread. Two different sends that reuse a key land in the same thread, and the second is ignored. Use a key that identifies the message across every sender to this channel, not only across retries of one sender.

`initialMessage` takes the same inputs as `thread.post`, including cards and optional files. eve posts the root message, then uploads files into its thread. A retried proactive send repeats the root post and its uploads, so don't use it as an exactly-once notification. For example, start a thread with a Markdown root:

```ts title="agent/channels/slack.ts"
import { slackChannel } from "eve/channels/slack";

export default slackChannel({
  async onEvent(ctx, event) {
    if (event.type !== "team_join") return;
    await ctx.send("Prepare a welcome message for the new teammate.", {
      auth: null,
      target: {
        channelId: "C0123ABC",
        initialMessage: { markdown: "A new teammate joined. Preparing their welcome." },
      },
    });
  },
});
```

The agent's replies appear under the root. Teammates continue the session by mentioning the app in the thread. To accept replies without a mention, [configure `onMessage` and its subscriptions](#continue-conversations-without-repeated-mentions).

To post without an agent turn, use `ctx.thread.post(...)` in an inbound handler, `ctx.channel.thread.post(...)` in a renderer, or [`callSlackApi(...)`](#slack-api-calls-outside-a-handler) elsewhere.

### Slack API calls outside a handler

Inbound handlers call the Slack Web API with `ctx.slack.request(operation, body)`, and a [renderer](#customize-rendering)'s event handlers use `ctx.channel.slack.request(...)`. Elsewhere, such as in a schedule, call `callSlackApi`:

```ts
import { callSlackApi } from "eve/channels/slack";
import { connectSlackCredentials } from "@vercel/connect/eve";

const { botToken } = connectSlackCredentials("slack/my-agent");
const response = await callSlackApi({
  api: { apiBaseUrl: process.env.SLACK_API_BASE_URL },
  botToken,
  context: { teamId: "T0123456789" },
  operation: "reactions.get",
  body: { channel: "C0123456789", timestamp: "1712345678.000100", full: true },
});
if (!response.ok) throw new Error(String(response.error));
```

- `callSlackApi` passes `context` to a function-form token.
- It form-encodes the body, because some methods, such as `conversations.replies`, reject JSON.
- It takes the same [`api`](#point-the-channel-at-a-different-slack-api-host) option as the channel. An `undefined` base keeps Slack's own hosts.
- `resolveSlackBotToken` returns the bearer token as a string.

### Point the channel at a different Slack API host

```ts
slackChannel({
  api: {
    apiBaseUrl: "https://slack-simulator.example/api/slack",
    fetch: (input, init) => {
      const headers = new Headers(init?.headers);
      headers.set("x-vercel-protection-bypass", process.env.SLACK_SIMULATOR_BYPASS_SECRET ?? "");
      return fetch(input, { ...init, headers });
    },
    fileBaseUrl: "https://slack-simulator.example/files",
  },
  credentials: { botToken: process.env.SLACK_BOT_TOKEN },
});
```

| Field         | Default                  | What it does                                                                                                           |
| ------------- | ------------------------ | ---------------------------------------------------------------------------------------------------------------------- |
| `apiBaseUrl`  | `https://slack.com/api/` | The base that Web API method names resolve against.                                                                    |
| `fileBaseUrl` | `apiBaseUrl`             | A host whose file downloads get the bot token, alongside `files.slack.com` and Enterprise Grid file URLs.              |
| `fetch`       | Global `fetch`           | Carries requests to the configured bases' origins only. With no base set, it carries all Slack traffic, as for a test. |

Other public `https:` file URLs download without the token. Both bases must be absolute `http:` or `https:` URLs without a query string or fragment, or `slackChannel()` throws. A missing trailing slash is added. A header that `api.fetch` adds, such as the simulator's bypass secret above, never reaches `files.slack.com` or other hosts Slack names.

### Customize rendering

Pass `renderers` to change what the agent posts. Each renderer wraps the ones after it, ending with eve's default renderer. A renderer has four optional parts:

- `received(message, channel, next)` acknowledges a mention or DM when it arrives, and another message once `onMessage` accepts it. eve's default sets `Thinking...`.
- `events` handles session events such as `content.completed` or `interaction.opened`. Each handler receives `(event, ctx, next)`. The event has `type`, `data`, and `scope` (the turn or call it belongs to). The context has `ctx.channel.thread`, `ctx.channel.slack`, `ctx.position`, and `ctx.view`.
- `taskCard(view, next)` returns the task card's blocks and notification text, or `null` for no card.
- `interactionCard(card, next)` returns the messages for one approval, question, or budget prompt.

Call `next()` to run the rest of the chain, before or after your own work. You can also pass it a changed event, as in `next({ ...event, data: { ...event.data, value } })`. The rest of the chain runs at most once. Skip `next` to replace the default. This renderer adds feedback buttons below each final reply and a note to the finished task card:

```ts title="agent/channels/slack.ts"
import { connectSlackCredentials } from "@vercel/connect/eve";
import { defineSlackRenderer, slackChannel } from "eve/channels/slack";

const feedback = defineSlackRenderer({
  events: {
    async "content.completed"(event, ctx, next) {
      await next(); // eve posts the reply, or uploads a long one as a snippet
      if (event.data.phase !== "reply" || event.data.kind !== "text") return;
      await ctx.channel.thread.post({
        blocks: [
          {
            type: "context_actions",
            elements: [
              {
                type: "feedback_buttons",
                action_id: "reply_feedback",
                positive_button: { text: { type: "plain_text", text: "Helpful" }, value: "up" },
                negative_button: {
                  text: { type: "plain_text", text: "Not helpful" },
                  value: "down",
                },
              },
            ],
          },
        ],
        text: "Was this helpful?",
      });
    },
  },
  taskCard(view, next) {
    const card = next(view);
    if (card === null || view.state !== "finished") return card;
    const note = {
      type: "context",
      elements: [{ type: "mrkdwn", text: "Results are in the reply below." }],
    };
    return { ...card, blocks: [...card.blocks, note] };
  },
});

export default slackChannel({
  credentials: connectSlackCredentials("slack/my-agent"),
  renderers: [feedback],
});
```

`onInteraction` receives clicks on buttons a renderer posts, such as the feedback buttons above.

A `content.completed` handler that posts the reply itself, instead of calling `next()`, is responsible for that reply. If it throws, eve logs the error, posts the [delivery notice](#delivery), and tells the model, but doesn't re-send your reply. If you post a follow-up after the reply, as the example above does, catch the follow-up's errors. Otherwise eve posts the notice even though the reply arrived.

To keep eve's fallbacks for a reply you render, post it with `postCompletedSlackReply`. eve tries, in order:

1. Your `blocks`, when given, with `text` as the notification text. `text` defaults to `markdown`.
2. Your `markdown` as one native Markdown message, when it fits in 12,000 characters. eve tries it when you gave no blocks or Slack refused them as too large or malformed.
3. Your `markdown` as the `eve-response.md` snippet, when it's longer or Slack refuses the Markdown message.

Other errors, including a failed upload, go to your handler; if your handler doesn't catch them, eve posts the notice. Slack caps the combined text of all `markdown` blocks in one message at 12,000 characters. A reply that fits in `markdown_text` can still be refused as blocks.

```ts title="agent/channels/slack.ts"
import { defineSlackRenderer, postCompletedSlackReply, slackChannel } from "eve/channels/slack";

const sourcedReplies = defineSlackRenderer({
  events: {
    async "content.completed"(event, ctx, next) {
      const { kind, phase, value } = event.data;
      if (phase !== "reply" || kind !== "text" || typeof value !== "string") return next();
      await postCompletedSlackReply(ctx.channel, {
        blocks: [
          { type: "markdown", text: value },
          { type: "context", elements: [{ type: "mrkdwn", text: "Sources: internal docs" }] },
        ],
        markdown: value,
      });
    },
  },
});

export default slackChannel({ renderers: [sourcedReplies] });
```

Pass a string, as in `postCompletedSlackReply(ctx.channel, reply)`, to post Markdown alone, as eve's default does.

`taskCard` runs for every turn that calls a tool, including a turn without tasks. It receives:

- `calls`: the turn's tool calls on this card as `CallObservation` values that you can't change, in call order. A call that started a task has a `taskId`. eve leaves out its own task controls and calls a tool makes for the model.
- `view`: a snapshot of the session. Read it with the selectors from `eve/events`:
  - `callState(view, callId)` returns `running`, `blocked`, `completed`, `cancelled`, and other states.
  - `callLabel(row)` returns the row title.
  - `openInteractions(view, { about: { callId } })` returns the open approvals, questions, and sign-ins holding a call up.
- `state`: `blocked` while any task waits on an approval, question, or sign-in, `working` while the turn or any task works, then `finished`.
- `audience`: who reads the card. eve's default shows errors and request prompts only when it's `private`; do the same with what you show from `calls`.

`taskCard` must be synchronous and have no side effects; eve posts and updates the card. eve's default returns `null` for a card without tasks. Its block keeps one `block_id` for the whole turn, so keep that `block_id` on a block you build in its place. To change a row's title in every channel, give the tool a [label](/docs/tools#label-tool-activity) instead.

A renderer's `interaction.opened` handler can add to how a request appears, then call `next()` for eve's controls. This one posts non-sensitive context in the thread first, while `approvalChannel` still sends sensitive reviews to a DM:

```ts title="agent/channels/slack.ts"
import { slackChannel } from "eve/channels/slack";
import { isPrivate } from "../lib/review-policy";

export default slackChannel({
  approvalChannel(request) {
    return isPrivate(request) ? "direct-message" : "thread";
  },
  renderers: [
    {
      events: {
        async "interaction.opened"(event, ctx, next) {
          if (event.data.request.kind === "sign-in" || !("thread" in ctx.channel)) return next();
          await ctx.channel.thread.post({
            blocks: [
              {
                type: "context",
                elements: [
                  {
                    type: "mrkdwn",
                    text: "A review is needed before this work can continue.",
                  },
                ],
              },
            ],
            text: "A review is needed before this work can continue.",
          });
          await next();
        },
      },
    },
  ],
});
```

#### Restyle approval and question cards

`interactionCard(card, next)` restyles the card for one approval, question, or budget prompt. It doesn't run for sign-ins. `card` holds:

| Field         | What it is                                                                                                                                                                                                                  |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `interaction` | The request, with its `status`, `outcome`, `call` (including the tool `input`), and `answer`. While the request is open, `answer` is the latest accepted answer, if any. Once it ends, `answer` is the one that decided it. |
| `destination` | `"thread"` or `"direct-message"`, as [`approvalChannel`](#human-in-the-loop-hitl) decided. In a code channel, `"thread"` is the code channel itself.                                                                        |
| `audience`    | Who reads the message. A direct message is always `private`; a thread request has the thread's audience.                                                                                                                    |
| `answeredBy`  | The Slack user ID whose answer stands or decided the request, when known.                                                                                                                                                   |
| `view`        | The session snapshot, for the selectors from `eve/events`.                                                                                                                                                                  |

It returns `controls`, the message with eve's buttons or select, and an optional `details` message that eve posts before the controls. Each is a `SlackCardMessage` with `blocks` and `text`, the shape `taskCard` returns. Slack sends the whole controls message back with every click, so put long content, such as tool input, in `details`. Requests asked together share one details message, which eve deletes once its last open request ends. This renderer shows a `plan-create` tool's steps as the approval's details:

```ts title="agent/channels/slack.ts"
import { defineSlackRenderer, slackChannel } from "eve/channels/slack";

const plan = defineSlackRenderer({
  interactionCard(card, next) {
    const parts = next(card);
    const { call, status } = card.interaction;
    if (call?.name !== "plan-create" || status !== "open") return parts;
    const { steps = [] } = (call.input ?? {}) as { steps?: string[] };
    if (steps.length === 0) return parts;
    const text = steps.map((step, index) => `${index + 1}. ${step}`).join("\n");
    return {
      ...parts,
      details: { blocks: [{ type: "section", text: { type: "mrkdwn", text } }], text },
    };
  },
});

export default slackChannel({ renderers: [plan] });
```

eve calls `interactionCard` when a request opens, when an answer is accepted or refused, and when the request ends. It updates the Slack message only when its blocks changed. Pass `next` a changed card, such as one with a shorter `interaction.request.prompt`, to have eve's default render it.

eve still routes, groups, and posts the messages, and owns the controls' action IDs, so clicks keep reaching the session. You can relabel, reorder, or nest eve's controls within these rules:

- While the request is open and unanswered, `controls` holds exactly the controls `next` renders, each once, with the same values. Every eve control's `action_id` starts with `eve_input:` or `eve_input_freeform:`.
- Once the request is answered or ended, `controls` holds no eve controls.
- `details` never holds eve controls.
- A message holds at most 50 blocks, including requests eve grouped with yours. An update over that limit uses eve's default for the changed request, then only the block with eve's controls, so an open request always shows them.

If `interactionCard` throws or breaks these rules, eve logs it and renders that request with its default, because a request nobody can answer would hold the turn. If Slack refuses a message's content, such as with `invalid_blocks` or `msg_too_long`, eve sends it once more with its defaults. eve doesn't resend after other failures, such as a timeout or `rate_limited`, because the first message may have posted.

### Show your own tool on the task card

A renderer can draw any of the turn's tool calls from their input. This `plan` tool records a checklist, and the renderer shows it ahead of eve's task rows:

```ts title="agent/tools/plan.ts"
import { defineTool } from "eve/tools";
import { z } from "zod";

export default defineTool({
  description:
    "Show the steps of a multi-step request as a checklist. Pass the complete list on every call.",
  inputSchema: z.object({
    items: z.array(
      z.object({
        status: z.enum(["pending", "working", "completed", "failed"]),
        title: z.string(),
      }),
    ),
  }),
  async execute() {
    return { updated: true };
  },
});
```

```ts title="agent/channels/slack.ts"
import { type BlockKitBlock, defineSlackRenderer, slackChannel } from "eve/channels/slack";

interface PlanItem {
  readonly status: "pending" | "working" | "completed" | "failed";
  readonly title: string;
}

const SLACK_STATUS = {
  completed: "complete",
  failed: "error",
  pending: "pending",
  working: "in_progress",
} as const;

const plan = defineSlackRenderer({
  taskCard(card, next) {
    const rendered = next(card);
    const calls = card.calls.filter((call) => call.capability.name === "plan");
    const input = calls.at(-1)?.input as { items?: PlanItem[] } | undefined;
    const items = input?.items;
    if (items === undefined) return rendered;
    // eve's card is one `plan` block, or one `task_card` block for a single task.
    const [block] = rendered?.blocks ?? [];
    const taskRows: BlockKitBlock[] =
      block === undefined ? [] : block.type === "plan" ? (block.tasks as BlockKitBlock[]) : [block];
    const planRows = items.map((item, index) => ({
      status: SLACK_STATUS[item.status],
      task_id: `plan_${index}`,
      title: item.title,
    }));
    const tasks = [...planRows, ...taskRows.map(({ type: _type, ...row }) => row)];
    return {
      blocks: [{ type: "plan", block_id: block?.block_id, title: "Plan", tasks }],
      text: `Plan: ${items.map((item) => item.title).join(", ")}`,
    };
  },
});

export default slackChannel({ renderers: [plan] });
```

### Render and decode HITL controls yourself

`renderInteractionBlocks(request, route?)` returns eve's Block Kit blocks for one request (`Interaction`). `answerFromSlackAction(action)` decodes a click on them into `{ response, kind?, route? }`, where `response` is the eve `Answer`. It returns `null` for any other action. Every eve control's `action_id` starts with `ANSWER_ACTION_PREFIX` (`"eve_input:"`), so give your own buttons a different prefix to route them to `onInteraction`.

```ts
import { answerFromSlackAction, renderInteractionBlocks } from "eve/channels/slack";

const [card] = renderInteractionBlocks(request) as [
  { actions: { action_id: string; value: string }[] },
];
const button = card.actions[0]!;

// For a request whose first option id is "approve":
answerFromSlackAction({ actionId: button.action_id, value: button.value });
// { response: { optionId: "approve", interactionId: request.interactionId } }
```

Use them to test a custom renderer against eve's Slack payloads, or to post eve's controls from your own renderer. To restyle the cards eve posts, use [`interactionCard`](#restyle-approval-and-question-cards) instead, which keeps eve's batching and card updates.

- A click on these controls in the session's thread resumes the session through `onAnswers`.
- eve doesn't track controls you post, so update or remove them in your renderer's `interaction.settled` handler.
- To pass `response` to `respond()` yourself, validate it with `parseAnswers` from `eve/client`.

For a sign-in, a renderer's handler gets a private-only `ctx.channel` with `postEphemeral`, `postDirectMessage`, and `state`. It gets no public `post` or raw API access. `postDirectMessage` needs the `im:write` scope.

`audience.principalIds` lists the eve identities (`principalId` values) of the people the sign-in is for. `state.slackUsersByPrincipal` maps each identity seen in the thread to its Slack user ID. An identity without an entry gets no private sign-in. Skip `next()` to deliver the sign-in yourself:

```ts
renderers: [
  {
    events: {
      "interaction.opened"(event, ctx, next) {
        const { audience, request } = event.data;
        if (request.kind !== "sign-in") return next();
        const principalId = audience?.principalIds[0];
        const userId =
          principalId === undefined ? undefined : ctx.channel.state.slackUsersByPrincipal?.[principalId];
        if (!userId || !request.signIn?.url) return;
        return ctx.channel.postDirectMessage(userId, `Sign in to continue: ${request.signIn.url}`);
      },
    },
  },
],
```

## Test a preview branch

Create a second connector for preview traffic and route it to your preview branch:

```bash
vercel connect create slack --name my-agent-preview --triggers
vercel connect attach slack/my-agent-preview \
  --environment preview \
  --triggers \
  --trigger-branch your-preview-branch \
  --trigger-path /eve/v1/slack \
  --yes
```

Then select the connector at runtime:

```ts title="agent/channels/slack.ts"
import { connectSlackCredentials } from "@vercel/connect/eve";
import { slackChannel } from "eve/channels/slack";

const connectorUid =
  process.env.VERCEL_ENV === "preview" ? "slack/my-agent-preview" : "slack/my-agent";

export default slackChannel({
  credentials: connectSlackCredentials(connectorUid),
});
```

In the [Connect dashboard](https://vercel.com/d?to=/%5Bteam%5D/~/connect&title=Go+to+Connect):

- Remove the production destination that `connect create --triggers` adds, so preview traffic stays separate.
- Set the production connector's project access to **Production** and the preview connector's to **Preview**, because guided setup doesn't restrict credential environments.

A connector can have at most three trigger destinations.

Slack must reach the preview route without an authentication challenge. For a Connect trigger, exempt the branch domain with a [Deployment Protection Exception](https://vercel.com/docs/deployment-protection/methods-to-bypass-deployment-protection/deployment-protection-exceptions) or use an unprotected domain. For a self-managed Slack app, append `?x-vercel-protection-bypass=your-generated-secret` to its event and interaction Request URLs. Slack doesn't send the [automation bypass](https://vercel.com/docs/deployment-protection/methods-to-bypass-deployment-protection/protection-bypass-automation) header.

## Troubleshoot Slack delivery

| What you see                                            | What to do                                                                                                                              |
| ------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `eve add channel/slack` stops before finishing          | Fix the step the error names, then rerun `eve add channel/slack`.                                                                       |
| Setup says the Slack app isn't installed in a workspace | Rerun `eve add channel/slack`, then finish the install in the browser page it opens while setup waits.                                  |
| Setup says a connector is used by another project       | Let setup create a new Slack app, or remove the existing app from the other project in the Connect dashboard first.                     |
| Setup says the connector has too many destinations      | Remove an unused destination in the Connect dashboard, then rerun setup.                                                                |
| Mentions never reach the deployment                     | Rerun `eve add channel/slack` to repair the production destination, and check branch destinations in the Connect dashboard.             |
| A preview request receives an authentication page       | Exempt the branch domain from Deployment Protection, or add the bypass secret to a self-managed app's Request URLs.                     |
| Mentions work but DMs or thread replies don't           | Add `message.im` and `im:history` for DMs, or the matching message event and history scope for channel replies, then reinstall the app. |
| A long response can't be uploaded as a snippet          | Add the `files:write` bot scope and reinstall the app.                                                                                  |
| The thread says the agent couldn't deliver its answer   | Search the Vercel runtime logs for the notice's error id on the `final reply was not delivered to Slack` line.                          |
| The webhook arrives but the agent doesn't reply         | Check the Vercel runtime logs, then the session in [**Agent Runs**](/docs/observability/agent-runs) when your team has access.          |
