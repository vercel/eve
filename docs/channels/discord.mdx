The Discord channel wires your agent into Discord's HTTP Interactions, including slash and application commands, message components, and modal submissions. Discord enforces a three-second ACK deadline, so the channel acknowledges the command right away and runs the eve work in the background. Credentials and inbound request verification run through [Vercel Connect](../guides/auth-and-route-protection), so Discord's bot token stays out of your environment and Connect verifies Discord's signature before forwarding an interaction to eve.

Ordinary DMs, mentions, replies, and thread messages do not reach Discord's HTTP Interactions endpoint. You can opt into experimental ordinary-message support by running a separate Discord Gateway relay. See [Channels](./overview) for the channel contract.

## Set up Discord

Run the guided setup from your eve project:

```bash
pnpm eve add channel/discord
```

The setup guides you through creating a Discord application and bot, then:

- signs you in to Vercel and creates or links a project when needed;
- validates the bot token;
- creates a Vercel Connect client and attaches `/eve/v1/discord` as its trigger destination;
- registers an application command with a required `message` option;
- configures the Discord application's Interactions Endpoint URL;
- scaffolds the channel with Connect-managed credentials; and
- prints the bot installation URL.

The command defaults to `/ask` with the description **Ask the eve agent**. You can edit both during setup. Discord global commands can take up to an hour to appear after registration.

The generated channel looks like this:

```ts title="agent/channels/discord.ts"
import { connectDiscordCredentials } from "@vercel/connect/eve";
import { discordChannel } from "eve/channels/discord";

export default discordChannel({
  credentials: connectDiscordCredentials("discord/my-agent"),
});
```

The route is `POST /eve/v1/discord` by default. Connect resolves the application ID and bot token lazily and verifies forwarded interactions with same-project Vercel OIDC.

### Configure Discord manually

If you do not use the guided Connect setup, register a command with Discord's API or the Developer Portal. A string option named `message` lines up with eve's default prompt extraction:

```bash
curl -X PUT "https://discord.com/api/v10/applications/$DISCORD_APPLICATION_ID/commands" \
  -H "Authorization: Bot $DISCORD_BOT_TOKEN" -H "Content-Type: application/json" \
  -d '[{"name":"ask","description":"Ask the eve agent","type":1,
    "options":[{"name":"message","description":"What should the agent do?","type":3,"required":true}]}]'
```

Then configure the public `https://…/eve/v1/discord` route as the application's Interactions Endpoint URL. Pass `credentials: { applicationId, botToken, publicKey }` to `discordChannel`, or set the corresponding `DISCORD_APPLICATION_ID`, `DISCORD_BOT_TOKEN`, and `DISCORD_PUBLIC_KEY` environment variables.

## Receive ordinary bot messages (experimental)

Discord sends ordinary bot messages as `MESSAGE_CREATE` events over its persistent [Gateway WebSocket](https://docs.discord.com/developers/events/gateway), not to the HTTP Interactions endpoint. `discordChannel()` does not open that socket: an eve application can be evaluated during builds and run on several instances, while a Gateway client needs one long-lived owner that maintains heartbeats, Resume state, and reconnects.

Run a separate relay that owns the outbound WebSocket and forwards authenticated events to eve:

```text
Discord Gateway WebSocket
          |
          v
separately deployed relay
          |
          | signed HTTP MESSAGE_CREATE envelope
          v
POST /eve/v1/discord/gateway
          |
          v
discordChannel() -> durable eve session -> Discord REST reply
```

Gateway support is experimental. The relay lifecycle, deployment, retry behavior, and duplicate suppression remain your responsibility. A persistent process is the most direct deployment. A relay built from bounded Vercel Functions or Workflow steps must deliberately close and Resume its socket before the function duration limit, and cannot provide permanent-daemon or strict singleton guarantees.

### Opt into Gateway ingestion

Add `gateway` to the same channel that handles Discord interactions:

```ts title="agent/channels/discord.ts"
import { connectDiscordCredentials } from "@vercel/connect/eve";
import { discordChannel } from "eve/channels/discord";

export default discordChannel({
  credentials: connectDiscordCredentials("discord/my-agent"),
  gateway: {
    connectorId: "discord/my-agent",
    secret: () => process.env.RELAY_FORWARD_SECRET!,
  },
});
```

This mounts `POST /eve/v1/discord/gateway` in addition to the interaction route. `connectorId` is a stable namespace and must match the relay's connector identity. Guided Connect setups should use the Connect connector UID; with manual credentials, choose an ID and keep it stable. Changing it starts a new conversation namespace.

`secret` is required and must resolve to the same independent secret used by the relay to sign requests. Do not use the Discord bot token as the relay secret. Omitting `gateway` leaves the route unmounted and preserves the existing interaction-only routing behavior.

### Native bot behavior

With `gateway` enabled, the built-in policy behaves as follows:

- Every non-bot DM is accepted and resumes by DM channel ID.
- An explicit bot mention in an unthreaded guild channel starts a new session.
- A reply in an unthreaded guild channel continues only when its referenced message is the current eve response anchor.
- An unknown or old reply anchor returns `409 anchor_not_ready` instead of creating another session.
- Ambient guild messages and bot-authored messages are ignored.
- Slash commands in guild channels start new message-chain sessions; their first response becomes the current reply anchor.

Only the current bot response anchors an unthreaded guild conversation. Replying to an older response does not recover that session. Discord threads remain the preferred surface for a shared group conversation, but the default policy still requires an explicit mention or a reply that resolves to the active response.

Supplying `gateway.onMessage(ctx, message)` replaces the built-in acceptance policy. Return `{ auth }` to dispatch, optional `context` or `title` with it, or `null` to ignore the message. `DiscordMessage` is an eve-owned normalized shape with message, channel, guild/thread, author, mention, reply-reference, and attachment metadata plus `raw` for the original dispatch object.

### Run a Gateway relay

A relay needs the same Discord application's bot token. It may resolve that token from the Vercel Connect connector or use a directly configured bot token. Connect still owns and forwards HTTP interactions; the relay owns only ordinary Gateway events.

For one small bot, the relay must:

1. Open `wss://gateway.discord.gg/?v=10&encoding=json`.
2. Handle Hello (`op 10`), randomized initial heartbeat, heartbeat ACK (`op 11`), server-requested heartbeat (`op 1`), Reconnect (`op 7`), and Invalid Session (`op 9`).
3. Identify (`op 2`) with Guilds (`1`), Guild Messages (`512`), and Direct Messages (`4096`) intents. Add Message Content (`32768`) only after enabling that privileged intent in Discord's Developer Portal.
4. Record each dispatch sequence, and save the session ID and Resume Gateway URL from `READY`.
5. Resume (`op 6`) after a reconnect when the saved session is still valid; otherwise identify again.
6. Forward only `MESSAGE_CREATE` dispatches to eve using the contract below.
7. When `channel_id` is a Discord thread or forum-post channel, add `thread: { id: channel_id }` to the forwarded `data` object. Use the Gateway channel cache or `GET /channels/{channel.id}` to determine the channel type.
8. Keep one logical Gateway owner for the bot token and stop it on token rotation or deployment shutdown.

Larger bots also need Discord's sharding and Identify concurrency rules. The experimental eve contract does not manage either one.

### Forward events to eve

Forward the raw `MESSAGE_CREATE` dispatch object from the Gateway payload's `d` field in this JSON envelope:

```json
{
  "version": 1,
  "connectorId": "discord/my-agent",
  "deliveryId": "discord:discord/my-agent:message:1234567890",
  "event": "MESSAGE_CREATE",
  "sequence": 42,
  "sessionId": "gateway-session-id",
  "data": {}
}
```

| Field         | Contract                                                                                 |
| ------------- | ---------------------------------------------------------------------------------------- |
| `version`     | Must be `1`.                                                                              |
| `connectorId` | Must equal `gateway.connectorId` and the signed connector header.                         |
| `deliveryId`  | A non-empty relay delivery ID. Use the connector and Discord message ID for stability.    |
| `event`       | Must be `MESSAGE_CREATE`.                                                                 |
| `sequence`    | The Gateway dispatch sequence, or `null`.                                                 |
| `sessionId`   | Optional Discord Gateway session ID for diagnostics.                                      |
| `data`        | The `d` object from `MESSAGE_CREATE`, enriched with `thread.id` for a thread channel.      |

Serialize the envelope exactly once. Sign the exact UTF-8 request body with HMAC-SHA256 and send these headers:

```text
X-Eve-Discord-Timestamp: <Unix time in decimal seconds>
X-Eve-Discord-Connector: <gateway.connectorId>
X-Eve-Discord-Signature: v1=<64 lowercase hexadecimal characters>
Content-Type: application/json
```

The signature input has no trailing newline:

```text
v1\n<timestamp>\n<connector-id>\n<raw-request-body>
```

The following helper produces a request accepted by the default Gateway route:

```ts
import { createHmac } from "node:crypto";

async function forwardMessageCreate(input: {
  connectorId: string;
  eveUrl: string;
  gatewaySessionId?: string;
  relaySecret: string;
  sequence: number | null;
  data: { id: string } & Record<string, unknown>;
}) {
  const timestamp = String(Math.floor(Date.now() / 1000));
  const body = JSON.stringify({
    version: 1,
    connectorId: input.connectorId,
    deliveryId: `discord:${input.connectorId}:message:${input.data.id}`,
    event: "MESSAGE_CREATE",
    sequence: input.sequence,
    sessionId: input.gatewaySessionId,
    // Add { thread: { id: input.data.channel_id } } when this is a thread channel.
    data: input.data,
  });
  const signature = createHmac("sha256", input.relaySecret)
    .update(`v1\n${timestamp}\n${input.connectorId}\n${body}`, "utf8")
    .digest("hex");

  return fetch(new URL("/eve/v1/discord/gateway", input.eveUrl), {
    method: "POST",
    headers: {
      "content-type": "application/json",
      "x-eve-discord-connector": input.connectorId,
      "x-eve-discord-signature": `v1=${signature}`,
      "x-eve-discord-timestamp": timestamp,
    },
    body,
  });
}
```

The route rejects bodies over 1 MB. Timestamps are Unix seconds and must be within five minutes of eve's clock. eve verifies the signature before parsing JSON and requires the configured connector ID, signed header, and envelope field to match.

### Handle relay responses and duplicates

Use the response status to decide whether to retry:

| Status    | Meaning                                                                                   |
| --------- | ----------------------------------------------------------------------------------------- |
| `202`     | Accepted. Stop retrying.                                                                  |
| `200`     | Valid but ignored, stale, or unsupported by policy. Stop retrying.                        |
| `400–403` | Invalid envelope, signature, timestamp, connector, or configuration. Fix before retrying. |
| `409`     | `anchor_not_ready`. Retry briefly with bounded backoff, then treat the reply as stale.    |
| `413`     | Body exceeds 1 MB. Do not retry unchanged.                                                |
| `429`     | Rate limited. Retry with backoff.                                                         |
| `5xx`     | Delivery failed. Retry with bounded backoff.                                              |

Gateway delivery is at least once. Suppress common replays in the relay with a recent-message set keyed by connector and Discord message ID, and persist that set with Gateway checkpoints when your deployment allows it. The relay should record completion only after eve returns `202` or a terminal `200` response.

This is best-effort deduplication: if eve accepts a message but the relay crashes or loses the HTTP response before recording completion, forwarding it again can start another turn. eve does not durably claim `deliveryId` values today.

## How the channel handles messages

### Dispatch

`onCommand(ctx, interaction)` decides whether to dispatch and under what `auth`. Return `{ auth }` to proceed, `null` to drop the interaction, or `title` alongside `auth` to set the title when the dispatch starts a run. By default, auth comes from the invoking user.

The model-visible `<discord_context>` includes `user_id` and the receiving application's `application_id`.

Event handlers receive `(eventData, channel, ctx)`, with Discord platform handles on `channel.discord`:

```ts
import { discordChannel } from "eve/channels/discord";

export default discordChannel({
  onCommand: (ctx, interaction) => ({
    auth: {
      principalId: interaction.user.id,
      principalType: "user",
      authenticator: "discord",
      attributes: { channel_id: interaction.channelId, guild_id: interaction.guildId ?? "" },
    },
  }),
  events: {
    "message.completed"(eventData, channel, ctx) {
      if (eventData.finishReason === "tool-calls") return;
      if (eventData.message) channel.discord.post(eventData.message);
    },
  },
});
```

### Delivery

The default `message.completed` handler edits the deferred response for the first reply and sends followups after that. If the interaction token is rejected, it falls back to a bot-authenticated channel message. Long text is split to Discord's 2000-char limit, and generated messages default to `allowed_mentions: { parse: [] }`.

Typing fires on `turn.started` and `actions.requested`, but only when a bot token is present. In custom hooks, call `channel.discord.startTyping()` yourself.

### Human-in-the-loop (HITL)

HITL renders as Discord components. Confirmations and options become buttons, `display: "select"` becomes a string select, and freeform input becomes a button that opens a modal. When the user responds, the parked session (paused awaiting input) resumes.

### Proactive sessions

Start a session without an inbound interaction through `to(discord, target).send(message, { auth })` from a schedule `run` handler, or `ctx.to(discord, target).send(message, { auth })` from another channel. The proactive target shape is `{ channelId, conversationId?, initialMessage? }`. Either path needs a bot token, supplied by Connect or `DISCORD_BOT_TOKEN`.

### Attachments

Inbound file attachments are not supported on this channel today.
