Every eve agent has one sandbox rooted at `/workspace`. The built-in `bash`, `read_file`, and `write_file` tools use it. Without an authored sandbox file, eve selects the best available environment automatically.

## Use the sandbox

Authored tools and callbacks access the live sandbox with `ctx.getSandbox()`:

```ts title="agent/tools/run_analysis.ts"
import { defineTool } from "eve/tools";
import { z } from "zod";

export default defineTool({
  description: "Run a Python script.",
  inputSchema: z.object({ script: z.string() }),
  async execute({ script }, ctx) {
    const sandbox = await ctx.getSandbox();
    await sandbox.writeTextFile({ path: "analysis.py", content: script });
    const result = await sandbox.run({ command: "python analysis.py" });
    if (result.exitCode !== 0) throw new Error(result.stderr);
    return result.stdout;
  },
});
```

Relative paths resolve under `/workspace`. `run()` returns `{ exitCode, stdout, stderr }`; a nonzero exit code does not throw automatically. Use `spawn()` for a long-running process.

## Define an environment

A sandbox module exports an environment and returns a sandbox from `defineSandbox()`:

```ts title="agent/sandbox.ts"
import { DefaultSandbox, defineSandbox } from "eve/sandbox";

export const environment = DefaultSandbox.environment();
export default defineSandbox(() => environment.create());
```

`environment.create()` creates a persistent sandbox owned by the current eve session. The callback can configure the real sandbox before returning it:

```ts
import { defineSandbox } from "eve/sandbox";
import { VercelSandbox } from "eve/sandbox/vercel";

export const environment = VercelSandbox.environment();

export default defineSandbox(async ({ session }) => {
  const sandbox = await environment.create({ networkPolicy: "deny-all" });
  await sandbox.writeTextFile({ path: ".eve/session", content: session.id });
  return sandbox;
});
```

The environment export is required because `eve build` prepares its immutable template inputs before a session exists.

### Prepare a reusable environment

Set the environment's `prepare` option for setup that every new sandbox inherits:

```ts
import { defineSandbox } from "eve/sandbox";
import { VercelSandbox } from "eve/sandbox/vercel";

export const environment = VercelSandbox.environment({
  prepare: async (sandbox) => {
    const result = await sandbox.run({
      command: "sudo apt-get update && sudo apt-get install -y jq",
    });
    if (result.exitCode !== 0) throw new Error(result.stderr);
  },
});

export default defineSandbox(() => environment.create());
```

Vercel environments use the existing snapshot-backed template lifecycle. Docker and microsandbox use local image/template storage.

### Share a named sandbox

`getOrCreate()` shares one provider-owned persistent sandbox across eve sessions that use the same name:

```ts
export default defineSandbox(({ session }) =>
  environment.getOrCreate({ name: `team-${session.auth.current?.principalId}` }),
);
```

eve namespaces the authored name with the sandbox definition, environment generation, and constructor configuration. Calls that reuse a name with the built-in environments must use the same configuration; conflicting calls fail. Named sandboxes have provider-owned lifetime, so an attached eve session cannot delete or stop one. Do not write per-user credentials into a shared filesystem or apply per-session network policy changes to it.

### Share a parent sandbox

A declared subagent can use its dispatching parent's sandbox explicitly:

```ts title="agent/subagents/reviewer/sandbox.ts"
import { defineParentSandbox } from "eve/sandbox";
export default defineParentSandbox();
```

An inheriting subagent cannot declare its own managed workspace or skill files.

## Seed workspace files and skills

Use the folder layout when the sandbox needs authored files:

```text
agent/sandbox/
  sandbox.ts
  workspace/
    schema.sql
```

Files under `workspace/` seed writable `/workspace`. Skills are available under `$HOME/.agents/skills`. Docker and microsandbox stage compiled workspace and skill resources through content-addressed read-only mounts under `/eve/resources`, then copy workspace seed files into writable `/workspace` when the template is prepared.

## Environments

| Import                                                | Environment                                                                          |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `DefaultSandbox` from `eve/sandbox`                   | Vercel on Vercel, then Docker, microsandbox, or just-bash according to availability. |
| `VercelSandbox` from `eve/sandbox/vercel`             | Snapshot-backed Vercel Sandbox.                                                      |
| `DockerSandbox` from `eve/sandbox/docker`             | A local Docker container.                                                            |
| `MicrosandboxSandbox` from `eve/sandbox/microsandbox` | A local microsandbox VM.                                                             |
| `JustBashSandbox` from `eve/sandbox/just-bash`        | A pure-JavaScript shell and virtual filesystem.                                      |

### Existing images

Docker and microsandbox accept existing OCI images:

```ts
import { defineSandbox } from "eve/sandbox";
import { DockerSandbox } from "eve/sandbox/docker";

export const environment = DockerSandbox.image("ghcr.io/acme/agent@sha256:...", {
  networkPolicy: "deny-all",
});
export default defineSandbox(() => environment.create());
```

Use `MicrosandboxSandbox.image()` for microsandbox. Vercel does not use the local OCI-image path.

### Custom providers

Define a reusable provider with `defineSandboxProvider()` from `eve/sandbox/provider`. Its `environment()` implementation prepares provider-native templates and implements named persistent creation; eve supplies stable names, resources, and persisted metadata.

```ts
import { defineSandboxProvider } from "eve/sandbox/provider";

export const AcmeSandbox = defineSandboxProvider<
  { image: string },
  { networkPolicy?: "allow-all" | "deny-all" },
  { remoteId: string },
  { templateId: string }
>({
  name: "acme",
  environment(options: { image: string }) {
    const client = createAcmeClient(options);
    return {
      async prepare(ctx) {
        const temporary = await client.createTemporary({
          mounts: await uploadResources(ctx.resources),
          name: ctx.templateName,
        });
        const sandbox = adaptAcmeSandbox(temporary);
        await sandbox.run({
          command: [
            "cp -a /eve/resources/workspace/. /workspace/ 2>/dev/null || true",
            'mkdir -p "$HOME/.agents"',
            'ln -s /eve/resources/skills "$HOME/.agents/skills" 2>/dev/null || true',
          ].join("\\n"),
        });
        await ctx.runPreparation(sandbox);
        const template = await client.saveTemplate(ctx.templateName, temporary);
        return { artifact: { templateId: template.id }, reused: false };
      },
      async getOrCreate(ctx, prepared) {
        const templateId = prepared?.artifact.templateId;
        const remote = await client.getOrCreate({
          existingId: ctx.existing?.remoteId,
          mounts: await uploadResources(ctx.resources),
          name: ctx.sandboxName,
          templateId,
        });
        return ctx.handle({
          sandbox: adaptAcmeSandbox(remote),
          metadata: { remoteId: remote.id },
          stop: () => remote.stop(),
          shutdown: () => remote.stop(),
          delete: () => remote.delete(),
        });
      },
    };
  },
});
```

Built-in and custom providers use this same contract. `prepare()` returns a JSON-serializable environment artifact that eve writes into build output. At runtime, eve passes `{ templateName, artifact }` as the second `getOrCreate()` argument when the environment was prepared, or `undefined` otherwise. The fourth `defineSandboxProvider` generic types that artifact for both methods. Providers consume it instead of reconstructing prepared resource identifiers.

`ctx.resources.workspace` and `ctx.resources.skills` each provide a content key, optional materialized source path, relative files, a read-only mount path under `/eve/resources`, and the final agent-visible target (`/workspace` or `$HOME/.agents/skills`). A provider can upload files directly or mount native volumes, but it must make the resources available at those target paths before calling `ctx.runPreparation()`. Keep provider SDK types behind the provider so selectors always receive eve's `RuntimeSandboxSession`.

### A colocated Dockerfile

Docker and microsandbox can build `agent/sandbox/Dockerfile`:

```text
agent/sandbox/
  Dockerfile
  sandbox.ts
  workspace/
```

```ts
import { defineSandbox } from "eve/sandbox";
import { DockerSandbox } from "eve/sandbox/docker";

export const environment = DockerSandbox.dockerfile();
export default defineSandbox(() => environment.create());
```

Use `MicrosandboxSandbox.dockerfile()` for microsandbox. `eve build` hashes the Dockerfile context, builds the image with Docker, and reuses it until an input changes. microsandbox publishes that local image through its development registry before creating a VM. A Docker daemon is required for both Dockerfile build paths.

## Lifecycle

Session-owned sandboxes persist across turns and deployments while their provider state remains available. `sandbox.stop()` stops compute without deleting persisted state. `sandbox.delete()` removes a session-owned sandbox; the next `ctx.getSandbox()` creates a fresh sandbox from the current environment.

Changing sandbox source, preparation code, Dockerfile content, or workspace resources produces a new environment generation. Existing durable sessions retain their recorded sandbox state; new sessions use the current generation.

## Network policy

Declare immutable local policies on the environment. Vercel can also resolve policy and resource options when it creates a session:

```ts
export const environment = DockerSandbox.environment({ networkPolicy: "deny-all" });
export default defineSandbox(() => environment.create());
```

```ts
return vercelEnvironment.create({ networkPolicy: "deny-all" });
```

Vercel and microsandbox support domain policies and credential transforms. Docker supports `"allow-all"` and `"deny-all"`. just-bash has no network isolation. You can call `setNetworkPolicy()` later on a dedicated sandbox, but shared named sandboxes must use one policy for every attached session.
