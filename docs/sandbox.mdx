Every eve agent has a sandbox: a filesystem rooted at `/workspace` with process and file operations. The built-in `bash`, `read_file`, `write_file`, `glob`, and `grep` tools use it automatically.

You do not need to author anything for the default sandbox. Add `agent/sandbox.ts` or `agent/sandbox/sandbox.ts` when you need a particular provider, build-time setup, session-dependent selection, intentional sharing, or direct access to the host filesystem.

## Using the sandbox

Authored runtime code gets the current sandbox from its callback context:

```ts title="agent/tools/run_analysis.ts"
import { defineTool } from "eve/tools";
import { z } from "zod";

export default defineTool({
  description: "Run a Python analysis script.",
  inputSchema: z.object({ script: z.string() }),
  async execute({ script }, ctx) {
    const sandbox = await ctx.getSandbox();
    await sandbox.writeTextFile({ path: "analysis/run.py", content: script });
    return await sandbox.run({ command: "python analysis/run.py" });
  },
});
```

Relative paths resolve from `/workspace`; absolute paths pass through. `sandbox.resolvePath("repo/build.py")` returns `/workspace/repo/build.py`.

| Method                                   | Use                                                    |
| ---------------------------------------- | ------------------------------------------------------ |
| `run({ command })`                       | Run a command and wait for its result                  |
| `spawn(options)`                         | Start a long-running process                           |
| `readTextFile` / `writeTextFile`         | Read or write text                                     |
| `readBinaryFile` / `writeBinaryFile`     | Read or write bytes                                    |
| `readFile` / `writeFile`                 | Stream bytes                                           |
| `removePath({ path, force, recursive })` | Remove a file or directory                             |
| `resolvePath(path)`                      | Resolve a path against `/workspace`                    |
| `setNetworkPolicy(policy)`               | Change the live sandbox's egress policy when supported |

## Returning a sandbox

A sandbox definition is a function that returns the actual durable `Sandbox` the agent should use:

```ts title="agent/sandbox.ts"
import { defineSandbox } from "eve/sandbox";
import { VercelSandbox } from "eve/sandbox/vercel";

export default defineSandbox(() => {
  return VercelSandbox.create({
    resources: { vcpus: 2 },
  });
});
```

The function runs on the first sandbox access for a session. eve persists the returned provider handle. Later turns and runs restore that handle directly without invoking the definition again.

The definition receives only information useful for choosing or configuring the sandbox:

```ts
defineSandbox(({ session, runtime, signal, parent, root }) => {
  // session: current session and auth
  // runtime.mode: "development" | "production"
  // signal: creation cancellation signal
  // parent?.sandbox: parent's durable Sandbox
  // root?.sandbox: root agent's durable Sandbox
});
```

There are no authored sandbox ids, cache keys, template keys, or revalidation keys.

## Build-prewarmed templates

Build-time setup is a separate, statically discoverable value. Export a provider template and return a sandbox created from it:

```ts title="agent/sandbox/sandbox.ts"
import { defineSandbox } from "eve/sandbox";
import { VercelSandbox } from "eve/sandbox/vercel";

export const template = VercelSandbox.template({
  async prepare(sandbox) {
    await sandbox.run({
      command: "pnpm install --frozen-lockfile",
    });
  },
});

export default defineSandbox(() => {
  return template.create({
    resources: { vcpus: 4 },
  });
});
```

`VercelSandbox.template()` is synchronous and has no provider side effects. During `eve build`, eve discovers the named export, hydrates managed files, runs `prepare()`, captures the provider result, and freezes its exact snapshot reference into the deployment. At runtime, `template.create()` starts the session sandbox from that result.

The session definition is never executed during build. It can safely inspect auth, choose among exported templates, or return a parent sandbox:

```ts
export const standard = VercelSandbox.template();
export const python = VercelSandbox.template({
  async prepare(sandbox) {
    await sandbox.run({ command: "uv sync --frozen" });
  },
});

export default defineSandbox(({ session }) => {
  return session.auth.current?.attributes.runtime === "python"
    ? python.create()
    : standard.create();
});
```

Every template a runtime branch can choose must be a named export so eve can prewarm it.

## Seeding `/workspace`

Files under `agent/sandbox/workspace/` are copied into the prewarmed template:

```text
agent/sandbox/
├── sandbox.ts
└── workspace/
    ├── schema.sql
    └── scripts/run.sh
```

Use the folder layout and export a template whenever an authored sandbox owns managed workspace files:

```ts title="agent/sandbox/sandbox.ts"
import { DefaultSandbox, defineSandbox } from "eve/sandbox";

export const template = DefaultSandbox.template();

export default defineSandbox(() => template.create());
```

The workspace contents and relevant compiled preparation code participate in eve's private template revision. Change the source or managed files and eve builds a new compatible template automatically.

## One-time session setup

Configure the live sandbox before returning it. This code runs only when the owning session needs a new sandbox, not during restoration:

```ts
export default defineSandbox(async ({ session }) => {
  const sandbox = await template.create({
    resources: { vcpus: 4 },
  });

  await sandbox.setNetworkPolicy(
    session.auth.current === null ? "deny-all" : { allow: ["api.github.com"] },
  );
  await sandbox.writeTextFile({
    path: ".eve/owner.txt",
    content: `${session.auth.current?.principalId ?? "anonymous"}\n`,
  });

  return sandbox;
});
```

## Reuse and sharing

Reuse across runs of one eve session is automatic. The definition runs once, eve persists the returned `Sandbox`, and later runs reconnect to it.
If the persisted provider resource has been deleted or replaced, restoration fails instead of silently substituting a fresh sandbox.

To intentionally share one Vercel sandbox across independent eve sessions, choose the same provider resource:

```ts
export const template = VercelSandbox.template();

export default defineSandbox(({ session }) => {
  const teamId = session.auth.current?.attributes.teamId;
  if (typeof teamId !== "string") {
    throw new Error("A team identity is required");
  }

  return template.getOrCreate({
    name: `team-${teamId}-workspace`,
  });
});
```

Both eve sessions persist their own handle to the same provider sandbox. They see the same files and processes, and their commands can race, so do not use this shape when credentials or network policies must differ.

eve shutdown hooks may stop active compute, but they never delete durable provider state. Provider retention and deletion remain explicit provider or application operations, including when a child returns an ancestor sandbox.

A child can deliberately return its parent's exact durable sandbox:

```ts title="agent/subagents/reviewer/sandbox.ts"
import { defineSandbox } from "eve/sandbox";

export default defineSandbox(({ parent }) => {
  if (parent === null) {
    throw new Error("reviewer must run as a child");
  }
  return parent.sandbox;
});
```

Nested children can return `root.sandbox` the same way. Declared subagents still use their own sandbox definition or the framework default unless they explicitly return an ancestor.

## Providers

| Provider API          | Runs the sandbox                                                                  |
| --------------------- | --------------------------------------------------------------------------------- |
| `VercelSandbox`       | Hosted [Vercel Sandbox](https://vercel.com/docs/sandbox)                          |
| `DockerSandbox`       | A local container through the Docker CLI                                          |
| `MicrosandboxSandbox` | A lightweight local microsandbox VM                                               |
| `JustBashSandbox`     | A pure-JavaScript shell and virtual filesystem; no real binaries                  |
| `DefaultSandbox`      | Vercel when hosted, then Docker, microsandbox, or just-bash by local availability |

Each provider exposes `create(options)` and, when it supports prewarming, `template(options)`.

```ts
import { DockerSandbox } from "eve/sandbox/docker";

export const template = DockerSandbox.template({
  image: "node:24-bookworm",
  pullPolicy: "if-not-present",
  async prepare(sandbox) {
    await sandbox.run({ command: "corepack enable" });
  },
});

export default defineSandbox(() => template.create());
```

Development can deliberately use a local container while production uses hosted compute:

```ts
import { defineSandbox } from "eve/sandbox";
import { DockerSandbox } from "eve/sandbox/docker";
import { VercelSandbox } from "eve/sandbox/vercel";

export default defineSandbox(({ runtime }) => {
  if (runtime.mode === "development") {
    return DockerSandbox.create();
  }
  return VercelSandbox.create();
});
```

## Custom providers

Provider packages create and adapt native handles with `defineSandboxAdapter`. eve supplies the stable resource identity; the adapter maps it to provider creation, serialization, and restoration. App definitions still return only `Sandbox` values. The provider-owned `type` identifies its durable wire protocol and stays inside the provider implementation.

```ts
import { defineSandboxAdapter } from "eve/sandbox/provider";

const asDevboxSandbox = defineSandboxAdapter<Devbox, { id: string }>({
  type: "example.com/devbox/v1",
  reference(devbox) {
    return { id: devbox.id };
  },
  restore({ id }, { signal }) {
    return Devbox.get({ id, signal });
  },
  session(devbox) {
    return adaptDevboxSession(devbox);
  },
});

export const DevboxSandbox = {
  create(options: { owner?: string } = {}) {
    return asDevboxSandbox.create(({ resourceId, signal }) => {
      return Devbox.getOrCreate({
        id: resourceId,
        owner: options.owner,
        signal,
      });
    });
  },
};

export default defineSandbox(({ session }) =>
  DevboxSandbox.create({
    owner: session.auth.current?.principalId,
  }),
);
```

`adapter.create()` supplies eve's stable resource id, cancellation signal, app root, and resource tags to provider implementation code. App definitions never forward that framework bookkeeping.
The serialized provider reference must keep identifying the same durable resource. Providers that rotate snapshots or checkpoints keep the latest checkpoint behind that identity instead of invalidating handles already held by a parent or child session.

A provider that supports build prewarming can additionally expose a template using `defineSandboxTemplate` from `eve/sandbox/provider`. The template supplies its own stable, versioned `type`, such as `"example.com/devbox-template/v1"`. Its `prewarm({ appRoot, assets, hydrate, log, templateId })` implementation returns a JSON-serializable provider reference; its `create({ options, reference })` implementation returns a durable `Sandbox`. References are scoped to the active definition invocation, so one immutable template value can be used safely by concurrent sessions.

## Network policy

Default egress is `allow-all`. For sensitive or production workloads, set `deny-all` or an explicit allow-list before running untrusted commands:

```ts
const sandbox = await VercelSandbox.create({
  networkPolicy: {
    allow: ["ai-gateway.vercel.sh", "*.github.com"],
    subnets: { deny: ["10.0.0.0/8"] },
  },
});
```

You can also call `sandbox.setNetworkPolicy(...)` before returning the sandbox or during a turn. Vercel Sandbox and microsandbox support domain policies and credential brokering. Docker supports `"allow-all"` and `"deny-all"`. just-bash does not provide network isolation.
