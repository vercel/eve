`useEveAgent()` from `eve/vue` exposes the shared eve frontend client as Vue computed refs and methods. Read the [frontend overview](./overview) for session behavior, messages, human input, authorization, callbacks, and persistence. This page covers the Vue-specific interface.

Nuxt users normally receive the composable as an auto-import after registering the [`eve/nuxt` module](./nuxt).

## Basic usage

Import the composable from `eve/vue`. Its state is exposed as `ComputedRef`s, so templates unwrap it automatically:

```vue
<script setup lang="ts">
import { useEveAgent } from "eve/vue";
import { computed, ref } from "vue";

const { messages, status, send } = useEveAgent();
const message = ref("");
const isBusy = computed(() => status.value === "busy");
const isInputDisabled = computed(() => isBusy.value || status.value === "resuming");

async function handleSubmit() {
  const text = message.value.trim();
  if (!text || isInputDisabled.value) return;
  message.value = "";
  await send(text);
}
</script>

<template>
  <div v-for="item in messages" :key="item.id">
    <p>{{ item.role }}: {{ item.parts }}</p>
  </div>
  <form @submit.prevent="handleSubmit">
    <input v-model="message" :disabled="isInputDisabled" />
    <button type="submit" :disabled="isInputDisabled">Send</button>
  </form>
</template>
```

## What it returns

The state fields are computed refs; the commands are ordinary methods:

| Property                                                                                    | Vue shape                                       |
| ------------------------------------------------------------------------------------------- | ----------------------------------------------- |
| `messages`, `agents`                                                                        | Computed refs for each projected snapshot field |
| `view`                                                                                      | `ComputedRef<SessionView>`                      |
| `status`                                                                                    | `ComputedRef<UseEveAgentStatus>`                |
| `error`                                                                                     | `ComputedRef<Error \| undefined>`               |
| `events`                                                                                    | `ComputedRef<readonly SessionStreamEvent[]>`    |
| `session`                                                                                   | `ComputedRef<ClientSessionState \| undefined>`  |
| `send`, `respond`, `prewarm`, `resume`, `cancel`, `clear`, `compact`, `reset`, `newSession` | Methods                                         |

Destructuring preserves reactivity because each state value remains a ref. Read refs with `.value` in `<script>` and without `.value` in a template. The [shared returned-state reference](./overview#returned-state) describes what each value and command does.

## Send a message

Call `send(text)` for text or pass content parts for attachments. The API and transport behavior match the [shared sending guide](./overview#sending-and-streaming); only reactive access differs in Vue. `send()` and `respond()` resolve with `{ sessionId, deliveryId }` when accepted, without waiting for execution to finish.

## Human-in-the-loop prompts

Read requests from the shared `view` and answer them with `respond()`. Submission does not settle
an interaction; its response rows and eventual settlement are authoritative.

```vue
<script setup lang="ts">
import { computed } from "vue";
import { openInteractions } from "eve/events";
import { useEveAgent } from "eve/vue";

const { view, status, respond } = useEveAgent();
const pendingRequests = computed(() =>
  openInteractions(view.value).filter(
    (item) => item.request.kind !== "sign-in" && item.answer === undefined,
  ),
);
</script>

<template>
  <fieldset
    v-for="item in pendingRequests"
    :key="item.interactionId"
    :disabled="status === 'resuming'"
  >
    <legend>{{ item.request.prompt }}</legend>
    <button
      v-for="option in item.request.options ?? []"
      :key="option.id"
      type="button"
      @click="respond([{ interactionId: item.interactionId, optionId: option.id }])"
    >
      {{ option.label }}
    </button>
  </fieldset>
</template>
```

See [Human-in-the-loop prompts](./overview#human-in-the-loop-prompts) for request semantics and rendering guidance.

## Cancel, reset, and resume

Pass `prewarm: true` to prepare an owned workflow on mount and after `newSession()`. It defaults
to `false`, so the first send creates the session. The binding waits for create acceptance,
retries while the inbox starts, and keeps the session stream open across turns. See [Prewarming and returned state](./overview#returned-state) for creation, failure, and
connection behavior.

Call `cancel()` to stop the durable server-side turn while the composable remains attached through settlement. Offer it while `activeTurn(view.value)` from `eve/events` returns a turn: `status` reports outstanding work, so it is `"idle"` while a turn waits only on a person. Disposing the component only disconnects its local stream; it does not cancel server execution. Call `newSession()` to clear local state and start a new session. `reset()` instead retires the server-side session. Pass `initialSession`, `initialEvents`, and `resume: true` to restore a saved conversation and follow an in-flight turn. During bounded catch-up, `status.value` is `"resuming"`; keep the hydrated conversation visible, disable submission, and wait for `"idle"` or `"busy"`, and inspect the separate `error` field. Use `resume()` directly when restoration is controlled imperatively. See [Resumable sessions](./overview#resumable-sessions) for the persistence contract and [Sending and streaming](./overview#sending-and-streaming) for cancellation behavior.

## Custom host and credentials

Pass `baseUrl`, `auth`, or `headers` to the composable using the same options as the other frontend bindings. See [Custom hosts and headers](./overview#custom-hosts-and-headers).

## Attach page context per turn

Pass `clientContext` to `send()` or `respond()`, or use `prepareSend` to add context before every turn. See [Attach page context per turn](./overview#attach-page-context-per-turn).

## Lifecycle callbacks

Pass `onEvent`, `onError`, `onFinish`, or `onSessionChange` when the application needs lifecycle notifications. See [Lifecycle callbacks](./overview#lifecycle-callbacks) for callback timing and optimistic projection behavior.

## Derive your own state

Use `view` and selectors from `eve/events` for lifecycle state, and `messages` for rendering. See [Derive your own state](./overview#derive-your-own-state).
