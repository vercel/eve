Use this guide when you already have a browser application and need to connect it to an eve agent. `useEveAgent()` opens a durable session, sends turns, streams the reply back, and turns the raw event stream into render-ready state. React is the reference implementation; [Vue](./use-eve-agent-vue) and [Svelte](./use-eve-agent-svelte) ship the same surface.

## The integration model

A browser UI is a client of the agent's HTTP routes (the [eve channel](../../channels/overview)). Two layers wire it up:

- **Routing** makes the agent reachable from the browser. A framework integration can mount eve on your app's origin: [Next.js](./nextjs) (`withEve`), [Nuxt](./nuxt) (the `eve/nuxt` module), [SvelteKit](./sveltekit) (the `eveSvelteKit` Vite plugin), or [TanStack Start](./tanstack) (the `eveTanStack` Vite plugin). If the frontend and agents are peer services, use your deployment platform or reverse proxy instead. The hook works with either setup; pass `host` for a different origin or a named path mount.
- **The hook** (`useEveAgent`) holds the session state, streaming, errors, and composer status. It defaults to same-origin eve routes such as `/eve/v1/session`.

The framework pages walk through the wiring step by step: [Next.js](./nextjs), [Nuxt](./nuxt), [SvelteKit](./sveltekit), and [TanStack Start](./tanstack). See [Project Structure](../../concepts/project-structure#configure-a-web-deployment) to choose between a framework integration and peer services.

For scripts, server-to-server calls, evals, tests, or custom clients that do not need framework UI state, use the [Client SDK](../client/overview) directly.

## Authenticate browser requests

A same-origin framework integration sends your application cookies with every eve request. For bearer tokens or another non-cookie scheme, pass `auth` or `headers` to `useEveAgent`.

The default eve channel fails closed. Without an authored `agent/channels/eve.ts`, production browser traffic receives `401` from the default `[vercelOidc(), localDev(), placeholderAuth()]` policy. Add the channel file with an `AuthFn` that verifies your application session or token.

For a public demo, use `none()` from `eve/channels/auth` to admit anonymous requests explicitly. Do not use `none()` for an agent that handles private or production data. See [Authentication](../auth-and-route-protection) for application-session examples, token verifiers, and the default policy.

## Basic chat (React)

The hook lives in `eve/react`. Render `messages`, use `status` to steer follow-ups during an active turn, and send text with `send`:

```tsx
"use client";

import { useEveAgent } from "eve/react";

export function Chat() {
  const agent = useEveAgent();
  const isBusy = agent.status === "busy";
  const isResuming = agent.status === "resuming";

  return (
    <form
      onSubmit={(event) => {
        event.preventDefault();
        const form = new FormData(event.currentTarget);
        const message = String(form.get("message") ?? "").trim();
        if (message.length > 0 && !isResuming) {
          void agent.send(message, isBusy ? { turnPolicy: "steer" } : undefined);
        }
      }}
    >
      {agent.messages.map((message) => (
        <article key={message.id}>
          <header>{message.role}</header>
          {message.parts.map((part, index) =>
            part.type === "text" ? <p key={part.id ?? index}>{part.text}</p> : null,
          )}
        </article>
      ))}
      <input disabled={isResuming} name="message" />
      <button disabled={isResuming} type="submit">
        Send
      </button>
    </form>
  );
}
```

## Returned state

`useEveAgent()` returns the current UI state plus commands:

| Field             | What it is                                                                            |
| ----------------- | ------------------------------------------------------------------------------------- |
| `view`            | Committed lifecycle tables: turns, calls, tasks, interactions, deliveries, and usage. |
| `previews`        | In-progress text and tool-input previews.                                             |
| `messages`        | Rendered messages, including local optimistic submissions and answers.                |
| `agents`          | Followed child sessions and their independent observations.                           |
| `status`          | `"idle"`, `"busy"`, or `"resuming"`. Errors are separate.                             |
| `error`           | The latest session creation, stream, resume, or turn failure.                         |
| `events`          | Raw eve stream events for this session.                                               |
| `session`         | Serializable fixed session cursor (`sessionId`, `streamIndex`).                       |
| `prewarm`         | Create the durable session without starting a turn.                                   |
| `send`, `respond` | Submit a message or answers; resolve with `{ sessionId, deliveryId }` when accepted.  |
| `resume`          | Replay through the current durable tail, then keep following independently.           |
| `cancel`          | Request durable cancellation of the active turn.                                      |
| `reset`           | Clear local state and the local session cursor.                                       |

Most chat UIs only need `messages` and `status`. Use `view` with selectors from `eve/events` for lifecycle state, or `events` when you need the wire log for persistence or audit. Snapshots publish after every fact in a committed line has folded.

Pass `prewarm: true` to start a workflow when the chat mounts and after each reset:

```tsx
import { useEveAgent } from "eve/react";

export function Chat() {
  const agent = useEveAgent({ prewarm: true });

  return <button onClick={agent.reset}>New chat</button>;
}
```

In React, `prewarm` is a live boolean. Use component state to wait until the user starts
composing a message:

```tsx
import { useEveAgent } from "eve/react";
import { useState } from "react";

export function Chat() {
  const [message, setMessage] = useState("");
  const agent = useEveAgent({ prewarm: message.length > 0 });

  return (
    <>
      <input value={message} onChange={(event) => setMessage(event.currentTarget.value)} />
      <button
        onClick={() => {
          setMessage("");
          agent.reset();
        }}
        type="button"
      >
        New chat
      </button>
    </>
  );
}
```

An initial `true` value or a later `false` to `true` change prepares the current owned session.
Changing `prewarm` back to `false` does not abort creation or discard an existing session. If
a reset and state update happen in the same event, React applies both before deciding whether
to prepare the next session. Vue and Svelte read `prewarm` when their binding is created; call
their returned `prewarm()` method for interaction-driven creation.

Prewarming defaults to `false`: the first send creates the session. Set it to `true` only after
your application's auth, headers, and any chat-record binding are ready. Applications that
prepare those in the submit handler should keep the default until then.

Prewarming starts the workflow and establishes its inbox, then parks before session hooks,
dynamic definitions, or sandbox setup run. The first message passes through the channel's
`onMessage` hook and supplies the identity and context for initialization and `turn_0`.

The explicit `prewarm()` method resolves on `202 Accepted`, as does `client.sessions.create()`.
It does not wait for an initialization event; concurrent calls share the same create request.
The composer stays `"idle"`, meaning it can accept input, and prewarming does not run
`prepareSend`. A concurrent `send()` waits only for acceptance, then posts the message.
If the inbox is still starting, the client retries `409 session_not_ready` with bounded
exponential backoff for up to 20 seconds. The caller's abort signal cancels the wait. Stream
events are not a prerequisite for sending.

A failed create sets `error` and calls `onError` when no send is waiting. A waiting send can
fall back to creating a session with its message. After creation succeeds, initialization
failures arrive on the stream during the first turn. The configured session timeout starts
at creation, so an unused prewarmed session can expire before its first message. React does not
retry a failed prewarm on unrelated renders while the option remains `true`; call `prewarm()`,
change the option from `false` to `true` again, reset, or send a message to recover.

The hook keeps consuming one session stream across turns and idle periods. Replies,
authorization updates, and turns started elsewhere all update the same projection. Each message a
person sends is its own bubble, placed where its turn took it in: a message that arrives while the
turn works splits the agent's response, so what the agent did before the message shows above it
and the rest below. The pieces share `metadata.turnId`. A single event that coalesces multiple
deliveries remains one bubble. A turn settling does not close the connection. The transport reconnects from
its cursor after a disconnect or the
server's renewable 60-second lease; lease renewal does not start a turn or clear UI state.
Unmounting or resetting closes the local stream without cancelling the old durable session.

An open stream reconnects for as long as the chat stays mounted, even when nothing happens. If
your UI only shows replies to its own messages, such as a help sidebar that stays mounted across
pages, pass `followIdle: false`. The binding then closes the stream once the session is idle: no
turn is running or parked, no task is working, and no sign-in is pending. A prewarmed session
opens no stream until its first message. The next `send()`, `respond()`, or `resume()` reopens
the stream from the session cursor, so events that arrived in between are applied then. Leave
`followIdle` on when other sources, such as schedules, channels, or another tab, can start turns
in the session while your UI is idle.

`reset()` reuses the hook instance and clears the conversation. When `prewarm` is true after
the reset, it prepares the next owned session; otherwise, the next send creates it. An explicitly
supplied `session` remains externally owned and is never replaced by prewarming or reset. Use
`initialSession` with `resume: true` to restore a saved chat.

`messages` are eve-owned `EveMessage[]`. Assistant text and reasoning parts have a stable `id` from the event that created the part. Appends and completion retain that ID. Use `part.id` to key streamed assistant content, including successive text parts within one step. Older events without an ID get a best-effort fallback. User text parts may not have an ID.

A message's parts are `text`, `reasoning`, `file` (an attachment a person sent; its `url` can be absent), `tool` (a call the turn made), and `interaction` (something the turn asked a person that no call carries: a sign-in, the budget prompt, or a question about no call). Each assistant part carries its turn's `stepIndex`. The parts are eve's own; if you pass messages to an API typed as AI SDK `UIMessage[]`, adapt them first.

A `tool` part is the call's row in the session's tables, the same state every eve reader reads:

| Field                      | What it is                                                                                                                                                      |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `callId`, `name`           | The call, and the tool, agent, or skill it invokes.                                                                                                             |
| `kind`                     | `tool`, `agent`, `skill`, or `control` (task controls, usually hidden in activity displays).                                                                    |
| `label`                    | The tool's authored label, its latest output label, or a readable name.                                                                                         |
| `state`                    | `streaming` while input arrives, then the shared `CallState`: `requested`, `approval`, `running`, `blocked`, `completed`, `failed`, `rejected`, or `cancelled`. |
| `inputText`                | Partial input, only when `state` is `streaming`.                                                                                                                |
| `input`, `output`, `error` | Validated input, current or final output, and error details after input streaming.                                                                              |
| `interaction`              | The latest approval or question about the call. Its status stays `open` while an answer is submitted; settlement confirms the decision.                         |

Read raw outcomes, reasons, and task identities from `view.calls[part.callId]` instead of duplicate
fields on the renderable part.
A call your stream stopped following stays open; decide yourself what an open call shows once the stream ended. A call a model retry replaced doesn't show: the replacement asks again.

When the root agent delegates, its stream emits `task.started` for the task, `call.started` with the task's `taskId` for the call, `child.opened` with the child's `sessionId`, and `call.settled` with the call's result, failure, or cancellation. The subagent's tool part stays running until its `call.settled` arrives and then settles with the call's outcome; the start receipt never settles it. `view.calls[callId]` records each call's `taskId`, `status`, `outcome`, `output`, and `error`, and `agents[sessionId]` records each session a call opened, with its `taskId` and opening `callId`. These records come from the root stream alone.

Detailed child progress lives on the child session's stream, not in the root `messages`. Pass `followSubagents: true` to follow the session each subagent call reaches while the component is mounted; following is off by default. Narrow `agents[sessionId].observation.status` before reading its `conversation`: `"not-followed"` has no child detail, `"following"` has live detail, and `"idle"` has everything the calls so far produced and resumes when another call reaches the task. `"unavailable"` means the stream failed, not that the child failed. Calls that continue a task with its `taskId` reach the same session, so one session's `conversation.messages` and its native `view` tables span all of them. Sessions that a custom task opens with `ctx.agent` are recorded but not followed.

If you manage your own session rather than using the hook, pass a `child.opened` event from `events` to [`session.agent()`](../client/streaming#follow-a-subagent) and follow the child with `stream()`. It follows local and remote children through the parent, so the browser never calls a remote deployment directly. See [What the parent sees](../../subagents#what-the-parent-sees) for the complete contract.

## Sending and streaming

Pass the message first and optional per-turn settings second. Use `respond()` for HITL answers:

```tsx
await agent.send("Summarize this session.");

await agent.send([
  { type: "text", text: "What is in this file?" },
  {
    type: "file",
    data: fileDataUrl, // base64 data URL
    mediaType: "application/pdf",
    filename: "report.pdf",
  },
]);
```

Assistant text, reasoning, and tool parts update `messages` as they arrive. `status` is `busy`
while a submission is pending or the session has active work, and `idle` otherwise. `resuming`
means the hook is catching up an attached session; disable message and HITL submission then.
A failure updates `error` without replacing the transport status.

`send()` and `respond()` resolve on HTTP acceptance, before the agent needs to reply or pause. They reject if preparation or submission fails; a later execution failure arrives through `view`, `error`, and `onError`. A turn stays open while its work or questions are pending. Read `activeTurn(view)`, `waiting(view, turnId)`, and `activity(view)` from `eve/events` instead of maintaining another turn state. The stream continues after the command's promise resolves.

To steer an active turn with a follow-up, send the message with `turnPolicy: "steer"`. Before answer output or local tool execution begins, eve interrupts pending model generation and continues the same turn with the correction. Executing tools finish and checkpoint their results first; after answer output starts, steering waits for the next committed workflow boundary. Reasoning and search progress do not count as answer output. The hook stays attached through completion:

```tsx
await agent.send(message, { turnPolicy: "steer" });
```

You can submit another message while work runs: use `turnPolicy: "queue"` to wait for the current
turn, or `"steer"` to guide it. Answers are accepted while other work runs. Read interactions with
`interaction(view, id)` from `eve/events`: their originating turn, step, task, request, and answer
are in one projection. `activeTurn(view)?.turnId` identifies the current root turn. Followed
sessions have their own view under `agents[sessionId].observation.conversation`.
Call `cancel()` to stop the durable turn without replacing it.

`cancel()` targets the currently observed turn and keeps the event stream attached. If no turn is active, it waits for a submission pending when you called `cancel()` to identify its turn. This includes preparation, session creation, and POST acceptance. Cancellation always names the identified turn, so a delayed request cannot stop an unrelated later turn.

This wait does not withdraw a queued message or prevent its turn from starting. If the pending deliveries settle without a running turn, cancellation returns `"no_active_turn"`. Calling `cancel()` while idle, with no pending submissions, does not arm cancellation for future messages. Resetting or unmounting aborts the wait.

The promise resolves when eve accepts cancellation or reports no active turn. It rejects if submission, observation, or the cancellation request fails while waiting. An accepted cancellation settles cooperatively on the same stream with `outcome: "cancelled"`; a turn can finish before cancellation reaches the server.

```tsx
if (agent.status === "busy") {
  await agent.cancel();
}
```

Unmounting the component or closing the page disconnects the local stream but does not cancel server execution. Call `cancel()` before detaching when the user intends to stop the durable turn.

After eve confirms an attachment turn with `delivery.consumed`, each received attachment shows as
a `file` part on the user message. The part includes `mediaType`, optional
`filename` and `size`, and a `url` only when the original attachment was browser-resolvable.

## Human-in-the-loop prompts

Tools gate calls with approval policies, and workflow tools ask questions with `ctx.ask()`.
See [Human-in-the-loop](/docs/human-in-the-loop) for the server-side model. Read open prompts from
`view` and answer through the same session. A call's approval or question also appears as
`part.interaction`; other prompts are `interaction` message parts.

```tsx
import { interaction, openInteractions } from "eve/events";

const pendingRequests = openInteractions(agent.view)
  .flatMap((row) => interaction(agent.view, row.interactionId) ?? [])
  .filter((item) => item.request.kind !== "sign-in" && item.answer === undefined);

return pendingRequests.map(({ interactionId, request }) => (
  <fieldset disabled={agent.status === "resuming"} key={interactionId}>
    <legend>{request.kind === "approval" ? "Approval required" : "Question"}</legend>
    <p>{request.prompt}</p>
    {request.options?.map((option) => (
      <button
        key={option.id}
        type="button"
        onClick={() => void agent.respond([{ interactionId, optionId: option.id }])}
      >
        {option.label}
      </button>
    ))}
  </fieldset>
));
```

For free text, send `{ interactionId, text }`. An optimistic answer appears on its message part
during the POST round trip. Once the view holds that delivery, response rows own the answer.
The interaction stays `open` until `interaction.settled` confirms the decision; there is no local
`responded` status. A refused response leaves the prompt answerable. A POST that fails retracts
only its own optimistic answer, not a newer submission.

## Sign-ins and other interactions

Connections and tools that need OAuth or another grant open a sign-in: an `interaction.opened` with `request.kind: "sign-in"`. Sign-ins are interactions like approvals and questions, in `view.interactions`. An approval or question about a call shows on that call's tool part; every other interaction, such as a sign-in or the budget prompt, is an `interaction` message part of its own (`EveInteractionPart`). Its `request` is the interaction as asked, a sign-in's challenge in `request.signIn` (the display name, instructions, device code, and user-facing sign-in URL). The part is `open` until its interaction settles, then `settled` with its `outcome`. Render the part as a normal chat message and keep the session cursor so eve can resume the parked turn once the sign-in completes:

```tsx
import { signInEnding, type EveMessagePart } from "eve/react";

function SignInPrompt({ part }: { part: EveMessagePart }) {
  if (part.type !== "interaction" || part.request.kind !== "sign-in") return null;
  const signIn = part.request.signIn;
  const name = signIn?.displayName ?? signIn?.name;

  if (part.status === "settled" && part.outcome !== undefined) {
    // "connected", "declined", "failed", "timed out", or "cancelled"
    return <p>{`${name}: ${signInEnding(part.outcome)}.`}</p>;
  }

  return (
    <section>
      <p>{signIn?.instructions ?? part.request.prompt}</p>
      {signIn?.userCode ? <code>{signIn.userCode}</code> : null}
      {signIn?.url ? <a href={signIn.url}>Sign in</a> : null}
    </section>
  );
}
```

A sign-in's `interaction.opened` and `interaction.settled` facts are also available on `events` and `onEvent`.

## Attach page context per turn

`clientContext` adds ephemeral context for the current turn. Strings (or an array of strings) become user-role context messages; an object is JSON-serialized into one. The context remains available to every model call in the turn, then disappears before the next turn. It rides along with a message or HITL response, so it never dispatches a turn on its own and never lands in durable session history. Pass it in the second argument to `send()` or `respond()`:

```tsx
await agent.send("What should I do on this screen?", {
  clientContext: { route: "/billing", plan: "pro", seatsUsed: 4 },
});
```

To attach the same context to every turn without threading it through each call site, use `prepareSend`. It runs right before each send and returns the (possibly augmented) turn. The optimistic message is already visible while asynchronous preparation runs:

```tsx
const agent = useEveAgent({
  prepareSend: (input) => ({
    ...input,
    clientContext: { route: location.pathname },
  }),
});
```

## Lifecycle callbacks

The hook accepts these lifecycle callbacks:

- `onEvent(event)`: fires for each eve stream event as it arrives.
- `onError(error)`: fires when session creation, streaming, resume, or a turn fails. A failed prewarm reports here when no send is waiting to retry creation.
- `onFinish(snapshot)`: fires when a live turn settles, after its whole committed line is visible. An explicit `resume()` does not replay historical finish callbacks.
- `onSessionChange(session)`: fires when a session is created, its cursor advances, or reset clears it. Persist the session state to resume across reloads.

```tsx
const agent = useEveAgent({
  onEvent: (event) => console.debug(event.type),
  onError: (error) => toast.error(error.message),
  onFinish: (snapshot) => console.log(snapshot.status),
});
```

The `optimistic` option (default `true`) shows submitted user messages in `messages` before eve confirms them with a `delivery.consumed` fact. A follow-up sent while a turn works shows at the end of the conversation and stays there once the turn takes it in; if the send fails, the failed placeholder stays in place, with `metadata.status` `"failed"`. They show in `messages` only; `events` stays the authoritative eve stream. The hook reconciles each placeholder with the server's delivery ID, including the first message. Its message ID stays unchanged when confirmed, so an unrelated or identical message cannot consume it. While POST acknowledgements are pending, stream-driven snapshot publication waits for their identities; `onEvent` still receives the stream events.

## Derive your own state

Read lifecycle state directly from `view`. It is the shared fold's committed snapshot, not a second conversation-specific turn or task model:

```tsx
import { activeTurn, activity, waiting } from "eve/events";

const turn = activeTurn(agent.view);
const currentActivity = activity(agent.view);
const blocked = turn === undefined ? undefined : waiting(agent.view, turn.turnId);
```

For event-level queries, use `events`, the authoritative, deduplicated list of the session's stream events, which a reset empties:

```tsx
import { useMemo } from "react";
import { useEveAgent } from "eve/react";

const agent = useEveAgent();
const toolCalls = useMemo(
  () => agent.events.filter((event) => event.type === "call.requested").length,
  [agent.events],
);
```

Use the snapshot's `view` instead of folding `events` again inside a component. Outside the
store, `foldEvents` and `emptySessionView` from `eve/events` fold received events by whole line;
retain any unfinished line that `foldEvents` returns and pass it with the next batch. To render a
saved log, use `conversationOf(events)` from `eve/client`.

## Resumable sessions

The browser conversation lives durably on the server. Persist both the rendered event log and the `session` cursor to pick it back up after a reload:

```tsx
import { useEffect, useState } from "react";
import { useEveAgent } from "eve/react";
import type { ClientSessionState, SessionStreamEvent } from "eve/client";

type SavedEveChat = {
  events?: readonly SessionStreamEvent[];
  session?: ClientSessionState;
};

const [saved] = useState<SavedEveChat>(() => {
  const raw = localStorage.getItem("eve-chat");
  return raw ? JSON.parse(raw) : {};
});

const agent = useEveAgent({
  initialEvents: saved.events ?? [],
  initialSession: saved.session,
  resume: saved.session !== undefined,
});

useEffect(() => {
  localStorage.setItem(
    "eve-chat",
    JSON.stringify({ events: agent.events, session: agent.session }),
  );
}, [agent.events, agent.session]);
```

Store the full `session` object (`sessionId`, `streamIndex`). The session cursor
lets eve continue the exact durable conversation; the event log lets your UI
render historical messages without replaying the whole stream. A database-backed
chat app should persist committed events and the matching cursor as they change. Do not save only
in `onFinish`: a turn paused for a person has not finished, but its events must survive a reload.

`initialEvents` must be an ordered prefix of the same session's stream, but its endpoint does not have to line up exactly with where the stream resumes. Catch-up starts at the next complete line in the saved log, using line positions rather than the number of materialized events. A partial line is replayed from its start; already observed events are skipped. Every event carries a stable [`meta.position`](/docs/concepts/sessions-runs-and-streaming#positions), and the store drops any event whose position it has already applied, so an overlapping replay renders once and `onEvent` only fires for events your UI has not seen.

For multiple chat threads, keep one saved event log and session cursor per thread. `agent`, `host`, `session`, `initialEvents`, `initialSession`, `auth`, `headers`, `optimistic`, `followIdle`, and `resume` are read when the hook creates its store, so remount the chat component when switching threads, for example with `key={chat.id}`. React reads `prewarm` on every render.

Pass `resume: true` with `initialSession` to rebuild the projection from the durable stream after mount. While `status` is `"resuming"`, render hydrated `messages` but disable message and HITL submission; do not present cancellation or active-turn progress controls. `resume()` resolves when catch-up reaches the durable tail, even if a turn is still running. The binding then reports `"busy"` and continues following it. The stream reports its initial durable tail so catch-up can finish without closing the connection or waiting for an idle timeout. A settled tail changes directly to `"idle"`; a newer turn or pending authorization remains `"busy"`. The connection stays open to receive later events. A terminal session failure sets `error`.

```tsx
const agent = useEveAgent({
  initialSession: { sessionId, streamIndex: 0 },
  resume: true,
});
```

If the user can refresh or navigate immediately after pressing send, create your app-level chat row before calling `send()`, then persist the session ID from `onSessionChange`. This lets the reloaded UI mount with that ID and pass `resume: true` while the durable turn is still running.

## Custom hosts and headers

Pass `host` when the eve server isn't same-origin, and pass `auth` or `headers` when the channel needs credentials. Function values are re-resolved before every HTTP request, reconnects included:

```tsx
const agent = useEveAgent({
  host: "https://agent.example.com",
  auth: {
    bearer: async () => await getAccessToken(),
  },
});
```

Headers supplied to `send()` apply to that turn request and become the credentials used by the
continuous session stream on its next reconnect. A later send replaces them with that turn's
headers.

When a framework integration mounts multiple named agents, pass `agent` instead of `host`:

```tsx
const support = useEveAgent({ agent: "support" });
```
