The `eve/nuxt` module runs a Nuxt frontend and an eve agent as one project, with one dev server and one Vercel deploy. The auto-imported [`useEveAgent`](./use-eve-agent-vue) composable finds the mounted routes on its own, so you configure no CORS or URL env vars.

## Prerequisites

- The `eve` package installed in your project (`npm install eve@latest`).
- An existing eve agent directory. If you don't have one, start from [Getting started](../../getting-started).
- A Nuxt app to mount the agent in.

## Register the module

```ts title="nuxt.config.ts"
export default defineNuxtConfig({
  modules: ["eve/nuxt"],
});
```

The module looks for an `agent/` folder in the Nuxt project root, mounted at `/eve/v1/*`. An `agents/` workspace mounts each member at `/eve/<name>/v1/*` instead. Pass `eveRoot` when the agent lives elsewhere:

```ts
export default defineNuxtConfig({
  modules: ["eve/nuxt"],
  eve: {
    eveRoot: "../my-agent",
  },
});
```

### `eve/nuxt` options

All fields are optional.

| Option               | Type     | Default           | Purpose                                                                                                           |
| -------------------- | -------- | ----------------- | ----------------------------------------------------------------------------------------------------------------- |
| `eveRoot`            | `string` | Nuxt project root | eve project root, relative to the Nuxt project root unless absolute.                                              |
| `eveBuildCommand`    | `string` | generated         | Build command for the generated eve Vercel service.                                                               |
| `devServerTimeoutMs` | `number` | `180000`          | Maximum time to wait for the eve development server to start, including when another Nuxt process is starting it. |

For slow cold starts, increase the development timeout:

```ts
export default defineNuxtConfig({
  modules: ["eve/nuxt"],
  eve: {
    devServerTimeoutMs: 300_000,
  },
});
```

## Call the composable

`useEveAgent` (`eve/vue`) is auto-imported, so a component calls it without an explicit import and without passing `baseUrl`:

```vue
<script setup lang="ts">
const { status, send } = useEveAgent();

const isBusy = computed(() => status.value === "busy");
const isInputDisabled = computed(() => isBusy.value || status.value === "resuming");

const message = ref("");

async function handleSubmit() {
  const text = message.value.trim();
  if (!text || isInputDisabled.value) return;
  message.value = "";
  await send(text);
}
</script>

<template>
  <form @submit.prevent="handleSubmit">
    <input v-model="message" :disabled="isInputDisabled" />
    <button type="submit" :disabled="isInputDisabled">Send</button>
  </form>
</template>
```

The browser still needs a production authentication policy. See [Authenticate browser requests](/docs/guides/frontend#authenticate-browser-requests) for the default policy, which rejects unverified requests, and for channel configuration.

## Dev vs deploy topology

- **Local dev.** `npm run dev` starts an eve dev server for each agent beside `nuxt dev` and proxies the eve routes to it. The browser talks only to the Nuxt origin. Set `EVE_BASE_URL` to proxy to an eve dev server you already run instead.
- **Vercel.** The web app and the eve runtime deploy as a single project. On Vercel builds, the module adds an eve [service](https://vercel.com/docs/services) per agent and routes its transport requests to it before filesystem routing. The Nuxt app serves everything else, and no `vercel.json` is required. When `vercel.json` declares services, or a `vercel.ts` composes them with `withEve` from `eve/vercel`, the module generates nothing and that configuration controls routing. By default, each generated service runs the installed eve binary from its agent root, so agent directories don't need their own `package.json`. When the agents need their own build step, set `eveBuildCommand`:

  ```ts
  export default defineNuxtConfig({
    modules: ["eve/nuxt"],
    eve: {
      eveBuildCommand: "npm run build:eve",
    },
  });
  ```

- **Non-Vercel hosts.** The built Nuxt server starts each built eve agent and proxies its transport routes to a loopback server. A standalone `agent/` uses `http://127.0.0.1:4274`. Workspace members use consecutive ports in alphabetical order of member name (`4274`, `4275`, ...). Each backend serves `/eve/v1`; Nuxt mounts it at `/eve/<name>/v1`. Set `EVE_NUXT_PRODUCTION_PORT` during `nuxt build` to select another first port. The build fixes both the proxy destinations and managed server ports.

  `eve build` and `nuxt build` both write `.output/`. For a standalone agent, use a separate eve project directory with its own `package.json` declaring `eve` as a dependency. Set `eveRoot` to that directory; managed startup rejects shared outputs. For example, with `eveRoot: "./backend"`:

  ```bash
  (cd backend && npx eve build)
  npx nuxt build
  node .output/server/index.mjs
  ```

  For an `agents/` workspace, build each member from its own directory; a root `eve build` produces a Vercel workspace deployment:

  ```bash
  (cd agents/support && npx eve build)
  (cd agents/research && npx eve build)
  npx nuxt build
  node .output/server/index.mjs
  ```

  Deploy every member's output, preserving its path relative to the workspace root. A workspace can share the Nuxt project root because member outputs do not overwrite Nuxt's output. See [Run workspace members](../deployment/self-hosted-operations#run-workspace-members) for each member's authentication, Workflow world, and sandbox configuration.

  Run the Nuxt server from the deployed Nuxt project root. Preserve the relative location of `eveRoot`, or set `EVE_NUXT_PRODUCTION_ROOT` at startup to relocate the eve project root. Workspace member paths remain relative to that root. Relative values resolve from the Nuxt server's working directory:

  ```bash
  EVE_NUXT_PRODUCTION_ROOT=./relocated-backend node .output/server/index.mjs
  ```

  Each agent's transport requests wait for its listener during startup, for up to three minutes. Startup does not require an authored health route. If an agent fails to start, its routes return `503`; check the Nuxt server logs for the cause. Other agents and frontend pages remain available. With the default eve channel, use `/eve/v1/health` (or `/eve/<name>/v1/health`) for deployment readiness checks.

  Managed startup supports one Node.js process with Nitro's `node-server` preset. For `node-cluster`, worker deployments, or multiple frontend processes, use an externally managed eve service. Set `EVE_NUXT_PRODUCTION_ORIGIN` at build time, as shown below. Keep Nitro's graceful shutdown enabled; do not set `NITRO_SHUTDOWN_DISABLED`. Shutdown cancels eve startup before draining HTTP requests and waits up to 21 seconds for eve to terminate.

  To manage eve separately, set `EVE_NUXT_PRODUCTION_ORIGIN` during `nuxt build`. That build proxies to the configured origin and does not start eve, even when the variable is absent at runtime. Workspace members keep their public paths on that host (`/eve/<name>/v1`):

  ```bash
  EVE_NUXT_PRODUCTION_ORIGIN=https://agent.example.com npx nuxt build
  ```

  See [Self-host eve](../deployment/self-hosting) for running the separate service. Managed startup does not run during prerendering or `nuxt generate`. Static output has no server-side eve proxy; use a server deployment for this topology.

## Managing vercel.json yourself

When `vercel.json` declares [`services`](https://vercel.com/docs/services), the module generates nothing, and your configuration controls routing. It must include the eve service (`framework: "eve"`) and a rewrite that sends `/eve/v1/*` requests to it, or the module fails the build:

```json title="vercel.json"
{
  "services": {
    "web": { "root": ".", "framework": "nuxtjs" },
    "eve": { "root": "agent", "framework": "eve", "buildCommand": "eve build" }
  },
  "rewrites": [{ "source": "/eve/v1/(.*)", "destination": { "service": "eve" } }]
}
```

### Remove `experimentalServices`

Vercel doesn't route the `experimentalServices` field in `vercel.json`: both services build, but every `/eve/v1/*` request returns `NOT_FOUND`. The module ignores the field and warns that `vercel.json defines experimentalServices`. Remove it in one of two ways:

- **Generated (default).** Delete `vercel.json` (or its `experimentalServices` block) and set the project's Framework Preset to Nuxt.js. The module generates the eve service and its routing on every Vercel build.
- **Hand-maintained.** Replace `experimentalServices` with the `services` and `rewrites` shown above, and keep the "Services" Framework Preset.
