title: "SvelteKit"
description: "Run an eve agent and a SvelteKit app as one project with the eveSvelteKit Vite plugin."
---

`eve/sveltekit` runs a SvelteKit frontend and an eve agent as one project. The `eveSvelteKit()` Vite plugin puts both on one dev server and one Vercel deploy. [`useEveAgent`](./use-eve-agent-svelte) finds the mounted routes on its own, so you configure no CORS or URL env vars.

## Prerequisites

- The `eve` package installed in your project (`npm install eve@latest`).
- An existing eve agent directory. If you don't have one, start from [Getting started](../../getting-started).
- A SvelteKit app to mount the agent in. To deploy on Vercel, use `@sveltejs/adapter-vercel` 6.3.5 or later, the first version that builds on Node.js 26.

## Register the Vite plugin

Add `eveSvelteKit()` before `sveltekit()`:

```ts title="vite.config.ts"
import { sveltekit } from "@sveltejs/kit/vite";
import { eveSvelteKit } from "eve/sveltekit";
import { defineConfig } from "vite";

export default defineConfig({
  plugins: [eveSvelteKit(), sveltekit()],
});
```

The plugin looks for an `agent/` folder in the SvelteKit project root, mounted at `/eve/v1/*`. An `agents/` workspace mounts each member at `/eve/<name>/v1/*` instead. Pass `eveRoot` when the agent lives elsewhere:

```ts
export default defineConfig({
  plugins: [
    eveSvelteKit({
      eveRoot: "../my-agent",
    }),
    sveltekit(),
  ],
});
```

The plugin accepts three options: `eveRoot`, `eveBuildCommand`, and `devServerTimeoutMs`, the maximum time to wait for the eve development server to start (default `180000`).

## Call the binding

With the plugin registered, components call [`useEveAgent`](./use-eve-agent-svelte) from `eve/svelte` and don't pass `baseUrl`:

```svelte
<script lang="ts">
  import { useEveAgent } from "eve/svelte";

  const agent = useEveAgent();
  let message = $state("");
  let isBusy = $derived(agent.status === "busy");
  let isInputDisabled = $derived(isBusy || agent.status === "resuming");

  async function handleSubmit() {
    const text = message.trim();
    if (!text || isInputDisabled) return;
    message = "";
    await agent.send(text);
  }
</script>

<form onsubmit={(event) => {
  event.preventDefault();
  void handleSubmit();
}}>
  <input bind:value={message} disabled={isInputDisabled} />
  <button type="submit" disabled={isInputDisabled}>Send</button>
</form>
```

The browser still needs a production authentication policy. See [Authenticate browser requests](/docs/guides/frontend#authenticate-browser-requests) for the default policy, which rejects unverified requests, and for channel configuration.

## Dev vs deploy topology

- **Local dev.** `npm run dev` starts an eve dev server for each agent and proxies its routes to it. The browser talks only to the SvelteKit origin. `npm run build && npm run preview` works the same way: the preview server proxies the eve routes. A server the plugin starts stops when the Vite server closes. Any tool that loads `vite.config.ts` in serve mode, such as Vitest, starts or reuses a server, so keep `eveSvelteKit()` out of a separate test config.
- **Vercel.** The SvelteKit app and the eve runtime deploy as a single project. On Vercel builds, the plugin adds an eve [service](https://vercel.com/docs/services) per agent and routes its transport requests to it before filesystem routing. The SvelteKit app serves everything else, and no `vercel.json` is required. By default, each generated service runs the installed eve binary from its agent root, so agent directories don't need their own `package.json`. When the agents need their own build step, set `eveBuildCommand`:

  ```ts
  export default defineConfig({
    plugins: [
      eveSvelteKit({
        eveBuildCommand: "npm run build:eve",
      }),
      sveltekit(),
    ],
  });
  ```

- **Non-Vercel hosts.** The Vite plugin only configures dev and preview. For production builds such as `adapter-node`, add the eve `handle` hook to proxy transport requests from the SvelteKit origin:

  ```ts title="src/hooks.server.ts"
  import { createEveHandle } from "eve/sveltekit";

  export const handle = createEveHandle();
  ```

  For a single `agent/`, the hook forwards `/eve/v1/**` to `http://127.0.0.1:4274`. Override the port with `EVE_SVELTEKIT_PRODUCTION_PORT`. Set `EVE_SVELTEKIT_PRODUCTION_ORIGIN` to use another host, or pass `origin` to override that variable. An origin override keeps public paths, including `/eve/<name>/v1/**` when one upstream host routes all agents.

  For an `agents/` workspace with separate servers, map each agent name to its server:

  ```ts title="src/hooks.server.ts"
  import { createEveHandle } from "eve/sveltekit";

  export const handle = createEveHandle({
    agents: {
      alice: "http://127.0.0.1:4274",
      bob: "http://127.0.0.1:4275",
    },
  });
  ```

  With `agents`, the hook forwards only the listed names and rewrites `/eve/<name>/v1/**` to each server's `/eve/v1/**`. The map takes precedence over `origin` and the environment variables. Other requests pass to SvelteKit. The deployed frontend needs no agent source files.

  Build and start each eve service yourself; the hook doesn't start backends. See [Self-host eve](../deployment/self-hosting) and [Run workspace members](../deployment/self-hosted-operations#run-workspace-members). The hook forwards only eve transport routes, not `/.well-known/workflow/**` callbacks; configure callback routing separately when your backend needs it. It streams request and response bodies and preserves cancellation, redirects, and cookies. Configure authentication on the eve services; the hook is not an authentication policy. Compose it with other hooks through SvelteKit's [`sequence`](https://svelte.dev/docs/kit/@sveltejs-kit-hooks#sequence).

  You don't need the hook on Vercel: service routing sends each agent's transport requests to its eve service before SvelteKit. The hook has no Vercel-specific bypass; any matching request that reaches it is forwarded.

  When the eve service instead runs on a public origin the browser calls directly, pass `baseUrl` to `useEveAgent` and handle CORS and authentication yourself:

  ```ts
  const agent = useEveAgent({
    baseUrl: "https://agent.example.com",
  });
  ```

## Managing vercel.json yourself

When `vercel.json` declares [`services`](https://vercel.com/docs/services), the plugin generates nothing, and your configuration controls routing. It must include an eve service (`framework: "eve"`) per agent and a rewrite that sends its requests to it, or the build fails. An `agents/` workspace needs one service per member, and a rewrite for `/eve/<name>/v1/*`:

```json title="vercel.json"
{
  "services": {
    "web": { "root": ".", "framework": "sveltekit" },
    "eve": { "root": "agent", "framework": "eve", "buildCommand": "eve build" }
  },
  "rewrites": [{ "source": "/eve/v1/(.*)", "destination": { "service": "eve" } }]
}
```

### Remove `experimentalServices`

Vercel doesn't route the `experimentalServices` field in `vercel.json`: both services build, but every `/eve/v1/*` request returns `NOT_FOUND`. The plugin ignores the field and warns that `vercel.json defines experimentalServices`. Remove it in one of two ways:

- **Generated (default).** Delete `vercel.json` (or its `experimentalServices` block) and set the project's Framework Preset to SvelteKit. The plugin generates the eve service and its routing on every Vercel build.
- **Hand-maintained.** Replace `experimentalServices` with the `services` and `rewrites` shown above, and keep the Services Framework Preset.
