description: "Run an eve agent and a Next.js app as one project with withEve."
---

`eve/next` connects a Next.js app to one or more eve agents. Wrap your Next.js config with `withEve(nextConfig)` to run the app and agents with one development command and deploy them as one Vercel project. Browser requests use same-origin routes, and each agent still runs as its own service.

Use this integration when the Next.js app runs and deploys the whole project. If the frontend and an agent workspace deploy as separate services, compose them with [`eve/vercel`](../deployment/vercel#compose-agents-with-other-vercel-services) on Vercel or your [self-hosted process manager and proxy](../deployment/self-hosting#run-workspace-members). A separately deployed frontend can use `eve/react` without `eve/next`. See [Project Structure](/docs/concepts/project-structure#configure-a-web-deployment) for the choice.

## Prerequisites

- The `eve` package installed in your project (`npm install eve@latest`).
- An existing eve agent directory. If you don't have one, start from [Getting Started](../../getting-started).
- A Next.js app, or an eve project where you want to generate one below.

## Add the generated Web Chat app

Install the generated Web Chat app from a standalone agent project, and choose **Next.js** when the installer asks which framework to use:

```bash
eve add channel/web
```

For an agent workspace, select the member the chat should call:

```bash
eve add channel/web --agent support
```

The installer adds a Next.js application under `apps/web`, or configures an existing root Web Chat app. With **Next.js** hosting, it wraps `next.config.ts` with `withEve()`. The chat uses same-origin `/eve/v1/*` routes for a standalone agent or `/eve/<name>/v1/*` for a workspace member. From a workspace root, the installer requires a selected member.

Before accepting production browser traffic, replace the generated placeholder authorization policy. See [Authenticate browser requests](./overview#authenticate-browser-requests).

To deploy the frontend and agents as separate Vercel services, choose **Vercel services** during setup instead. See the [workspace layout guidance](/docs/concepts/project-structure#configure-a-web-deployment). To integrate an existing Next.js application without generating a chat UI, follow the steps below.

## Wrap the Next.js config

```ts title="next.config.ts"
import type { NextConfig } from "next";
import { withEve } from "eve/next";

const nextConfig: NextConfig = {};

export default withEve(nextConfig);
```

By default `withEve(nextConfig)` looks for an `agent/` folder inside your Next.js project root and mounts its API at `/eve/v1/*`. When the project root is an eve workspace with `agents/<name>/` members, it discovers every member and mounts each at `/eve/<name>/v1/*`, without an explicit `agents` map.

If one agent lives somewhere else, point at it with `eveRoot`:

```ts
export default withEve(nextConfig, {
  eveRoot: "../my-agent",
});
```

## Mount agents outside a workspace

To mount agents that aren't members of the project-level `agents/` workspace, use `agents`. String values are agent roots; object values can override the build command or private production service prefix for that agent:

```ts
export default withEve(nextConfig, {
  agents: {
    support: "./apps/support-agent",
    billing: {
      root: "./apps/billing-agent",
      buildCommand: "pnpm build:billing-agent",
      servicePrefix: "/_eve_internal/billing",
    },
  },
});
```

Named agents mount under `/eve/<name>/v1/*`. Call the matching agent from React with `agent`:

```tsx
const support = useEveAgent({ agent: "support" });
const billing = useEveAgent({ agent: "billing" });
```

Use either `eveRoot` or `agents`, not both. `eveRoot` is the shorthand for a single unnamed agent mounted at `/eve/v1/*`.

Generated agent services build with `EVE_PUBLIC_ROUTE_PREFIX` set to the agent's public mount, such as `/eve/support`. OAuth connection callbacks and remote-subagent session callbacks then resolve to that public path. If you configure eve services manually in `vercel.json`, export that variable in each named agent's build command.

### `withEve` options

All fields are optional.

| Option               | Type                  | Default                  | Purpose                                                                                                                                                                                   |
| -------------------- | --------------------- | ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `eveRoot`            | `string`              | Next.js app root         | Eve project root, relative to the Next.js app root unless absolute. It may contain either one `agent/` or an `agents/` workspace. Do not combine with `agents`.                           |
| `agents`             | `Record<string, ...>` | inferred for a workspace | Named eve agents to mount under `/eve/<name>/v1/*`. Each value is a root string or `{ root, buildCommand?, servicePrefix? }`. Omit it and `eveRoot` to discover `agents/<name>/` members. |
| `eveBuildCommand`    | `string`              | generated                | Build command for generated eve Vercel services. In multi-agent mode this is the default for agents without their own `buildCommand`.                                                     |
| `servicePrefix`      | `string`              | `"/_eve_internal/eve"`   | Private route namespace for manual Vercel service configs and non-Vercel production proxying. Named agents derive unique defaults from this prefix.                                       |
| `devServerTimeoutMs` | `number`              | `180000`                 | Maximum time to wait for each eve development server to become available.                                                                                                                 |

When the Next.js app sits next to an eve project, point `eveRoot` at the project root instead of listing every agent path:

```ts title="apps/web/next.config.ts"
import type { NextConfig } from "next";
import { withEve } from "eve/next";

const nextConfig: NextConfig = {};

export default withEve(nextConfig, {
  eveRoot: "../..",
});
```

For slow cold starts, increase the development timeout:

```ts
export default withEve(nextConfig, {
  devServerTimeoutMs: 300_000,
});
```

## Call the hook

For a single unnamed agent, call [`useEveAgent`](./overview) without `agent` or `baseUrl`. For a named agent, discovered or configured, pass the name:

```tsx
"use client";

import { useEveAgent } from "eve/react";

export function SupportStatus() {
  const support = useEveAgent({ agent: "support" });
  return <p>{support.status}</p>;
}
```

See [Basic chat](./overview#basic-chat-react) for rendering messages and sending turns.

Bind each chat route to its agent. Include the agent name in session URLs so the UI doesn't restore a session through the wrong agent. Remount the chat component when switching agents, because the hook reads `agent` when it creates its store.

Requests are same-origin, so the browser sends application cookies to the agent. Each agent must verify them through its own channel authentication policy. For non-cookie schemes, attach the credentials yourself:

```tsx
const agent = useEveAgent({
  headers: async () => ({
    authorization: `Bearer ${await getAccessToken()}`,
  }),
});
```

Configure authorization for every exposed agent before accepting production browser traffic. See [Authenticate browser requests](./overview#authenticate-browser-requests) for the default policy, which rejects unverified requests, and for channel configuration.

## Use the generated Web Chat routes

`eve init --channel-web-nextjs` and `eve add channel/web` generate a chat UI that gives each session its own URL:

- `/` is the initial landing page.
- `/s` opens the conversation layout without creating an eve session. The first message creates the session.
- `/s/[sessionId]` attaches to that session, replays its transcript, and follows a turn that is still running.

After the first message is accepted, Web Chat replaces the browser URL with `/s/{sessionId}` without remounting the active stream. Reloading that URL passes the session to `useEveAgent` with `resume: true`, so completed history replays and an unfinished response keeps streaming. **New chat** navigates to `/s` without resetting or deleting the prior session, which stays available at its URL.

The generated UI keeps transcript scroll position in browser `sessionStorage`, not in the eve session.

For a custom Next.js chat route, pass the route session ID explicitly:

```tsx
const agent = useEveAgent({
  initialSession: { sessionId, streamIndex: 0 },
  resume: true,
});
```

See [Resumable sessions](./overview#resumable-sessions) for persistence and replay semantics.

## Dev vs deploy topology

- **Local dev.** `npm run dev` starts the eve dev server next to `next dev` and proxies the eve routes to it. The browser talks only to the Next.js origin.
- **Vercel.** The web app and the eve runtime deploy as a single project. `/eve/v1/**` requests reach the eve service before Next.js filesystem routes, and the Next.js app serves everything else. Authored [schedules](../../schedules) become Vercel Cron Jobs, prefixed for named agents, alongside the Next.js app's own cron entries. By default, generated services run the installed eve binary from the agent root, so the agent directory doesn't need its own `package.json`. When the agent needs its own build step, set `eveBuildCommand`:

  ```ts
  export default withEve(nextConfig, {
    eveBuildCommand: "npm run build:eve",
  });
  ```

- **Local production build.** `next build && next start` serves the eve runtime from its built `.output/server/index.mjs` on a stable local port (`4274`) and proxies the eve routes to it. Run `eve build` first so that output exists. In an `agents/` workspace, build every member from its `agents/<name>/` directory before starting Next.js. Change the port with `EVE_NEXT_PRODUCTION_PORT`:

  ```bash
  export EVE_NEXT_PRODUCTION_PORT=5000
  npm run build && npm start
  ```

- **Non-Vercel hosts.** `withEve()` starts the agent processes and provides the Next.js proxy rewrites, so you don't recreate the browser-facing routing. By default, `next start` runs each built eve service on its own loopback port. If your host supervises eve services itself, run each service separately. Then set `EVE_NEXT_PRODUCTION_ORIGIN` to the origin that serves its private route prefix:

  ```bash
  export EVE_NEXT_PRODUCTION_ORIGIN=https://agent.example.com
  npm run build && npm start
  ```

  This setting disables automatic production agent startup. The destination includes `servicePrefix`: for named agents, the default is `/_eve_internal/eve/<name>/eve/v1/*`. Configure that routing on the destination host, and use the same origin setting when building and starting Next.js.

  If the public routing layer mounts an agent below a path, set `EVE_PUBLIC_ROUTE_PREFIX` in that agent's build and runtime environments. Callback URLs then use the public path. Process restarts, persistent workflow storage, sandbox configuration, and workflow callback routing are your host's responsibility; see [Self-host eve](../deployment/self-hosting).
