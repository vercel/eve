Add lifecycle instrumentation as files under `agent/instrumentation/`. Each
file handles eve runtime events independently. Configure trace exporters and
shared span settings with the [built-in OpenTelemetry APIs](./otel).

The instrumentation directory replaces `agent/instrumentation.ts`. See
[Migrate instrumentation](/docs/observability/instrumentation-migration) when
upgrading from `eve < 0.62.0`.

## Add instrumentation

The filename identifies the instrumentation slot. A lifecycle-event file must
default-export `defineInstrumentation(...)` or `disableInstrumentation()`.
See [OpenTelemetry](./otel) for the supported OTel declarations.

```text
agent/instrumentation/
  audit.ts  lifecycle instrumentation
```

This instrumentation measures the time from a call being requested until it
settles, including any approval wait, without receiving arguments or results:

```ts title="agent/instrumentation/audit.ts"
import { defineInstrumentation } from "eve/instrumentation";

export default defineInstrumentation({
  events: {
    "call.requested": (event, ctx) => {
      ctx.state.set({ name: event.toolName, startedAt: Date.now() });
    },
    "call.settled": (event, ctx) => {
      const started = ctx.state.get() as { name: string; startedAt: number } | undefined;
      if (started === undefined) return;

      console.log({
        tool: started.name,
        durationMs: Date.now() - started.startedAt,
        outcome: event.outcome,
      });
    },
  },
});
```

`ctx.state` is JSON storage scoped to this file and operation. It survives
durable suspension and is released after the terminal event.

Use `setup` for asynchronous initialization. In `eve dev` and built servers,
eve awaits every provider's setup before loading the server entry. A setup
failure stops startup. Modules imported by an instrumentation file load before
setup, so keep dependencies that need initialization out of those imports.

## Control inputs and outputs

Each lifecycle file created with `defineInstrumentation(...)` has an
independent `tracePolicy`. It decides whether that file receives a trace and
whether its events include input or output content. OpenTelemetry destinations
share the process-wide policy declared by `otel(...)`.

```ts title="agent/instrumentation/audit.ts"
import { defineInstrumentation } from "eve/instrumentation";

export default defineInstrumentation({
  tracePolicy: ({ audience, environment }) => ({
    emit: true,
    recordInputs: audience === "public" || environment === "development",
    recordOutputs: audience === "public" || environment === "development",
  }),
  events: {
    "model.call.started": (event) => {
      console.log("input", event.input);
    },
    "model.call.settled": (event) => {
      if (event.outcome === "completed") console.log("output", event.content);
    },
  },
});
```

The function receives `agentName`, `channel`, `audience`, `environment`, and
`principalType`. `audience` is `"public"`, `"private"`, or
`"unknown"`; `environment` is `"development"`, `"preview"`, or
`"production"`.

Without a policy, or when it returns `true`, eve sends metadata for every
trace. It includes input and output content in these cases:

| Environment           | Audience               | Content            |
| --------------------- | ---------------------- | ------------------ |
| Development           | Any                    | Inputs and outputs |
| Preview or production | `public`               | Inputs and outputs |
| Preview or production | `private` or `unknown` | Metadata only      |

Return `{ emit: false }` to not sample the trace for this file. Return
`{ emit: true, recordInputs, recordOutputs }` to choose the two content
directions explicitly. Inputs include model prompts, tool arguments, call labels,
channel input, and user responses. Labels follow the input policy because they can contain
input-derived text. Outputs include model responses, tool results,
requests for user input, model provider metadata, and error details. Omitted
content fields are unavailable to the handler.

The channel assigns the audience once when it creates the session. It controls
content capture, not access. See [Audience](../channels/overview#audience) for
how the channel derives `public`, `private`, and `unknown`.

## Redact fields

Lifecycle events are immutable snapshots. Copy the fields you need into a
destination-specific payload and redact that copy before sending it:

```ts title="agent/instrumentation/audit.ts"
import { defineInstrumentation } from "eve/instrumentation";

export default defineInstrumentation({
  tracePolicy: () => ({
    emit: true,
    recordInputs: true,
    recordOutputs: false,
  }),
  events: {
    "call.requested": async (event) => {
      await sendAuditRecord({
        id: event.idempotencyKey,
        input: redactApiKey(event.input),
        kind: event.capability.kind,
        name: event.toolName,
      });
    },
  },
});

function redactApiKey(value: unknown): unknown {
  if (typeof value !== "object" || value === null || Array.isArray(value)) return value;

  const record = value as Record<string, unknown>;
  return "apiKey" in record ? { ...record, apiKey: "[redacted]" } : record;
}

async function sendAuditRecord(record: unknown): Promise<void> {
  // Send the sanitized record to your destination.
  void record;
}
```

Prefer `recordInputs: false` or `recordOutputs: false` when the destination does not need an entire content direction. Use field-level redaction only when the destination needs part of that content.

## Lifecycle events

Lifecycle events derived from session facts use the same names and outcomes as
the stream. For example, `turn.settled` carries the turn's `outcome`. Match an
operation's start and terminal events by their shared `idempotencyKey` when
upserting records across replays.

| Lifecycle        | Events                                                 | Meaning                                                                                                                                                                                                          |
| ---------------- | ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Session          | `session.started`, `session.ended`                     | Session creation and end. `session.ended.outcome` is `completed` or `failed`.                                                                                                                                    |
| Turn             | `turn.started`, `turn.settled`                         | Turn work. `outcome` is `completed`, `cancelled`, or `failed`; a cancelled turn is not a failure.                                                                                                                |
| Delivery         | `delivery.consumed`, `delivery.settled`                | The committed delivery facts. Settlement includes `outcome`: `handled`, `awaiting-input`, `applied`, `ignored`, `refused`, or `failed`. Channel metadata is on consumption when available.                       |
| Model run        | `model.started`, `model.retried`, `model.settled`      | Each attempt of a model run. `model.retried` ends a failed attempt before another try; `model.settled.outcome` is `completed`, `failed`, `interrupted`, `abandoned`, or `cancelled` when the turn was cancelled. |
| Provider call    | `model.call.started`, `model.call.settled`             | An individual provider call; one model attempt can make several. Settlement has `outcome: "completed"` or `"failed"`; completion carries usage, finish reason, and optional `providerMetadata`.                  |
| Call             | `call.requested`, `call.settled`                       | A tool, skill, or agent call, including direct `invokeTool` calls. `capability` identifies its kind and name. Settlement carries `completed`, `failed`, `rejected`, `interrupted`, or `abandoned`.               |
| User input       | `interaction.opened`, `interaction.settled`            | A question, approval, or budget prompt, keyed by `interactionId`. Settlement includes the interaction's `outcome` and, when recorded, its `answer`.                                                              |
| Memory operation | `memory.operation.started`, `memory.operation.settled` | A memory search or write, with operation name, phase, and slot. Settlement has `outcome: "completed"` or `"failed"`.                                                                                             |

A delivery that pauses for a person settles `awaiting-input`; resumed work belongs to the answer's delivery. OTel attributes a turn to a delivery only when exactly one delivery was consumed. Event `scope` includes session and run coordinates; `turnId` can be absent for compaction or direct calls. Treat `idempotencyKey` as opaque.

Use `InstrumentationEvent<"model.call.settled">` from `eve/instrumentation` when typing a
standalone handler. Model input content is `unknown`: the messages are the provider's request
messages, not an eve conversation-message schema. Narrow that content before reading it.

Each call emits one `call.*` lifecycle; SDK callbacks do not duplicate it. A subagent's `call.settled` includes its reported usage. A thrown tool error is reconstructed from the durable record, so don't use `instanceof` to classify it; inspect `error.name` instead.

When upgrading, use each operation's terminal event and inspect its `outcome` instead of subscribing to separate completion and failure events. See the [v27 event mapping](/docs/concepts/upgrade-to-v27-events#event-mapping). Provider metadata moved to `model.call.settled`. Replace step indices and encoded attempt IDs with `runId` and `attempt`; use `capability` for call kind and name. Channel types and `isChannel` now come from `eve/channels`. Runtime-context resolvers receive `run: { id, attempt }` instead of `step.index`.

The OpenTelemetry trace schema remains version 4: span names, attributes, and span events are unchanged.

Handlers from different files run concurrently and are failure-isolated. Do
not depend on execution order. Use `flush` to drain buffered records and
`shutdown` to release resources.
