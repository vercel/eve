Create a session with its first turn, then use the returned `ClientSession` for follow-ups. Each handle targets one durable session ID.

## Send text

Pass a string to `send()` for plain text:

```ts
import { Client } from "eve/client";

const client = new Client({ baseUrl: "http://127.0.0.1:2000" });
const { session, delivery } = await client.sessions.create({
  message: "What is the weather in Brooklyn?",
});

// Metadata is available as soon as the POST succeeds.
console.log(delivery.sessionId);

const result = await delivery.result();
console.log(result.status, result.reply);
```

`delivery.result()` reads through this delivery's settlement and returns a `DeliveryResult`.
Import `Delivery`, `DeliveryReadOptions`, and `DeliveryResult` from `eve/sessions`:

| Field          | Meaning                                                                                            |
| -------------- | -------------------------------------------------------------------------------------------------- |
| `reply`        | The request's reply text, from the parts `turn.settled.reply` lists.                               |
| `status`       | `awaiting-input`, `completed`, `failed`, or `cancelled` for this settled request.                  |
| `sessionEnded` | Whether the session ended in the delivery's final commit.                                          |
| `deliveryId`   | The accepted command's ID.                                                                         |
| `outcome`      | The delivery's outcome: `handled`, `awaiting-input`, `applied`, `ignored`, `refused`, or `failed`. |
| `error`        | Required `ErrorInfo` when `status` is `failed`.                                                    |
| `interactions` | Display-safe interactions left open for a person.                                                  |
| `sessionId`    | Session ID for streaming and inspection.                                                           |
| `data`         | Structured output when the turn requested an [output schema](./output-schema).                     |

A settled request's failure returns `status: "failed"` and `error`; inspect `error.code` and
`error.message` to recover. HTTP failures and reads interrupted before settlement throw rather
than fabricating a result. An `awaiting-input` result is complete: answering the prompt creates
another delivery. Ordinary results do not retain an event log; capture `delivery.stream()`
explicitly when you need one.

`session.send()` retries `409 session_not_ready` with bounded exponential backoff for up to 20
seconds when a durable run has been accepted but its command inbox is still starting. The caller's
abort signal cancels the wait. Other errors, `session.respond()`, control methods, and raw HTTP
requests do not use this retry. An unknown
or terminal session throws `SessionNotActiveError` immediately with `retryable: false`. A
`session_not_ready` rejection has `retryable: true` if the bounded send retry expires. A
[stranded](../../concepts/execution-model-and-durability#stranded-sessions) session throws
`ClientSessionStrandedError`, a `ClientError` with `code: "session_stranded"` and the
`eveVersion` that built the session when it recorded one. It is never retried automatically. Call
`session.reset()` and create a new session.
The client never creates a replacement session. Following or reconnecting to a stranded session's
stream reports the same typed error without retrying, including when you were waiting for a
response to a message accepted before the upgrade. That accepted message is not redelivered.
`session.clear()` throws the same error, because clearing would keep a session that cannot run.
`session.stream({ follow: false })` and `session.snapshot()` still read the recorded history.

## Send a full turn payload

Pass the full payload to `create()` for the first turn or `send()` for a follow-up:

```ts
const { session, delivery } = await client.sessions.create({
  message: "What should I do on this screen?",
  clientContext: {
    route: "/billing",
    plan: "pro",
    seatsUsed: 4,
  },
});

await delivery.result();
```

`clientContext` is ephemeral context for the current turn. Strings become user-role context messages, arrays of strings become multiple context messages, and objects are JSON-serialized into one context message. The context remains available to every model call in the turn, then disappears before the next turn. It isn't persisted to durable session history and doesn't dispatch a turn by itself.

## Send attachments

`send()` accepts `MessageContent`, so a message can mix text and file parts. A file part's `data` is the file inline (bytes, base64, or a `data:` URL) or a URL:

```ts
const response = await session.send([
  { type: "text", text: "Summarize this report." },
  {
    type: "file",
    data: reportDataUrl,
    mediaType: "application/pdf",
    filename: "report.pdf",
  },
]);

await response.result();
```

For local files, read the file and send a base64 `data:` URL:

```ts
import { readFile } from "node:fs/promises";

const bytes = await readFile("report.pdf");
const reportDataUrl = `data:application/pdf;base64,${bytes.toString("base64")}`;

const response = await session.send([
  { type: "text", text: "Summarize this report." },
  {
    type: "file",
    data: reportDataUrl,
    mediaType: "application/pdf",
    filename: "report.pdf",
  },
]);

await response.result();
```

The stream confirms the turn with `delivery.consumed`. Its `data.parts` contains structured text and
file metadata for clients that render attachments. File parts never include raw bytes or internal sandbox paths. See [Inbound
attachments](../../sandbox#inbound-attachments) for how eve stages byte-backed files in the session
sandbox and prepares them for each model call.

## Answer human input requests

Tools can pause for approval or ask the user a question. The stream emits one `interaction.opened` per request, and the response's result lists the open requests in `interactions`. Reply through the same session with `answers`:

```ts
const response = await session.send("Run the deployment checks.");
const { interactions: pendingRequests } = await response.result();

const resumed = await session.respond(
  pendingRequests.map((request) => ({
    interactionId: request.interactionId,
    optionId: "approve",
  })),
);

await resumed.result();
```

The reply's delivery records a `response.submitted` for each answer, and each request ends with `interaction.settled`: its `interactionId`, terminal `outcome`, and the `response` that decided it. Persist this authoritative event instead of relying on the submitting client's optimistic state when rebuilding message history.

`send(message, options)` and `respond(answers, options)` are separate operations. Put `clientContext`, `outputSchema`, headers, or stream options in the second argument to either method.

## Reusable delivery reads

Call `stream()` to observe progress, then `result()` for the summary:

```ts
for await (const event of response.stream()) {
  console.log(event.type);
}
const result = await response.result();
```

Each read follows the same interval, from the admitting commit through the complete settlement
commit, independently of other readers. Repeated or concurrent reads are supported; reading the
interval again can open another HTTP stream. A completed summary may be cached.

Pass `{ signal }` to `stream()` or `result()` to abort that read. An aborted or failed read does
not consume the handle or cancel the accepted work; retry the same delivery without submitting
another message. Use `session.cancel()` to cancel work. A signal passed to `send()` controls
submission, so pass it to the read too when a timeout must cover both.
