`ClientSession.send()` posts a message and returns a `Delivery` when the server accepts it. The receipt has its own `sessionId` and `deliveryId`; it does not wait for a reply. Call `result()` for its summary or `stream()` to observe it live. Both methods support independent, repeated reads. Import the shared delivery and reader contracts from `eve/sessions`.

Session controls return deliveries too. `session.cancel({ turnId })` targets an observed turn, so a late cancellation cannot stop unrelated later work. Omitting `turnId` cancels the current work. For example, cancel as soon as this message reaches a turn:

```ts
const { session, delivery } = await client.sessions.create({ message: "Run the long operation." });

for await (const event of delivery.stream()) {
  if (
    event.type === "delivery.consumed" &&
    event.data.deliveryId === delivery.deliveryId &&
    event.data.turnId !== undefined
  ) {
    const cancellation = await session.cancel({ turnId: event.data.turnId });
    await cancellation.result();
  }
}
```

The cancellation delivery settles when the command is applied, including a no-op for a turn that already ended. Continue reading the original message's delivery to observe its outcome and advance its cursor. A live idle session also accepts cancellation; it does not return a separate `no_active_turn` result.

Between turns, `session.compact()` queues context compaction without sending model input. `session.clear()` removes model-message history while retaining the session and its durable resources. Await their deliveries before sending another turn:

```ts
const compaction = await session.compact();
for await (const event of compaction.stream()) {
  if (event.type === "context.settled") console.log(event.data.outcome);
}
await compaction.result();

const cleared = await session.clear();
await cleared.result();
```

Observe `context.settled` while streaming to check whether summarization succeeded. A failed or empty summary preserves the previous history. `session.reset()` instead retires the session; its delivery settles after retirement and address release.

## Aggregate a turn

Use `result()` when you only need the final turn summary:

```ts
const response = await session.send("Summarize the latest forecast.");
const result = await response.result();

console.log(result.status);
console.log(result.reply);
console.log(result.outcome);
if (result.status === "failed") console.error(result.error.code, result.error.message);
```

This reads until the message's delivery settles (`delivery.settled` for its
`deliveryId`), finishing that line. A stream that ends without the accepted delivery's settlement
rejects the read, including when only a session terminal was observed. A delivery settles when the
turn that consumed it settles (`handled`), or when the turn pauses on an interaction
(`awaiting-input`), such as for an approval, question, or sign-in. See
[authorization pauses](#authorization-pauses).

A turn that waits on its [tasks](/docs/tools/workflows#run-calls-as-tasks-task) stays open:
`result()` keeps reading to its final reply. The text the model wrote before the wait is
narration, not the reply. When a call the turn runs asks a question, such as a workflow tool's
`ctx.ask()`, `result()` returns `status: "awaiting-input"` with the question in `interactions`. Answer it
with `respond()`, which keeps reading the same turn. A question stays pending until its
`interaction.settled`, which the session you answer on also emits for a subagent's or workflow
tool's question.

`result().status` describes the settled request: `awaiting-input`, `completed`, `failed`, or
`cancelled`. To inspect live progress, use `delivery(view, deliveryId)` and, when it has a `turnId`, `turn(view, turnId)` from `eve/events`.
A completed request can leave its session open. Read `result().sessionEnded` to check whether
the session itself ended, and `outcome` to distinguish an applied control from an ignored one.

Results do not collect an `events` array. To keep a request log, append events from
`response.stream()` to your own collection. You can still call `response.result()` afterward;
the reads do not share a consumption cursor.

`result()` closes that HTTP stream, including when fetch instrumentation clones
the response for tracing. The durable session remains available for follow-up
turns.

## Stream events live

Use `for await...of` when you want to render progress:

```ts
const response = await session.send("Draft a plan and show your work.");

for await (const event of response.stream()) {
  if (event.type === "content.delta") {
    process.stdout.write(event.data.delta);
  }

  if (event.type === "content.completed" && event.data.phase === "reply") {
    console.log("\nreply:", event.data.value);
  }
}
```

`content.delta` and `call.input` are progress records that carry only their new text. eve may merge adjacent deltas for the same part or call when the writer is busy; the text and ordering stay the same.

The default message reducer accumulates these for you. A raw stream consumer can apply the same rule directly, keyed by part:

```ts
const parts = new Map<string, string>();

for await (const event of response.stream()) {
  if (event.type !== "content.delta") continue;
  parts.set(event.data.partId, (parts.get(event.data.partId) ?? "") + event.data.delta);
}
```

After reconnecting without local state, replay the earlier lines or wait for the part's `content.completed`, which carries its whole value, instead of appending a later delta to an empty value.

The eve client validates the stream version on every connection and accepts version 27. A missing or different version fails instead of being read as current events.

## Handle event types

Import event types from `eve/client`, or the full catalog, the shared fold, and selectors from `eve/events`. Events read from a stream are `SessionStreamEvent`: a fact or progress record with its `meta` envelope.

```ts
import type { SessionStreamEvent } from "eve/client";
import { endsTurn } from "eve/client";

function handleEvent(event: SessionStreamEvent) {
  console.log(event.meta.position, event.meta.at);

  if (endsTurn(event)) {
    console.log("turn ended or paused on an interaction:", event.type);
  }
}
```

The most common UI events are:

| Event                 | Use                                                                                                                      |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `delivery.consumed`   | Confirm the user message landed; `data.parts` includes text and file metadata, and `data.history` any imported history.  |
| `content.delta`       | Render text and reasoning deltas as they stream.                                                                         |
| `content.completed`   | A finished part. `phase` tells a `"reply"` from `"narration"`; `kind: "result"` is [structured output](./output-schema). |
| `call.input`          | Accumulate raw tool-input deltas before validation completes.                                                            |
| `call.requested`      | Show tool calls as the model requests them, before execution.                                                            |
| `call.progress`       | Update a generator tool's provisional output snapshot.                                                                   |
| `call.settled`        | Show a call's result, error, or rejection.                                                                               |
| `task.started`        | Show a task; `kind: "agent"` marks agents. Its calls carry its `taskId` on `call.started`.                               |
| `interaction.opened`  | Pause the UI for an approval, question, budget prompt, or sign-in.                                                       |
| `interaction.settled` | Record how a request was decided.                                                                                        |
| `turn.settled`        | The turn ended: enable the composer.                                                                                     |
| `session.ended`       | Mark the conversation terminal or failed.                                                                                |

For the complete catalog, see [Sessions, runs & streaming](../../concepts/sessions-runs-and-streaming).

For `call.input`, the conversation's `tool` part reads `state: "streaming"` and accumulates the deltas in `inputText`, cumulative raw text that may be incomplete JSON. `call.requested` replaces it with the validated `input`.

A call to a tool that runs as a [task](/docs/tools/workflows#run-calls-as-tasks-task) starts with `call.started` carrying its `taskId` and settles later with its own `call.settled`. The model receives the result in its history.

File parts in `delivery.consumed.data.parts` never include raw bytes or internal sandbox paths; `url` appears only for `http(s)` URLs, and an inline file reports its `size` instead.

## Authorization pauses

A sign-in is an `interaction.opened` whose `request.kind` is `"sign-in"`. It means a connection needs OAuth or another authorization challenge before the paused turn can continue. Chat UIs should render the sign-in prompt from `request.signIn`, disable ordinary text input for that session, and persist the event with the rest of the chat history.

The sign-in holds the turn open, and the stream emits `turn.paused` awaiting it while the callback is pending. The current delivery settles with `status: "awaiting-input"`. Follow the session with `session.stream()` to observe the callback and the resumed work. If you support refresh while authorization is pending, save the session cursor and events, then rehydrate them on load. The callback or a structured decline resumes the same eve session.

## Reconnection

HTTP connections can end before a run does. The client reconnects from the next line it hasn't read, so long turns continue without replaying events. By default, a delivery keeps reconnecting until it settles or is aborted. Use a session stream to follow work beyond that delivery's settlement. A stream ends for good on `{"$eve":"stream.ended"}`, which the server sends once the session has ended.

Browser network failures use the same reconnect policy, both when opening a stream (`TypeError: Failed to fetch`, `TypeError: Load failed`, or `TypeError: NetworkError when attempting to fetch resource.`) and while reading a response body (any `TypeError`, such as `TypeError: network error`). Invalid stream events still fail the read.

If your consumer persists events, key on `event.meta.position`. It is stable across reconnects and rewinds, so an overlapping replay is safe to ingest twice. See [Positions](../../concepts/sessions-runs-and-streaming#positions).

Set `streamReconnectPolicy: { reconnect: false }` when a relay or proxy owns the cursor and reconnection policy. This makes a single stream GET attempt and returns when that connection ends; it does not stop the server-side turn:

```ts
const response = await session.send("Run the long operation.", {
  streamReconnectPolicy: { reconnect: false },
});

for await (const event of response.stream()) {
  console.log(event.type);
}
```

The same option is available on manual attachments as `session.stream({ streamReconnectPolicy: { reconnect: false } })`.

## Open a stream manually

Use `session.stream()` when you already have a session cursor and only need to attach to the existing stream:

```ts
const session = client.sessions.attach("wrun_01ARYZ6S41TSV4RRFFQ69G5FAV", {
  streamIndex: 10,
});

for await (const event of session.stream()) {
  console.log(event.type);
}
```

Pass `startIndex` to override the stored cursor:

```ts
for await (const event of session.stream({ startIndex: 0 })) {
  console.log(event.type);
}
```

Nonnegative values are line positions. Negative values read relative to the stream's current tail, so `-1` reads the latest line:

```ts
for await (const event of session.stream({ startIndex: -1 })) {
  console.log(event.type);
  break;
}
```

Tail-relative attachments do not automatically reconnect or advance the session's stored absolute `streamIndex`. Break after the event you need when using one as a tail lookup.

## Bounded catch-up reads

Pass `follow: false` to read from the cursor to the durable tail and then stop, instead of following the live stream (the default):

```ts
for await (const event of session.stream({ follow: false })) {
  console.log(event.type);
}
// Returns once every line recorded before the stream opened is consumed.
```

The first connection pins the bound to the tail the server reports at open time; events recorded afterward are not part of the read. Reconnects during the read keep that original bound, and the session's stored `streamIndex` still advances past the consumed events, so a follow-up `stream()` or `send()` picks up exactly where the bounded read ended. When the cursor is already at or past the tail, the iterator returns immediately without yielding.

Because a tail-relative cursor cannot be bounded, `follow: false` throws when combined with a negative `startIndex`. It also fails if the server does not report the durable tail (an agent running an older eve version).

## Snapshot a session

Use `snapshot()` when you need the complete event prefix and its matching cursor
as one value, such as when hydrating a server-rendered chat:

```ts
const session = client.sessions.attach(sessionId);
const snapshot = await session.snapshot();

// snapshot.events holds lines 0 through snapshot.session.streamIndex - 1.
```

The read pins the durable tail when it opens, just like
`stream({ follow: false })`. Events written afterward are not included, and
`snapshot.session.streamIndex` is the exact line from which a live consumer can
continue. `snapshot()` always reads from line `0`; use a bounded stream directly
when you only need the unread suffix from an existing cursor.

Unlike `stream()`, `snapshot()` does not advance the originating
`ClientSession`. Its returned cursor contains the fixed session ID and the exact
line after the captured prefix.

## Follow a subagent

A delegated subagent reports its progress on its own child session. The parent stream announces each child session with `child.opened`, whether the model called a subagent tool or a [workflow tool](/docs/tools/workflows#delegate-work-ctxagent) opened the session with `ctx.agent`. Pass the event to `agent()` on the parent's session handle to get the child's handle, then follow it with `stream()`:

```ts
import { endsTurn } from "eve/client";

const session = client.sessions.attach(parentSessionId);
const { events } = await session.snapshot();
const opened = events.find((event) => event.type === "child.opened");

if (opened?.type === "child.opened") {
  const child = session.agent(opened);
  for await (const event of child.stream()) {
    console.log(child.name, event.type);
    if (endsTurn(event)) break;
  }
}
```

Pass the received event, including its source position. The reader asks the parent's server to verify the opening at that committed line before returning child history. Cached events and their `stream` strings are not authority to access another session or destination.

- Local children are read only after verifying the recorded relationship on the same deployment.
- Remote children use the parent deployment's proxy and the remote agent's authored `auth` and `headers`. The browser never needs the remote URL or its credentials. Foreign redirects are not followed.

To read a deeper child, pass its received `child.opened` event to `child.agent(opened)`. Each hop verifies its own recorded relationship, including through remote proxies. Unsupported or unavailable relationships fail rather than attaching by ID. Paths are limited to eight hops.

The child has its own cursor, starting at `0`, and reading it never advances the parent's `streamIndex`. Pass `startIndex` to resume, `follow: false` for a bounded read, and `signal` to detach. A child parks after answering and can be continued later, so stop at a turn boundary with `endsTurn` when you only need the current turn. A parent follows only a child that speaks the current remote agent protocol; an earlier remote child's result still arrives, but its descendant reader reports unsupported history.

## Observe nested traces without a framework

Use `SessionStore` when you need projected nested conversations rather than managing readers yourself:

```ts
import { SessionStore } from "eve/client";

const store = new SessionStore({
  baseUrl: "https://agent.example.com",
  initialSession: { sessionId, streamIndex: 0 },
  followAgents: true,
  followWhile: () => false,
});
const stop = store.observe();
const unsubscribe = store.subscribe(() => {
  for (const child of Object.values(store.snapshot.agents)) {
    if (child.observation.status === "not-followed") continue;
    console.log(child.observation.key, child.observation.position, child.observation.caughtUp);
  }
});

try {
  await store.resume(); // Root catch-up only; descendants progress through subscriptions.
  await new Promise<void>((resolve) => setTimeout(resolve, 5_000)); // Bounded capture window.
} finally {
  unsubscribe();
  stop(); // Abort observation, not accepted execution.
}
```

Construction does not start reads. `observe()` activates a reference-counted scope and returns an idempotent cleanup function. Root streaming also activates child following; framework bindings activate and release scopes after mount. The store continues refreshing admitted children within an active scope even if `followWhile` closes the root stream. There is no full-tree catch-up barrier.

`followAgents: true` recursively follows all eligible recorded children within fixed depth, admission, and request limits. A predicate such as `({ depth }) => depth === 1` selects only immediate children. See [child observations](../frontend/overview#returned-state) for limits, states, and cursor semantics. Child conversations are whole-session views; their messages do not replace authoritative call results.

Stop the old scope and construct a new store when the principal or tenant changes. Token refresh callbacks resolve again for each request without changing observation identity. For a cross-origin browser connection, expose `x-eve-observation-key` in the channel's CORS configuration alongside the stream version and tail headers.

Archive projected messages and their per-node positions in an application-owned, versioned format. `SessionView` is opaque and is not a serialized archive format. Descendants can advance while the root position stays unchanged. A failed observation retains its last committed data; do not replace an existing archive with an empty failed read.

## Abort a request

Pass an `AbortSignal` to `send()` to abort submission, and to `stream()` or `result()` to abort a read. Aborting is local transport cancellation: turns are resumable across disconnects, so detaching never stops server-side work. Use `session.cancel()` to stop the active turn. Cancellation is asynchronous; watch the stream for `turn.settled` with `outcome: "cancelled"`.

Arm the timeout before awaiting `send()` so it covers the POST as well as the stream:

```ts
const controller = new AbortController();
const timeout = setTimeout(() => controller.abort(), 10_000);

const response = await session.send("Run a long analysis.", {
  signal: controller.signal,
});

for await (const event of response.stream({ signal: controller.signal })) {
  console.log(event.type);
}

clearTimeout(timeout);
```

An interrupted read does not consume the delivery. Call `response.stream()` or
`response.result()` again without the aborted signal to observe the same accepted work.
Aborting one read leaves concurrent readers running; do not send the message again merely to
resume observation.
