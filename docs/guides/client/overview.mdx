The `eve/client` entrypoint is the typed client for eve's default HTTP API. Use it from scripts, server-to-server integrations, tests, evals, backend jobs, or custom UIs that want the session protocol without hand-writing the POST and NDJSON (newline-delimited JSON) stream loop.

For browser chat UIs, start with [`useEveAgent`](../frontend/overview). For wire-level details, read [Sessions, runs & streaming](../../concepts/sessions-runs-and-streaming). The client sits between those two: lower level than the frontend hooks, higher level than raw HTTP.

## Create a client

A `Client` binds one base URL, auth policy, and header policy:

```ts
import { Client } from "eve/client";

const client = new Client({
  baseUrl: "http://127.0.0.1:2000",
});
```

`baseUrl` is the URL where the eve routes are mounted. In a same-origin browser integration this is often `""`; scripts and backend services usually name the full URL. Any query parameters on `baseUrl` are included on every request, including session POSTs and event streams. Request-specific parameters, such as a stream cursor, take precedence when names overlap.

## Check health

Use `health()` when a script needs to fail early before creating a session:

```ts
const health = await client.health();
console.log(health.status, health.workflowId);
```

The client requires the successful response to match `{ ok: true, status: "ready", workflowId: string }`. Non-2xx responses throw `ClientError`, which carries the HTTP `status` and response `body`; invalid JSON or a malformed successful payload throws `HealthResponseError`.

## Inspect an agent

Use `info()` to inspect an agent. The client requires a complete agent-info version 5 response before returning it:

```ts
const info = await client.info();
console.log(info.agent.name, info.agent.model.id);
```

Pass `info({ signal })` to cancel the HTTP request. The signal is checked only after custom header and credential callbacks resolve; it does not limit how long those callbacks or the complete `info()` call can take.

The response separates active static definitions from dynamic resolvers, includes binding-backed source ownership and composition history, reports first-class memory slots and their provider-tool wrapper dependencies, reports local and remote agents separately, and returns the exact compiled channel route order. It includes authored instruction content, skill and schedule markdown, and server paths, so the server answers only operator principals (`service`, `runtime`, or `local-dev`) unless the channel's auth grants `allowAgentInfo`. Authenticate the client with an operator credential, such as Vercel OIDC, `jwtHmac()`, `jwtEcdsa()`, or a custom `AuthFn` that returns `principalType: "service"`; any other principal gets a `ClientError` with `status` `403` and `code` `"info_forbidden"`.

The version changes only for breaking reshapes; a server adds fields and enum values within a version. The client ignores fields it does not know, and enum-like fields holding a string it cannot interpret (such as `mode`, `sourceKind`, or a channel `method`) read as `"unrecognized"`, so handle that value when you switch on them. A missing or non-string value still throws `AgentInfoResponseError`. `kind` discriminants, such as an owner's, a model endpoint's, or a module's backing `kind`, are closed: a new variant comes with a version bump, and an unknown one throws `AgentInfoResponseError`.

A non-success response throws `ClientError`. Invalid JSON, a different agent-info version, duplicate identities, inconsistent totals, or mismatched source provenance throws `AgentInfoResponseError`. For a version mismatch, its `issues` name which side to upgrade: eve in the agent, or the eve package the client runs from.

## Authentication

Pass `auth` when the [eve channel](../../channels/eve) route requires credentials:

```ts
const client = new Client({
  baseUrl: "https://agent.example.com",
  auth: {
    bearer: async () => await getAccessToken(),
  },
});
```

Bearer values and Basic auth passwords can be strings or functions. Functions run before every HTTP call, including stream reconnects:

```ts
const client = new Client({
  baseUrl: "https://agent.example.com",
  auth: {
    basic: {
      username: "agent-client",
      password: async () => await getRotatingSecret(),
    },
  },
});
```

For a Vercel OIDC-protected deployment, use `vercelOidc`. The client resolves the token once per request and sends it as both the bearer credential and Vercel's trusted-OIDC header:

```ts
import { getVercelOidcToken } from "@vercel/oidc";

const client = new Client({
  baseUrl: "https://agent.example.com",
  auth: {
    vercelOidc: {
      token: async () => await getVercelOidcToken(),
    },
  },
});
```

Use `headers` for route-specific credentials such as bypass tokens or tenant hints. Like `auth`, it can be static or dynamic:

```ts
const client = new Client({
  baseUrl: "https://agent.example.com",
  headers: async () => ({
    "x-vercel-protection-bypass": await getBypassToken(),
  }),
  redirect: "manual",
});
```

Clients reject redirects by default (`redirect: "error"`) so fetch cannot forward custom credentials to a redirected destination. Use `redirect: "manual"` to stop at a redirect without following it. Node.js exposes the response status and headers; browsers return an opaque redirect response with no readable status, headers, or body. The policy applies to inspection requests, custom fetches, session creation, and event streams, and overrides per-request redirect settings. Only opt into `redirect: "follow"` when you trust every possible redirect destination to receive your custom headers and request data.

Per-request headers can be attached to an individual turn:

```ts
const response = await session.send("Run the check.", {
  headers: { "x-request-id": requestId },
});

await response.result();
```

Per-request headers override client-level values with the same name. For example, a turn can set its application user's `Authorization` header while `vercelOidc` continues to send the deployment-protection credential in `x-vercel-trusted-oidc-idp-token`.

## Faster sends with `inbox`

Keep the complete `session.state` when saving and restoring a conversation. It can include an
opaque `inbox` value issued by the server. The client sends it back with later messages to avoid
another hook lookup. Persist it and pass it back unchanged: do
not inspect, edit, or construct it, because eve may change or extend its contents in any release.
A missing, stale, or rejected value only costs a slower lookup.

Set `EVE_INBOX_HANDLE_SECRET` to the same server-only random secret (at least 32 characters)
on the deployments that share sessions. Without this key, handles are neither issued nor used.
The signature authenticates all routing and encryption fields before use. Rotation falls back
to ordinary token resolution.

Reuse also requires a Workflow SDK with `parseHookResumeHandle`, an adapter that declares
`resolvedHookResume`, and a backend with the guarded resolved-hook endpoint.
Older SDKs do not issue or use handles, even when the secret
is configured. This change keeps the released SDK dependencies; adopting the SDK update
enables the optimization. Handles exclude user metadata, live capabilities, and trace carriers,
which may contain private server baggage. The signature authenticates a handle; it does not hide its contents.

The server checks that the handle addresses the requested session's inbox. Workflow still validates the
hook, persists the message, and wakes the workflow. A definite stale-owner rejection resolves
the current inbox again. An uncertain write is surfaced without submitting a second delivery.

## Sessions

Create and park an ID-addressed conversation before its first turn when you can start session work
while the user is still composing:

```ts
const { session } = await client.sessions.create();

const response = await session.send("Summarize account A.");
await response.result();
```

The create promise resolves when the server accepts the durable workflow. It does not open the
event stream or wait for initialization; an early `session.send()` uses the
same bounded startup retries as other follow-ups.

To create the session and start its first turn in one request, include the message:

```ts
const { session, delivery } = await client.sessions.create({ message: "Summarize account A." });
await delivery.result();

await (await session.send("Now list the risks.")).result();
await session.compact();
await session.clear();
```

If you already know the durable ID, attach a fixed handle without performing I/O:

```ts
const session = client.sessions.attach("wrun_A");
```

The fixed client handle exposes the full lifecycle around that ID. The calls below show the available shapes independently:

```ts
const response = await session.send("Continue the analysis.");
await response.result();

await session.cancel({ turnId: "turn_123" });
await session.compact();
await session.clear();

for await (const event of session.stream({ follow: false })) {
  console.log(event.type);
}

await session.end({ reason: "User requested a fresh session" });
```

`client.sessions` stores the session ID, stream cursor, and optional opaque `inbox` value. Every method calls an ID-addressed `/eve/v1/session/:sessionId/...` route. Sending through a handle for an unknown or terminal ID fails instead of creating a replacement, and `end()` leaves the handle pinned to the retired ID. Replace calls to the old `reset()` method with `end()`; use `client.sessions.create()` to start a different session. Upgrade the server before using a new client's `end()` method: earlier servers do not serve `/end`.

A client can own many independent fixed sessions at once:

```ts
const { session: alice, delivery: aliceDelivery } = await client.sessions.create({
  message: "Summarize account A.",
});
const { session: bob, delivery: bobDelivery } = await client.sessions.create({
  message: "Summarize account B.",
});

await Promise.all([aliceDelivery.result(), bobDelivery.result()]);
```
