An integration is a set of project files and dependencies, such as an extension, channel, or memory provider. `eve add` installs integrations from eve's official catalog, a third-party source, or a URL. Integrations use the [shadcn registry format](https://ui.shadcn.com/docs/registry).

## Install an integration

Run `eve add` from an eve agent project to install the integration's dependencies and write its files into your project.

```bash
eve add extension/agent-browser
eve add channel/linear
eve add instrumentation/braintrust
eve add memory/file
```

If an item isn't found, `eve add` prints close matches from the available catalogs without installing anything.

Web Chat installs a Next.js or TanStack Start application at `apps/web` for a standalone agent or a selected workspace member. The installer asks for the framework (`web-framework`), then the deployment. Non-interactive runs use Next.js unless you answer `web-framework="tanstack"`.

For the deployment, choose **Vercel services** (recommended) to deploy Web Chat and agents as separate services. Choose the framework (**Next.js** or **TanStack Start**) to serve Web Chat and route agent requests through one app. Vercel services run locally without a linked Vercel project. If you already have Next.js or Vercel configuration, eve stops with manual composition guidance instead of overwriting it. See [Project Structure](./concepts/project-structure) for browser-app placement, and [Next.js](./guides/frontend/nextjs) or [TanStack Start](./guides/frontend/tanstack) for framework-owned integration.

Run `eve add` without an argument to see how to search the registry with `eve registry search <query>`.

Each kind of integration writes files in its own directory:

- Extensions may create a mount under `agent/extensions/`, as `eve add eve/self-modification` does.
- Connections write a definition under `agent/connections/` and install `@vercel/connect` when required.
- Instrumentation integrations write one destination file under `agent/instrumentation/`, so you can configure several exporters independently.

Configure generated files and required environment variables before running your agent.

When an official item has interactive setup steps, eve asks whether to run them after installation. To resume a skipped or cancelled setup, run the printed `eve add <item> --skip-install` command, which reruns the setup from the beginning.

For example, setup for `eve add memory/file` creates or reuses a private Vercel Blob store, connects it to production, preview, and development, and offers to deploy. Before provisioning, it shows the project, store, region, environments, and possible Blob usage charges. See [File memory](./memory/file).

An official item may name optional pnpm dependencies that have build scripts. Before installation, eve asks whether to skip those packages, allow their build scripts, or abort. It records your choice in `ignoredOptionalDependencies` or `allowBuilds` in the owning pnpm workspace. Allow build scripts only when you trust the packages named in the prompt.

## Automate setup

Use `eve add <item> --non-interactive` when a script or coding agent cannot answer terminal prompts. It prints NDJSON events and exits with a status you can branch on:

| Exit code | Meaning                                         |
| --------- | ----------------------------------------------- |
| `0`       | Installation and setup completed.               |
| `1`       | Installation or setup failed.                   |
| `2`       | Setup needs an answer or an unmet prerequisite. |

On exit code `2`, read the final event and run its `next.command`. For a non-secret question, replace its `<JSON value>` placeholder with the answer you collected. Never pass a secret in `--answer`. Use the environment variable or secret store the integration documents instead. Add `--yes` to accept recommended values; explicit answers take precedence.

A setup may report `eve link` as a prerequisite. Run it, then retry the continuation. See [Deployment](./guides/deployment/vercel.mdx) for the non-interactive `eve link` and `eve deploy` forms.

## Find an integration

Browse the [Integrations directory](/integrations) to see the official integrations available from the eve registry.

List every official integration and configured third-party source:

```bash
eve registry list
```

Search the catalog by what an integration does. Omit `--limit` to return up to 10 matches, or set it between 1 and 100:

```bash
eve registry search browser --limit 5
```

Inspect an integration before you install it:

```bash
eve registry view extension/agent-browser
```

`list` includes the official eve catalog and every source you add to the project. `search` also includes [skills.sh](https://skills.sh), available as the built-in `@skills` source.

## Add a skill

Add a known [skills.sh](https://skills.sh) item directly:

```bash
eve add @skills/vercel-labs/agent-skills/vercel-react-best-practices
```

Skills from skills.sh are community-authored project files. Review their source and the resulting diff before you run your agent.

## Add a third-party source

Use the integration URL template provided by the registry publisher and give the source a namespace:

```bash
eve registry add @acme=https://registry.acme.com/r/{name}.json
```

eve stores the mapping in `package.json#registries`. The `{name}` placeholder becomes the integration name, so `@acme/analytics` resolves to `https://registry.acme.com/r/analytics.json`.

Limit listing or search to that registry when needed:

```bash
eve registry list --registry @acme
eve registry search analytics --registry @acme
```

Install an integration from that source:

```bash
eve add @acme/analytics
```

Install a known integration URL directly when you do not need a namespace:

```bash
eve add https://registry.acme.com/r/analytics.json
```

## Contribute an official integration

Open an issue and get maintainer agreement before you submit a pull request to the official registry. Then follow the [registry contribution guide](https://github.com/vercel/eve/blob/main/CONTRIBUTING.md#adding-an-integration-to-the-registry) for the required source files, metadata, validation, and extension requirements.

## Host your own registry

A hosted registry is what other eve projects add as a [third-party source](#add-a-third-party-source). It is a standard [shadcn registry](https://ui.shadcn.com/docs/registry), so any service that serves JSON over HTTP can host it. It needs two kinds of endpoint:

- A catalog such as `https://registry.acme.com/r/registry.json` for `eve registry list` and `eve registry search`
- One JSON document per integration, such as `https://registry.acme.com/r/analytics.json`, for `eve registry view` and `eve add`

Start with a source file for the integration and a `registry.json` that describes where to install it:

```text
registry.json
registry/
└── analytics.ts
```

```json title="registry.json"
{
  "$schema": "https://ui.shadcn.com/schema/registry.json",
  "name": "acme",
  "homepage": "https://registry.acme.com",
  "items": [
    {
      "name": "analytics",
      "type": "registry:item",
      "title": "Acme Analytics",
      "description": "Add Acme analytics tools to an eve agent.",
      "dependencies": ["@acme/eve-analytics"],
      "envVars": {
        "ACME_API_KEY": ""
      },
      "files": [
        {
          "path": "registry/analytics.ts",
          "type": "registry:file",
          "target": "agent/extensions/analytics.ts"
        }
      ]
    }
  ]
}
```

`files[].path` is relative to `registry.json`, and `files[].target` to the root of the installing eve project. Use `registry:item` with explicit `registry:file` targets so installation doesn't depend on a UI framework or shadcn project aliases.

Validate the source registry, then build its static JSON:

```bash
pnpm dlx shadcn@latest registry validate
pnpm dlx shadcn@latest build
```

The build writes the catalog to `public/r/registry.json` and each item to `public/r/<name>.json`. Deploy the `public` directory to a static host, or use the shadcn registry APIs to serve the same payloads from dynamic routes.

Before sharing the registry, test its deployed catalog and item endpoints from an eve project:

```bash
eve registry list --registry https://registry.acme.com/r/registry.json
eve registry view https://registry.acme.com/r/analytics.json
```

Share the item URL template with consumers, who add it as a third-party source:

```bash
eve registry add @acme=https://registry.acme.com/r/{name}.json
eve add @acme/analytics
```

## Configure generated files

Read the generated files before you run the agent. For an extension, this usually means setting environment variables and editing the mount under `agent/extensions/`. See [Extensions](./extensions) for mount configuration, namespacing, and overrides.

Provider-specific setup lives in the [Integrations directory](/integrations). Follow that guidance for credentials, approval policies, and service-specific options.

## Update an installed integration

Generated files are project code, so commit or review local changes before you install again. Run the same command to get the publisher's updated scaffold:

```bash
eve add extension/agent-browser
```

Pass `--overwrite` only when you intend to replace an existing generated file:

```bash
eve add extension/agent-browser --overwrite
```

Update the installed package with your package manager. Check the publisher's release notes before changing the generated mount or package version.

## Choose trusted sources

Integrations can add dependencies and write files. Add sources you trust, inspect an integration with `eve registry view`, and review the resulting project diff before you run the agent.
