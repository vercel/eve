Use a subagent to run independent work in parallel, narrow the available tools, or give a task to a specialist.

- Use the root-only [built-in `agent` tool](#the-built-in-agent-tool) to start or continue a copy of the root agent that shares its sandbox.
- Use a [declared local subagent](#declared-subagents) for a specialist with its own directory and authored capabilities, rather than inheriting the root's.
- Use a [remote agent](./guides/remote-agents) to delegate to a separately deployed eve agent, with its own configuration and authentication.

A subagent call is an ordinary tool call that eve runs as a [task](./concepts/tasks). The parent
turn waits for the subagent's answer, and the answer becomes the tool result. Several subagent calls
in one model step run in parallel, and the turn waits for all of them. In an interactive root
session, a new message can move waiting calls to the background; see
[Steering while a call waits](#steering-while-a-call-waits). The model can also run a call in the
background from the start; see [Run a call in the background](#run-a-call-in-the-background). If the child session expires, resets, or closes before replying, the
call fails with `AGENT_SESSION_ENDED` and reports the usage accumulated since the child's previous
answer. This applies to root-agent copies, declared local subagents, and remote subagents. The
subagent session remains available for later calls.

A subagent answers only when its session is quiescent. If the subagent calls a workflow tool
defined with `detach: true`, its turn can end while that task still works; the parent's call stays
open until the task reports, and the call's result is the reply the subagent gives in the result
turn that delivers the task's result. An interim reply never settles the call.

## Steering while a call waits

In an interactive root session, a root session in conversation mode, a steering message that
arrives while the turn waits on subagent calls moves those calls to the background so the agent can
answer the message. Each child keeps working. The model reads a receipt such as
`A new message arrived, so this call moved to the background as agent researcher-7k2m9q.`, and each
child's answer arrives later in a `task.result` message. Calls that one message moves deliver their
answers together, once every one of them has finished. The parent stream reports each moved call
with `task.detached`, and the call's `action.result` carries the receipt
`{ status: "working", taskId }`.

A message with `turnPolicy: "queue"` waits for the calls instead. In a subagent's own session, in a
task-mode run, and in a turn that a schedule started, a steering message is applied after the
waited calls return, in the same turn. Workflow tool calls in the same turn follow the same rules.
See [Detach a waited call](./concepts/tasks#detach-a-waited-call) for the full order.

## Run a call in the background

In an interactive root session, every agent tool accepts `background?: boolean`: the built-in
`agent`, declared and dynamic subagents, and remote agents. The model decides per call; there is no
author option. The parameter's description tells the model to use it only when the user does not
need the answer to continue, never to poll or call again to check on the agent, and to make calls
whose answers it needs together in the same step without `background`.

With `background: true`, the call starts the agent exactly like a waited call and returns a receipt
at once. The model reads:

```text
Agent researcher-7k2m9q is working in the background. Its result will arrive in a later message. Do not poll or repeat this work. Continue with anything that does not depend on it; if nothing remains, tell the user briefly what you started and end your turn.
```

Clients read the structured receipt on `action.result`: `output` is `{ status: "working", taskId }`,
and `task.started` reports `mode: "background"`. The agent's answer arrives later in its own
`task.result` message: an idle session starts a result turn, and a result waits for a turn from the
principal whose call started the agent. A background call's result is never held back for other
calls. Until its result arrives, the agent appears in the `<tasks>` block of the `[Tasks]` note. A
background agent call counts toward the 10 working background tasks a session holds, and a call over
the limit does not start and fails with `TOO_MANY_BACKGROUND_TASKS`. Passing the `agentId` of an
idle agent with `background: true` gives it new work in the background. See
[How results arrive](./concepts/tasks#how-results-arrive) for every delivery rule.

Only interactive root sessions offer the parameter. The decision is fixed when the session is
created, so the tool list does not change between turns, even when a later turn arrives with a
caller. A subagent's session and a task-mode run do not see it, and every agent call there waits. A
session that a schedule created offers it, but the turn the schedule started treats
`background: true` as a waited call, so a scheduled run posts one final reply; later turns in that
session can run calls in the background. The same rule applies to the turn that a message sent by a
schedule's handler starts in an existing interactive session, including when another message joins
that turn. A message sent from a later turn of a schedule-created session, such as by a tool, does
not count as a schedule's message. `ctx.agent` in a workflow body always waits.

`background` and detach cover different moments. `background: true` skips the wait when the model
makes the call. Detach moves calls that are already waiting to the background when a new message
arrives. Both deliver results the same way, and `task_cancel` stops either kind.

## The built-in `agent` tool

The root session receives `agent` by default. The model calls it to delegate a task to a new copy of the root agent or continue an existing copy:

```ts
{
  message: string;       // everything the child needs; it does not see the parent's history
  agentId?: string;      // give an idle child more work, or message a working one
  outputSchema?: object; // require structured output for this turn
  background?: boolean;  // interactive root sessions only
}
```

The copy uses the root's instructions, connections, auth, and sandbox. It receives the same tools except for the root-only `agent`, and starts with fresh conversation history and fresh state. Its file writes are immediately visible to the root. The built-in `agent` needs no configuration: each call waits for the copy's answer, which becomes the tool result, unless the model [runs it in the background](#run-a-call-in-the-background). Give parallel children non-overlapping write scopes.

`agent` is intentionally root-only. Copies created by it cannot call `agent`, and declared subagents never receive the built-in tool. If a stale or forced recursive call reaches execution, eve rejects it instead of starting another child session.

The parent transfers data to the child through the `message` input it gives the subagent. Do not include sensitive data in a subagent request unless that child and its inherited tools, connections, sandbox, and telemetry path are appropriate for that data.

To prevent the root session from delegating to a fresh copy of itself, set `tool: false` on the root agent:

```ts title="agent/agent.ts"
import { defineAgent } from "eve";

export default defineAgent({
  model: "anthropic/claude-opus-5.5",
  tool: false,
});
```

You can also export `disableTool()` from `agent/tools/agent.ts`. Any authored tool at that path replaces the model-facing framework tool and takes priority over `tool: false`; re-export `eve/tools/agent` to keep direct root-copy delegation. Tool composition does not change the callable-agent registry: a workflow in a top-level root session can still invoke the root copy with `ctx.agent("agent", ...)` and read its description from `ctx.agents.agent`.

## Declared subagents

A declared subagent lives under `agent/subagents/<id>/` and uses the same `defineAgent` helper as the root. Its location under `subagents/` is the only thing that marks it as a subagent. Declare one when the child needs a clearly different prompt, role, or tool surface.

```ts title="agent/subagents/researcher/agent.ts"
import { defineAgent } from "eve";

export default defineAgent({
  description: "Investigate ambiguous questions before the parent agent responds.",
  model: "anthropic/claude-opus-5.5",
});
```

`description` is required. The parent reads it to decide whether to delegate, so the compiler rejects any subagent whose `agent.ts` leaves it out. The path-derived invocation name `agent` is reserved for the built-in root-copy target; rename a declared subagent at `agent/subagents/agent/`. Namespaced names such as `crm__agent` do not collide and remain valid. Set `tool: false` to keep the subagent out of the parent model's tools while allowing an authored [workflow tool](/docs/tools/workflows) to call it by name through `ctx.agent()`:

```ts title="agent/subagents/researcher/agent.ts"
import { defineAgent } from "eve";

export default defineAgent({
  description: "Investigate ambiguous questions for the routing workflow.",
  model: "anthropic/claude-opus-5.5",
  tool: false,
});
```

The parent can alternatively export `disableTool()` from a same-named tool path, such as `agent/tools/researcher.ts`. This suppresses the derived model tool without removing `researcher` from the workflow invocation registry. A same-named authored tool replaces the model-facing surface while the workflow can still call the underlying subagent with `ctx.agent("researcher", ...)`.

Every declared local or remote subagent call waits for the child's answer, which becomes the tool result. Human input requests from a local or remote child surface on the parent session while the call waits; see [Remote agents](./guides/remote-agents#questions-approvals-and-sign-in) for a remote child.

A mounted extension can also contribute declared subagents from `extension/subagents/`. The mount namespace prefixes the subagent visible to the consuming agent node: mounting an extension as `crm` exposes its `reviewer` subagent as `crm__reviewer`. The contributed subagent keeps its own isolated tools, connections, skills, hooks, instructions, sandbox, and nested subagents, and its modules can read configuration from the extension handle. See [Extensions](./extensions#add-a-subagent) for the authoring and override behavior.

Local `eve dev` makes the bundled `self-modification__agent` subagent available by default. Bundled development extensions are not included in production builds. See [Self-Modification](/docs/guides/self-modification) for the local workflow.

### Vercel workspace peers

In a Vercel agent workspace, expose one other workspace member as a remote subagent with `defineWorkspaceAgent`. Create an ordinary file under the caller's `agent/subagents/` directory. Its filename gives the model-visible tool name; `name` identifies the peer under `agents/`.

```ts title="agents/foreman/agent/subagents/research.ts"
import { defineWorkspaceAgent } from "eve";

export default defineWorkspaceAgent({
  name: "research",
});
```

The helper uses the peer's root `defineAgent({ description })` value as the model-visible tool description. Pass `description` to override it for this caller. When `transport` is omitted, eve selects the built-in transport for the Vercel runtime environment. Local `vercel dev` routes workspace calls without deployment credentials; Vercel deployments route calls through the current deployment and authenticate with the caller's Vercel OIDC token. Named peers use their `/eve/<name>` mount. Outside those environments, provide an explicit transport with `url` and optional `auth` or `headers`:

```ts title="agents/foreman/agent/subagents/research.ts"
import { defineWorkspaceAgent } from "eve";
import { bearer } from "eve/agents/auth";

export default defineWorkspaceAgent({
  name: "research",
  transport: {
    url: () => process.env.RESEARCH_AGENT_URL!,
    auth: bearer(() => process.env.RESEARCH_AGENT_TOKEN!),
  },
});
```

An explicit transport replaces the environment default completely. The receiving peer must still accept the transport's credentials through its channel authentication policy. Set `forwardPrincipal: true` only when the peer trusts the caller to forward user identity, as described in [Remote agents](./guides/remote-agents#forward-the-callers-identity).

Use the peer's directory name under `agents/`. eve requires an exact workspace-member match, so add another declared subagent file for each additional peer. Run `vercel dev --local` with a root `vercel.ts` composed by `withEve` to start every member and enable the default local workspace transport. `eve dev` starts only the selected agent; use an explicit transport if it must call a separately running peer.

### Conditional availability

To expose a declared subagent only for certain sessions or turns, export
`defineDynamic` from that subagent's `agent.ts`. Return a `defineAgent`
configuration to expose the subagent, or `null` to omit it from the parent's tools.

```ts title="agent/subagents/researcher/agent.ts"
import { defineAgent, defineDynamic } from "eve";

export default defineDynamic({
  events: {
    "session.started": (_event, ctx) =>
      ctx.session.auth.current?.attributes.research === true
        ? defineAgent({
            description: "Investigate ambiguous questions before the parent responds.",
            model: "anthropic/claude-opus-5.5",
          })
        : null,
  },
});
```

Resolvers run at `session.started` or `turn.started`; `step.started` is not
supported for subagents. A nullish result (`null` or `undefined`) removes the
subagent's description and tool definition from the model-visible surface.
The subagent's filesystem manifest is always compiled; a non-nullish result injects
the returned agent configuration when the child runs.

Packaging controls must be available before the resolver runs. Put them on
`defineDynamic`, rather than the `defineAgent` returned by an event handler:

```ts
export default defineDynamic({
  build: { externalDependencies: ["native-package"] },
  events: {
    "session.started": () =>
      defineAgent({
        description: "Use a native package when handling delegated work.",
        model: "anthropic/claude-opus-5.5",
      }),
  },
});
```

The compiler applies `build.externalDependencies` while bundling every authored
module in that dynamic subagent.
See [Dynamic capabilities](./guides/dynamic-capabilities#dynamic-subagents) for
scope precedence, failure behavior, and the dispatch-time guard.

Minimum files:

```text
agent/subagents/researcher/
├── agent.ts            # required
├── instructions.md     # or instructions.ts, optional
├── tools/              # optional, its own tools
├── extensions/         # optional, mounted only into this subagent
├── skills/             # optional, its own skills
├── sandbox/            # optional, its own sandbox + workspace seed
└── subagents/          # optional, nested subagents
```

Extensions mounted under `subagents/<id>/extensions/` contribute only to that subagent. They use the same file and directory mount forms, namespacing, configuration, and overrides as root-agent extensions:

```ts title="agent/subagents/researcher/extensions/search.ts"
export { default } from "@acme/research-search";
```

The root agent does not receive the extension's tools, skills, instructions, connections, or hooks.

`schedules/` is not supported inside a declared subagent. Schedules are root-only.

## The isolation boundary

A declared subagent inherits nothing from the root's authored slots. Discovery treats its directory as its own agent root, so it has only the instructions, tools, connections, skills, sandbox, hooks, and nested subagents authored under `agent/subagents/<id>/`. For a slot with a framework default, eve selects that source when the subagent does not author a replacement; it never inherits the root's authored version.

| Slot         | Root built-in `agent` tool    | Declared subagent                      |
| ------------ | ----------------------------- | -------------------------------------- |
| Instructions | Inherited (copy of the agent) | Own `instructions.{md,ts}`, optional   |
| Tools        | Inherited except root-only    | Own `tools/`                           |
| Connections  | Inherited                     | Own `connections/`                     |
| Skills       | Inherited                     | Own `skills/`                          |
| Sandbox      | Reuses the parent sandbox     | Own `sandbox/`, else framework default |
| Hooks        | Inherited                     | Own `hooks/`                           |
| Extensions   | Inherited contributions       | Own `extensions/`                      |
| State        | Fresh                         | Fresh                                  |
| Channels     | Root-only                     | Root-only                              |
| Schedules    | Root-only                     | Root-only                              |

For a declared subagent this means authoring or mounting anything the child needs. When two subagents need the same procedure, package the skill in a [workspace extension](./extensions#use-an-extension-in-a-workspace) and mount that extension in each subagent. Share typed helpers through `lib/`. The sandbox does not inherit from the parent; eve selects the default sandbox source unless the subagent authors `subagents/<id>/sandbox.ts` or seeds files via `subagents/<id>/sandbox/workspace/`.

The root built-in `agent` tool is the exception. Its children reuse the root's sandbox and tools because they are copies of the same agent working on the same files.

`defineState` is never shared, for either kind. Each child starts with fresh durable state.

## What the parent sees

eve lowers every tool-enabled subagent visible to the current agent (the root built-in copy, declared, or [remote](./guides/remote-agents)) into a model-visible tool with the same `{ message, agentId?, outputSchema? }` shape, plus `background?` in interactive root sessions. The parent packs `message` with everything the child needs, since the child never sees the parent's history. Set `outputSchema` to require structured output for that turn; the child remains available for follow-up messages afterward.

Declared subagents can call nested subagents defined under their own directories. eve does not apply a separate depth limit; nesting ends where the authored directory tree ends. The built-in `agent` follows the stricter root-only rule above, so `limits.maxSubagentDepth` no longer exists.

Child sessions can still call their own declared or remote subagents, but they do not receive the built-in `agent`. Authored workflow tools use the same subagent availability and authorization checks as direct delegation. In a delegated root copy, `ctx.agents` also omits `agent`, so a router cannot select another root copy recursively.

A directly declared subagent's tool name is the bare path-derived name, with no prefix. `agent/subagents/researcher/` registers as the tool `researcher`. A subagent supplied by a mounted extension includes the mount namespace, such as `crm__reviewer`. The model, approvals, logs, and evals reference the resulting name. Its input schema is:

```ts
{
  message: string;       // all context the child needs; it never sees the parent's history
  agentId?: string;      // give an idle child more work, or message a working one
  outputSchema?: object; // require structured output for this turn
  background?: boolean;  // interactive root sessions only
}
```

By default, a subagent named `researcher` collides with an authored tool named `researcher`. Set the subagent's `tool` to `false` when the authored tool intentionally wraps that subagent; the authored tool becomes the model-facing capability while `ctx.agent("researcher", ...)` continues to address the child. A same-named `disableTool()` removes the model-facing capability entirely. Other static and active dynamic collisions remain errors.

Do not rely on subagent delegation by itself as an approval boundary. Put sensitive tools behind `approval`, connection approval, route/session authorization, or other controls wherever those tools can be called.

Each delegated subagent spins up its own child session and stream. The parent stream carries the control-plane events `task.started` and `task.settled` with `kind: "agent"`, plus interactive `input.requested`, `authorization.required`, and `authorization.completed` events proxied from descendants so the root channel can prompt the user. A proxied event carries the `taskId` of the child that asked. To follow the child's other progress, pass the `task.started` event to [`session.streamSubagent()`](./guides/client/streaming#follow-a-subagent) on a client session attached to the parent. It reads `task.started.data.child.streamPath`: the child's own session stream for a local child, or a parent-origin proxy for a remote child, which the parent authenticates to the remote deployment.

Every call that starts a task emits exactly one `task.settled` with its first outcome, identified by `taskId` and `callId`: `completed` with the actual `output`, `failed` with `error: { code, message }`, or `cancelled` when the parent cancels the call. The `taskId` is the agent ID that `agentId` continues, so each continuation emits another pair with the same `taskId`, and the child session can remain available for reuse after `task.settled`. A model call's tool result also appears on `action.result`. [Workflow tool](./tools/workflows#semantics) calls emit the same events with `kind: "workflow"` and no `child`. See [Task stream events](./concepts/tasks#task-stream-events) for every field, ordering rule, and error code.

Channels with activity reporting show the child's tool activity as a child item under the parent turn. Activity reporting is best-effort and does not change execution or result delivery.

Cancelling the parent turn cancels the child's current turn. If the child already replied but is holding its answer until its own background tasks report, the cancel reaches it anyway: the child cancels those tasks and confirms the cancel, so it stays available for another call. When the parent session ends, each child ends its own session and its own children; see [Cancel tasks](/docs/concepts/tasks#cancel-tasks).

Each delegated agent call has a time limit of 2 hours of active time by default. Time the child spends waiting on a question or approval that reaches the root channel does not count. A call still working at the limit fails: the parent's tool call gets an error with code `TIMED_OUT`, `task.settled` reports `failed` with the same error, and eve cancels the child's current turn. The child stays available for another call. If a local child has not stopped 30 seconds after eve cancels it, whether for a timeout or a parent cancel, eve terminates the child's session, and a later call with its `agentId` fails with `UNKNOWN_AGENT`.

Set `timeout` in a subagent's `agent.ts` to change the limit for calls to that subagent, in milliseconds. `false` removes the limit; the parent session's lifetime still bounds every call. On the root agent, `timeout` applies to calls of the built-in `agent` tool. For a [remote agent](./guides/remote-agents#how-remote-dispatch-and-callbacks-work), set `timeout` on `defineRemoteAgent`.

```ts title="agent/subagents/researcher/agent.ts"
import { defineAgent } from "eve";

export default defineAgent({
  description: "Investigate ambiguous questions before the parent agent responds.",
  model: "anthropic/claude-opus-5.5",
  timeout: 30 * 60_000, // 30 minutes of active time per call
});
```

Subagent model calls automatically retry classified transient provider failures, including overload errors delivered after a stream starts. eve makes at most three fresh model-call attempts, repeating only the current uncommitted call by default so completed earlier Workflow steps, tool results, and sandbox work remain available to the child. A declared subagent that opts into [Workflow checkpoint batching](./agent-config#workflow-checkpoint-batching) can instead repeat the uncommitted calls and inline tool executions in its current batch. Other recoverable task errors fall back to Workflow's durable step retry from the last committed session snapshot. Exhausting the transient model-call attempts or the dedicated empty-response reissue returns one failed task result instead of stacking both retry budgets; terminal errors fail immediately.

## Agent messaging

A child parks after answering instead of terminating, keeping its session and conversation history alive. A failed child turn can also leave the child parked — its latest status shows the error and the parent may message it again. Pass a parked child's `agentId` to the same subagent tool with a new `message` to continue that session. Omitting `agentId` (or passing an empty string or `null`) always starts a new child. An `agentId` that matches no agent in the session fails with `UNKNOWN_AGENT`, and passing an agent's id through a different subagent tool fails with `AGENT_MISMATCH`. Agent ids look like `researcher-7k2m9q`: the agent's name and six characters that eve assigns before the child starts.

Pass the `agentId` of a child that is still working to send it a message, such as a correction or an added requirement. The message joins the child's current call instead of starting a new one: eve publishes no new `task.started`, and the call returns at once with a receipt. For a background child, the model reads:

```text
Sent your message to agent researcher-7k2m9q, which is still working. Its result will arrive in a later message.
```

The child still delivers exactly one result for its current call, through that call: a background child's result arrives in a `task.result` message, and a waited call's result stays that call's tool result. The child receives the message as a steering message: in its current turn, or in its next turn for the same call when it is waiting on its own background tasks. A child that has not started yet receives the message when it starts; if eve cannot deliver it then, eve logs the failure, and the child's result does not reflect the message. The message does not change the output schema of the child's current call.

A child acts as the principal whose call started its current work, and its session holds that principal's conversation, so only that principal can give it more work or send it a message. A call from any other caller, such as another user in a shared thread, a schedule, or an app principal, fails with `AGENT_OTHER_PRINCIPAL`, whether the child is working or idle:

```text
Agent "researcher-7k2m9q" was started by a different caller, so it cannot take this message. Omit agentId to start a new agent.
```

Principals match by authenticator, principal type, and principal ID. Every unauthenticated caller is the same anonymous principal, so the check does not separate two anonymous callers. Stopping a child is not limited this way: any caller with access to the session can cancel it, as described in [Cancel tasks](./concepts/tasks#cancel-tasks). Anyone who can send to the session can also answer a child's question or approval; the child attributes the answer to whoever gave it and keeps acting as the principal that started it.

The `[Tasks]` note still lists every idle child in the session, including children another principal started. A model call that names a child whose current work a workflow body started with `ctx.agent` fails with `AGENT_BUSY`. Omit `agentId` to start a new child instead.

A child, local or remote, can reply just before a message reaches it. The child then runs the message as its next turn for the same call, and eve tracks that turn as the child's next background work: the parent stream reports another `task.started` with the same `taskId` and `mode: "background"`, and the turn's result arrives in a `task.result` message like any background result, so the model still receives a result that reflects its message.

Delivery failures are reported to the caller as `AGENT_UNREACHABLE`; eve does not start a replacement child session to hide them.

Whenever the set of parked (idle) children changes, eve appends a framework-injected note labeled `[Tasks]` to the conversation. Its `<idle_agents>` block lists each child's id, name, and a one-line summary of its last answer, most recent first, up to 10 children. Its `<tasks>` block lists each background task whose result has not reached history yet, with its status. The note is appended only when the listing changes (an append-only design that preserves the provider prompt cache), and the most recent note is authoritative. A child working in the background appears in `<tasks>`; a child working on a waited call does not appear until it parks again. See [The `[Tasks]` note](./concepts/tasks#the-tasks-note).

The parent keeps its children only for its session lifetime. When the parent session ends, eve asks each local child to end its session, which also ends that child's own tasks and children, and stops a local child outright if it is still running 30 seconds later while it was working or did not receive the request. eve sends authenticated reset requests for remote children. Remote reset is best-effort: an unreachable deployment may retain the parked child until its own session deadline. A [remote agent](./guides/remote-agents#upgrading-remote-agents) and the agent that calls it must use the same task protocol version.

## When to split

Split out a subagent when the task needs a different prompt or specialist role, a narrower tool surface, or its own runtime context. Don't reach for one when a [skill](./skills) would do. If the agent can keep its identity and needs only an optional procedure, a skill is the lighter choice.
