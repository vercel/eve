A workflow tool is a static tool defined with `defineWorkflowTool` from `eve/tools`, with
`"use workflow"` as the first statement of its executor. Each call starts a durable Workflow run. Use one when a tool must wait for a person, webhook, or timer,
delegate work to subagents, or coordinate retryable steps over a long period.

Each call runs as a [task](/docs/concepts/tasks), the model eve uses for both workflow tool calls
and agent calls. By default, a call is detached: it returns a receipt at once, the run keeps
working, and the model gets its result with `task_wait` or later in the same turn, which cannot end
while the run works. A tool defined with [`attached: true`](#hold-the-turn-with-attached) holds
the turn instead, and its result is the tool result. A tool defined with
[`resumable: true`](#take-more-input-with-resumable) keeps taking input by `taskId`. While the body
waits durably, the workflow holds no compute. See [Detached by default](#detached-by-default).

Workflow tools use the [Workflow SDK](https://workflow-sdk.dev): `"use workflow"`, `"use step"`, `createHook`,
`createWebhook`, `sleep`, retries, and replay. eve provides `ctx.ask` for questions answered through
the session's channel, `ctx.agents` for effective callable-agent descriptions, and `ctx.agent` for durable agent delegation. Use `yield` to report
progress and `await` on a workflow operation to wait durably. Values needed after a durable wait
stay in local variables in the workflow body.

A workflow tool runs code you wrote and appears to the model under its path-derived tool name, such
as `deploy`.

## Define a workflow tool

```ts title="agent/tools/deploy.ts"
import { defineWorkflowTool } from "eve/tools";
import { z } from "zod";
import { computePlan, runDeploy, type DeployPlan } from "../lib/deploy";

export default defineWorkflowTool({
  description: "Deploy a service to production. Pauses for a human to approve the plan.",
  inputSchema: z.object({ service: z.string() }),
  async execute({ service }, ctx) {
    "use workflow";
    const plan = await planDeploy(service);
    const answer = await ctx.ask({
      prompt: `Deploy ${service}?\n\n${plan.summary}`,
      display: "confirmation",
      options: [
        { id: "approve", label: "Deploy", style: "primary" },
        { id: "cancel", label: "Cancel" },
      ],
    });

    if (answer.status !== "answered" || answer.optionId !== "approve") {
      return { deployed: false, reason: "rejected" };
    }
    return { deployed: true, url: await applyDeploy(plan) };
  },
});

async function planDeploy(service: string) {
  "use step";
  return computePlan(service);
}

async function applyDeploy(plan: DeployPlan) {
  "use step";
  return runDeploy(plan);
}
```

The model calls `deploy`, which starts a task and returns a receipt. The turn stays open while the
person reads the plan. When they answer, minutes or days later, the run resumes, deploys, and
returns, and the model receives the result in the same turn.

### Rules

- Export `defineWorkflowTool({ ... })` as the default export. Its `execute` must be an async
  function or async generator, written inline or referenced as a top-level `async function` in
  the same module or an imported application module. Start the executor with `"use workflow"`
  as its first statement. A missing
  directive is a build error, even if another function in the module has one.
- `"use step"` marks a top-level `async function` in the tool module, or any module it imports, as a
  step. Side effects, clocks, randomness, `process.env`, and Node.js APIs belong in steps; the body
  is replayed and must stay deterministic.
- Import `createHook`, `createWebhook`, `sleep`, and `FatalError` from `workflow` in the body.
  `start`, `getRun`, and `resumeHook` from `workflow/api` belong in steps. Your app does not install
  the SDK; for types, new projects list `eve/workflow-modules` in the tsconfig `types`.
- In the body, `ctx` has `session`, `callId`, `toolName`, `abortSignal`, `agent`, `agents`, and `ask`,
  plus `receive` and `reply` for a [resumable](#take-more-input-with-resumable) tool.
  A `"use step"` helper that receives `ctx` directly gets a restricted `WorkflowStepToolContext` with
  `session`, `callId`, `toolName`, `abortSignal`, `getToken`, and `requireAuth`. Read `ctx.agents`, call
  `ctx.agent()`, and call `ctx.ask()` in the workflow body; pass only the serializable values the step needs.
  `getSandbox` remains unavailable.
- The tool's input must be a JSON object. Workflow bodies are for static tools under `agent/tools/`,
  not tools returned from `defineDynamic` resolvers.

`ctx.agent`, `ctx.agents`, and `ctx.ask` are available only on `WorkflowToolContext` in the workflow body.
Ordinary tools, channel handlers, schedule handlers, and workflow steps do not receive these methods. Type
step helpers with `WorkflowStepToolContext` from `eve/tools` when they need step-safe context capabilities.

Workflow executors require `defineWorkflowTool`. Adding `"use workflow"` to `defineTool`, a bare
tool object, a channel handler, or a schedule handler fails the build. To start a session from a
channel or schedule, use the [channel operations](/docs/channels/custom#channel-operations-and-session-handles)
or [schedule handler](/docs/schedules#handler-form-run) APIs.

Workflow imports resolve `paths` aliases from your application's `tsconfig.json` or
`jsconfig.json`, including when the application is a workspace package. eve includes only
workflow and step modules reachable from the agent's runtime modules. Unrelated workflows
in the host application stay outside the agent bundle. An unresolved workflow import fails
the build with the missing import in the error.

### Add a runtime-generated workflow tool

Create `agent/tools/workflow.ts` and export the provided `workflow` factory when the model should
supply the JavaScript program at runtime:

```ts title="agent/tools/workflow.ts"
import { workflow } from "eve/tools/workflow";

export default workflow({ maxSubagents: 20 });
```

The model supplies an async function body through the tool's `js` input. Its only host capability is
`ctx.agent(name, { message, taskId?, outputSchema? })`. This can invoke subagents configured with `tool: false` or hidden by a same-named `disableTool()` file. Include those path-derived names in the workflow tool description or agent instructions when the model writes the program. For example:

```js
const [triage, review] = await Promise.all([
  ctx.agent("ticket-triage", { message: JSON.stringify(tickets) }),
  ctx.agent("ticket-review", { message: JSON.stringify(tickets) }),
]);
return { triage, review };
```

`maxSubagents` defaults to `100` and must be an integer from `1` through `128`. The generated
program cannot access the workflow context, session state,
credentials, imports, or ordinary tools. Agent authorization, questions, approvals, cancellation,
and `taskId` continuation use the same owner-managed behavior as direct `ctx.agent` calls.

The sandbox resumes after every pending call in the current batch settles. `Promise.all` supports
fan-out followed by fan-in, but `Promise.race` does not resume after only the first child settles.
A child failure is thrown at the corresponding `ctx.agent` call, so generated code can catch it.
The program must return a JSON-serializable value.

### Migrate from `experimental_workflow`

The experimental uppercase `Workflow` framework tool and its exports have been removed. Replace the
old sentinel:

```diff
-import { experimental_workflow } from "eve/tools/workflow";
-
-export default experimental_workflow({ maxSubagents: 20 });
```

with the lowercase factory:

```ts
import { workflow } from "eve/tools/workflow";

export default workflow({ maxSubagents: 20 });
```

The path gives the authored tool the model-facing name `workflow`. eve does not discover or inject
an agent catalog. Calls use the same target resolution, availability, and authorization checks as
`ctx.agent` in any other authored workflow tool.

### Migrate an authored workflow tool

Replace `defineTool` with `defineWorkflowTool`, keep the executor's `"use workflow"` directive,
and replace `agent(ctx, input)` and `ask(ctx, request)` with `ctx.agent(target, input)` and
`ctx.ask(request)`. The `eve/workflow` entry point has been removed. Import `WorkflowToolContext`,
`AgentInput`, `ToolInputRequest`, and `ToolInputResponse` from `eve/tools` when you need explicit types.

### How suspension works

Suspension happens when a workflow must wait for an unresolved durable operation, such as
`ctx.ask`, an awaited hook or webhook, or `sleep`. The runtime persists the wait and releases the
workflow's compute. When the answer, event, or timer arrives, the runtime replays the workflow,
reuses recorded step results, and continues past the wait. Put side effects in `"use step"`
functions so replay does not repeat completed effects.

Consider a body that reports progress and then asks for approval:

```ts
async *execute(input, ctx) {
  "use workflow";
  yield { status: "awaiting approval" };
  const answer = await ctx.ask({ prompt: "Continue?", display: "confirmation" });
  return { answer };
}
```

The yield reports a snapshot, and eve advances the generator to `ctx.ask`. Awaiting the unanswered
request is the durable wait. The original tool call remains pending until the answer arrives and
the body returns. Answering resumes the body.

`yield` itself does not wait for approval. An ordinary
Promise or Node.js timer inside a step also does not create a durable workflow suspension; use
the workflow operations for waits that must survive a restart.

## Authorize inside a step

Pass `ctx` directly to a step helper and call `ctx.getToken(provider)` there. User-scoped providers
resolve as whoever launched this workflow tool, even if another person speaks in the session while it waits.
The provider declaration and the API request both stay inside the step:

```ts
import { connect } from "@vercel/connect/eve";
import type { WorkflowStepToolContext } from "eve/tools";

async function readRepository(ctx: WorkflowStepToolContext, repository: string) {
  "use step";
  const provider = connect("github/my-agent");
  const { token } = await ctx.getToken(provider);
  const response = await fetch(`https://api.github.com/repos/${repository}`, {
    headers: { Authorization: `Bearer ${token}` },
  });
  if (response.status === 401) ctx.requireAuth(provider);
  if (!response.ok) throw new Error(`GitHub returned ${response.status}`);
  return response.json();
}
```

Connections discovered through `connection_search`, ordinary tools, and workflow steps use the same
authorization machinery for requester identity, token caching, callback completion, and rejection
after sign-in. The execution runtime owns the wait: an agent returns to its model after authorization,
while a workflow retries the interrupted step and continues the authored body.

The workflow body calls `await readRepository(ctx, repository)`.

<Callout type="warning" title="Keep tokens out of step results">
  Step results enter the workflow's durable history, so do not return the token from the helper.
  eve's token cache stays inside the step. The step input is recorded too and, after sign-in,
  carries the provider's callback parameters, such as a one-time authorization code. This matches
  how agent turns record callbacks. Bearer tokens are never written.
</Callout>

When sign-in is required, the step attempt ends and the workflow waits on its own callback hook,
without holding compute. The channel renders the sign-in challenge. After the callback, eve retries
**the whole interrupted step**, resolves the token, and continues. Previously completed steps are
not rerun. Resolve auth before other side effects in that step, and make operations before
`requireAuth` safe to retry. A token rejected immediately after sign-in fails instead of prompting
again. Provider declarations can be shared imports, but context must be passed directly, not nested
inside another argument or captured in a closure.

After a successful callback exchange, eve records a completion marker before returning to authored
code. If that code later fails and the step retries, eve reads the token from the provider instead
of exchanging the same callback again. The provider must persist the grant or token; the marker
itself contains no credentials.

The tool call stays pending during sign-in, and the callback resumes the workflow. Cancelling an
authorization wait withdraws its callback. Cancellation uses the turn cancellation path rather than
a separate authorization completion event.

## Ask a human: `ctx.ask`

```ts
const answer = await ctx.ask({
  prompt: string,
  display?: "confirmation" | "select" | "text",
  options?: { id: string; label: string; description?: string; style?: "primary" | "danger" | "default" }[],
  allowFreeform?: boolean,
  dismissible?: boolean,
});
// | { status: "answered"; optionId?: string; text?: string }
// | { status: "dismissed" }
// | { status: "unavailable" }
```

`ctx.ask` publishes an `input.requested` event on the session — rendered the way channels render
tool approvals — and returns an awaitable answer. Awaiting it suspends the run until a response arrives.
The `ask_question` tool is a workflow tool built on `ctx.ask`.

The answer's `status` tells the body what happened:

- `answered`: the person picked an option (`optionId`) or typed a reply (`text`).
- `dismissed`: the request set `dismissible: true` and the person sent a message that did not answer
  it. The message reaches the agent as a normal turn.
- `unavailable`: the session cannot request input, such as a scheduled run. `ctx.ask` returns this
  immediately instead of waiting for an answer no one can give.

A plain follow-up message answers the request when it is the only pending question and the message
matches an option or the request allows free text, unless the session waits on an approval or
session-limit prompt of its own. A question a subagent asks counts as a pending question too, and
plain text answers it by the same rule.

`ctx.ask` composes with the SDK's own constructs; race it against a deadline:

```ts
const pending = ctx.ask({ prompt: `Deploy ${service}?`, options: APPROVE_OR_CANCEL });
const answer = await Promise.race([pending, sleep("4h")]);
if (answer === undefined) return { deployed: false, reason: "timed out" };
```

- The request belongs to the run, not the turn. It stays answerable until it is answered, dismissed,
  or the run ends.
- A request is answered once. Ask again for the next answer.
- Choose option `id`s that read well on their own, such as `approve` or the option's label. A
  response carries only the `id`. If a person answers after the request has already resolved, for
  example from an old Slack menu, the agent receives the `id` as a new message, not the label.
- Ending the run, by returning, throwing, or cancellation, withdraws its pending requests.
- Several requests may be outstanding at once.
- A response never steers. A new human message that does not answer a pending request follows the
  session's normal `turnPolicy`. A steering message from the turn's principal that answers nothing
  dismisses a `dismissible` request and cancels an [attached](#hold-the-turn-with-attached) call
  that waits on any other request. A detached call's requests stay pending and answerable; see
  [Steering during a turn](/docs/concepts/tasks#steering-during-a-turn).

Compare the [`approval`](/docs/human-in-the-loop) policy, which gates the call before `execute` runs
and can only show the model's input. Both compose: `approval` before the run, `ctx.ask` inside it.

## Delegate work: `ctx.agent`

Workflow tools can call a subagent and wait for its result:

```ts
const result = await ctx.agent("reviewer", {
  message: "Review the deployment plan for security risks.",
  outputSchema: {
    type: "object",
    properties: {
      findings: { type: "array", items: { type: "string" } },
    },
    required: ["findings"],
  },
});
```

The first argument is an available agent target. On the root agent, `"agent"` starts or continues a copy of the root agent. A declared subagent uses its path-derived name and remains callable when hidden with `tool: false` or `disableTool()`. Delegated root copies and declared subagent contexts do not expose the built-in root-copy target. The invocation name `agent` is reserved, so a declared subagent cannot shadow it. eve assigns each call a replay-stable invocation identity, including repeated and parallel calls to the same target. Pass `taskId` to
continue an idle agent this session started, such as one the `[Tasks]` note lists. A workflow body
awaits the agent's own answer, so a `taskId` that names an agent still working fails with
`TASK_BUSY`, and `ctx.agent` is never detached. For the same reason, while a `ctx.agent` call is
working, a model send to that agent's task fails with `TASK_BUSY`. A `ctx.agent` call made after
its generation stopped owning work, because it was cancelled, timed out, or already replied, fails
with `TASK_NOT_WORKING`. An inline
`outputSchema` requires structured output and determines the
return type, so `result` in the example is typed as `{ findings: string[] }`.

Pass a `signal` as the third argument to stop a call early. Aborting it cancels the call's task
through the normal cancel path, and the call rejects with the signal's reason:

```ts
const controller = new AbortController();
const review = ctx.agent("reviewer", { message }, { signal: controller.signal });
```

Work never outlives the generation that started it. When a call to the tool ends, by returning or,
for a resumable tool, by `ctx.reply`, eve first cancels every agent task the call still owns, such
as a `ctx.agent` call the body never awaited. A body can therefore bound an agent call with
`Promise.race` against `sleep` and return without cleaning up.

### Route to a hidden subagent with Jev

Use an authored workflow tool when the parent model should decide to delegate, but [Jev](https://vercel.com/i/what-is-jev) should choose the specialist. Set `tool: false` on each specialist so the parent model sees only the routing tool. The specialists remain available through `ctx.agents` and callable through `ctx.agent()`.

If the router may select the root-copy `agent`, author a root `description` that explains which work should stay with a copy of the root. `ctx.agents.agent` always exists in a top-level root workflow, but its `description` is an empty string when omitted from `agent.ts`. `agentRouter()` considers only entries with a non-empty description, so it does not route to an undescribed root copy.

```ts title="agent/agent.ts"
import { defineAgent } from "eve";

export default defineAgent({
  description: "Coordinate cross-specialist tasks that need the root agent's complete toolset.",
  model: "anthropic/claude-opus-5.5",
});
```

```ts title="agent/subagents/researcher/agent.ts"
import { defineAgent } from "eve";

export default defineAgent({
  description: "Investigation, analysis, and explanation",
  model: "anthropic/claude-opus-5.5",
  tool: false,
});
```

```ts title="agent/subagents/operator/agent.ts"
import { defineAgent } from "eve";

export default defineAgent({
  description: "Execution and operational changes",
  model: "openai/gpt-6-sol",
  tool: false,
});
```

Define the model-visible router under `agent/tools/`. Build the Jev criteria from the subagents' effective descriptions, then pass its typed choice directly to `ctx.agent()`:

```ts title="agent/tools/agent-router.ts"
import { evaluate } from "eve/ai";
import { defineWorkflowTool } from "eve/tools";
import { z } from "zod";

async function chooseTarget(
  task: string,
  criteria: Record<"researcher" | "operator", string>,
  abortSignal: AbortSignal,
) {
  "use step";

  const result = await evaluate({
    abortSignal,
    state: { task },
    questions: {
      route: {
        type: "choice",
        instructions: "Which specialist should handle this task?",
        criteria,
      },
    },
  });

  return result.answers.route.choice;
}

export default defineWorkflowTool({
  description: "Route a task to the appropriate specialist.",
  inputSchema: z.object({ task: z.string().min(1).max(8000) }),
  async execute({ task }, ctx) {
    "use workflow";

    const target = await chooseTarget(
      task,
      {
        researcher: ctx.agents.researcher.description,
        operator: ctx.agents.operator.description,
      },
      ctx.abortSignal,
    );

    return ctx.agent(target, { message: task });
  },
});
```

The evaluation runs in a step so workflow replay records its result instead of making the routing request again. The parent model receives `agent-router`, but not `researcher` or `operator`. Jev returns the typed `"researcher" | "operator"` choice, and the selected subagent's result becomes the result of the `agent-router` call.

`ctx.agents` is a replay-stable metadata snapshot taken when the workflow starts. In a top-level root workflow, `ctx.agents.agent` always represents the root-copy target and carries the root's authored `description` when provided. The snapshot also includes declared agents hidden from the parent model with `tool: false` or `disableTool()`, but exposes no model definitions, credentials, or callbacks. A delegated root copy omits `agent`, so `agentRouter()` cannot select another root copy recursively. Invocation still checks each target's availability through `ctx.agent()`.

#### Route across every agent target

To replace the model-facing `agent` tool with a router across every target in `ctx.agents`, export `agentRouter()` from the `agent` slot:

```ts title="agent/tools/agent.ts"
import { agentRouter } from "eve/tools/agent-router";

export default agentRouter();
```

Its input is `{ message: string, outputSchema?: object }`. `agentRouter()` ignores entries without a non-empty description. With two or more described targets, it sends the message and effective descriptions to Jev, then invokes the selected name through `ctx.agent()`. It invokes a sole target without evaluation and forwards an optional `outputSchema` unchanged. In a top-level root session, the candidates include the root-copy `agent`; delegated root copies and declared subagent contexts include only their declared targets.

When an authored tool accepts a JSON Schema supplied by the model, represent that input with a permissive object such as `z.looseObject({})`. Avoid `z.record(z.string(), z.json())`: its generated JSON Schema uses `propertyNames`, which OpenAI does not support. Validate the supplied value at the point where your tool consumes it.

This pattern controls specialist selection, not whether the parent model delegates at all. Route before the parent model runs if every incoming request must go through Jev.

## Report progress: `yield`

A workflow body may be an async generator. Yields report progress. After processing a yield, eve
advances the generator; use an awaited workflow operation when the body needs to suspend.

| Operation       | Effect                                                            |
| --------------- | ----------------------------------------------------------------- |
| `yield value`   | Emits an `action.partial` snapshot for the pending tool call.     |
| `return value`  | Settles the call with its output, the task's result.              |
| No return value | Uses the last yield as output, or `null` if there were no yields. |

An explicit `return null` also falls back to the last yield. Prefer an
explicit object return when progress snapshots and the final result have different shapes.
Progress snapshots are last-write-wins by tool call id and do not enter model history as
intermediate tool results. A snapshot used as the final output does enter history as the result.

This workflow reports progress, then suspends until its timer expires:

```ts title="agent/tools/remind_with_progress.ts"
import { defineWorkflowTool } from "eve/tools";
import { sleep } from "workflow";
import { z } from "zod";

export default defineWorkflowTool({
  description: "Wait, then return a reminder.",
  inputSchema: z.object({ note: z.string(), delay: z.string() }),
  async *execute({ note, delay }) {
    "use workflow";
    yield { status: "waiting" }; // Published as progress for the pending tool call.
    await sleep(delay); // Durable suspension while the timer is pending.
    return { reminder: note }; // The task's result.
  },
});
```

Use [`ctx.ask`](#ask-a-human-ctxask) when the workflow needs a human answer. See
[yield and return](/docs/tools#yield-and-return) for the final-output rules.

## Detached by default

A workflow tool call is detached unless the tool sets `attached: true`. The call returns a receipt at
once, the run keeps working, and a new message never stops it. Clients read the structured receipt on
`action.result` as `output: { status: "working", taskId }`, and the model reads
`Started task remind-q4x1ze. Use task_wait for its result.` The task starts with
`mode: "detached"` on `task.started`.

```ts title="agent/tools/remind.ts"
import { defineWorkflowTool } from "eve/tools";
import { sleep } from "workflow";
import { z } from "zod";

export default defineWorkflowTool({
  description: "Remind the user after a delay.",
  inputSchema: z.object({ note: z.string(), delay: z.string() }),
  async execute({ note, delay }) {
    "use workflow";
    await sleep(delay);
    return { reminder: note }; // The task's result.
  },
  toModelOutput(output) {
    return { type: "text", value: `Reminder: ${output.reminder}` };
  },
});
```

The model gets the result in one of two ways, both in the turn that made the call:

- It waits with `task_wait`, which returns the result as its tool result. A `timeout` bounds the
  wait, not the run, so a usually quick but sometimes long tool, such as a test run, stays detached
  and the model waits with `task_wait({ taskId, timeout: 120_000 })`.
- It continues without waiting. The result arrives in a user-role message of kind `task.result` at
  the turn's next tool step, or when the model tries to end the turn: a turn cannot end while tasks
  it started are working, so eve holds it until they settle.

Either way, the model reads the result as a `<task_result>` block:

```text
<task_result id="remind-q4x1ze" tool="remind" status="completed">
Reminder: stand-up at 10
</task_result>
```

The block body is the definition's `toModelOutput(output)` when it has one, and the output
otherwise. A failed task carries `status="failed"`, a `code` attribute, and the error message. No
result starts a turn of its own, and a result never appears in another principal's turn. Until the
result arrives, the task is listed in the `[Tasks]` note. See
[How results arrive](/docs/concepts/tasks#how-results-arrive) for every delivery rule.

A detached run's questions and approvals survive other messages: they stay pending, the task shows
`input_required`, and the turn stays open until someone answers or the task is cancelled. A
session holds at most 20 working tasks, and a call over that limit does not start: it fails with
`TOO_MANY_TASKS`. Yields publish `action.partial` for the call and never reach the model. The model
stops a task with [`task_cancel`](/docs/concepts/built-in-tools#task_cancel), and
`session.cancel()` stops every working task; the run then unwinds as described in
[Cancel and clean up](#cancel-and-clean-up-ctxabortsignal).

## Hold the turn with `attached`

Set `attached: true` when a call's result only matters to the turn that asked for it, such as a
quick lookup. The turn waits for the call, its result is the tool result, and a steering message
from the turn's principal cancels the call. eve's `sleep` and `ask_question` tools are attached.

```ts title="agent/tools/lookup_order.ts"
import { defineWorkflowTool } from "eve/tools";
import { z } from "zod";
import { findOrder } from "../lib/orders";

export default defineWorkflowTool({
  description: "Look up an order by ID.",
  inputSchema: z.object({ orderId: z.string() }),
  attached: true,
  async execute({ orderId }) {
    "use workflow";
    return await findOrder(orderId); // A "use step" helper.
  },
});
```

When a steering message arrives, eve first lets it answer a pending question that it matches, then
resolves questions created with `dismissible: true` as `dismissed`, and gives their calls 10 seconds
to return. Every attached call still running is then cancelled through the normal cancel path, and
its tool result reads `Stopped after 12 s because a new message arrived.` A message with
`turnPolicy: "queue"` waits instead. See
[Steering during a turn](/docs/concepts/tasks#steering-during-a-turn).

Suspension does not decide attachment. A tool that waits on an approval, such as `deploy` above,
should stay detached: an attached call's approval is not dismissible, so the next unrelated message
would cancel it.

## Take more input with `resumable`

Set `resumable: true` when a task should take more input after it starts, such as a draft to
revise or a stateful browser session. The model sends input by calling the tool again with the
task's `taskId`; eve adds `taskId` to the tool's input schema and a sentence about it to the tool's
description, and validates each send with the tool's own `inputSchema`. `resumable` cannot be
combined with `attached: true`, because a resumable task stays available across turns; the build
fails if a tool sets both.

A resumable body gets two more methods on `ctx`:

- `ctx.receive()` returns the next input sent with this task's `taskId`, typed by `inputSchema`.
  Input the body does not read waits for its next `ctx.receive()`. Racing `ctx.receive()` against
  the current work takes a correction into that work.
- `ctx.reply(output)` settles the current piece of work, a generation, with its one result, typed
  like the tool's output. `outputSchema` and `toModelOutput` apply to each result. A second reply
  before the next input throws. After replying, the task is idle until input arrives, and
  `ctx.receive()` then starts the next generation.

```ts title="agent/tools/release_notes.ts"
import { defineWorkflowTool } from "eve/tools";
import { z } from "zod";
import { draftNotes, reviseNotes } from "../lib/notes";

export default defineWorkflowTool({
  description: "Draft release notes, then revise them on request.",
  inputSchema: z.object({ request: z.string() }),
  resumable: true,
  async execute(input, ctx) {
    "use workflow";
    let notes = await draftNotes(input.request); // A "use step" helper.
    for (;;) {
      ctx.reply(notes); // This generation's one result.
      input = await ctx.receive(); // Idle until the model calls the tool again with taskId.
      notes = await reviseNotes(notes, input.request);
    }
  },
});
```

Returning from `execute` ends the task. The return value is the result of a generation that has not
replied; after a reply, end the body with a bare `return`, because a returned value is ignored.
Once the task ends, a send to its `taskId` fails with `UNKNOWN_TASK`. A send the body never read
still gets the generation it would have started, which fails at once with `EXECUTION_FAILED`, so
every send gets one result.

A send to an idle task starts its next generation. A send to a working task reaches the body through
`ctx.receive()` if the body reads while it works; otherwise the current generation ends with its own
result and the next starts right away with the send. `ctx.callId`, `ctx.session.turn`,
`ctx.abortSignal`, and `ctx.ask` follow the send that started the current generation. Yields
publish progress for that call.

Replying ends the generation, so eve first cancels the tasks it still owns, such as a `ctx.agent`
call the body never awaited. Between a reply and the next `ctx.receive()`, no generation is running,
so `ctx.agent` and `ctx.ask` throw.

Cancelling a resumable task, with `task_cancel` or `session.cancel()`, stops its current generation
and every send queued for it: `ctx.abortSignal` aborts, and the generation settles as `cancelled`.
The body then decides. Returning or throwing ends the task. Calling `ctx.receive()` leaves the task
idle, and only input sent after the cancel reaches it, so the cancelled work's late `ctx.reply`
never settles the next generation. An idle run is parked on its hook and holds no compute; it lives
as long as its session unless the session's idle limit of 50 retires it, and a send reaches it on
the deployment that started it.

## Limit a call with `timeout`

A workflow tool call has no time limit of its own; the session's lifetime bounds it. Set `timeout`,
in milliseconds, to fail a call that runs longer:

```ts title="agent/tools/run_tests.ts"
import { defineWorkflowTool } from "eve/tools";
import { z } from "zod";

export default defineWorkflowTool({
  description: "Run the test suite in the sandbox.",
  inputSchema: z.object({ filter: z.string().optional() }),
  timeout: 20 * 60_000,
  async execute(input, ctx) {
    "use workflow";
    return await runTests(input, ctx); // A "use step" helper.
  },
});
```

A call still working at the limit fails with `TIMED_OUT`. An attached call gets that error as its
tool result, a detached call delivers it as a failed task result, and `task.settled` reports
`failed` with the same error. For a resumable tool, the limit applies to each generation, and each
generation starts a fresh clock. eve then cancels the run, which unwinds as
described in [Cancel and clean up](#cancel-and-clean-up-ctxabortsignal). Time the run spends waiting
on `ctx.ask`, an approval, or a sign-in does not count toward the limit. A `ctx.ask` request that
a `Promise.race` moved past still waits, so the clock stays stopped until the request is answered
or the run ends. `timeout: false` is the same as leaving it unset.

At the limit, eve first reads the run once. A run that already finished but whose outcome never
reached the session settles the call with that outcome instead of `TIMED_OUT`. A call without a
`timeout` is never read this way: if its outcome never reaches the session, the call waits until the
session ends.

The tool's `timeout` and the `timeout` of a `task_wait` call are different. The tool's `timeout`
ends the call with `TIMED_OUT`. A `task_wait` timeout only ends that wait: the task keeps working
and reports its result later in the same turn.

## Cancel and clean up: `ctx.abortSignal`

`ctx.abortSignal` aborts when the run is cancelled, for example by `session.cancel()`, by the
model's `task_cancel`, or, for an attached call, by a steering message. In a resumable tool, it
belongs to the current generation, and each generation gets a fresh signal. It is durable — it survives replay, and a step that
receives it observes the abort. Pass it into the steps that should stop, and clean up in
`try/finally`:

```ts
async execute({ projectId }, ctx) {
  "use workflow";
  const jobId = await submitRender(projectId);
  try {
    return await waitForRender(jobId, ctx.abortSignal);
  } finally {
    if (ctx.abortSignal.aborted) await abortRender(jobId);
  }
}
```

After the signal fires, the run waits up to 30 seconds for the body to finish unwinding, then ends
as cancelled whether or not it did. A body parked on a hook or a `sleep` does not observe the signal;
it is abandoned when the grace period ends. Steps that received the signal are how you clean up
first.

The caller does not wait for that cleanup. Cancelling records the call as cancelled at once and
signals the run, which unwinds on its own. A run that
cannot receive the signal yet, for example because it has only just started, is stopped
immediately. A run that has not ended 35 seconds after the signal, 5 seconds past its own grace
period, is stopped outright.

## Workflow tool examples

### Approve with a deadline and an escalation

```ts
async execute({ service }, ctx) {
  "use workflow";
  const plan = await planDeploy(service);
  const pending = ctx.ask({ prompt: `Deploy ${service}?`, display: "confirmation", options: APPROVE_OR_CANCEL });

  let answer = await Promise.race([pending, sleep("4h")]);
  if (answer === undefined) {
    await pageOnCall(service);
    answer = await Promise.race([pending, sleep("20h")]);
  }

  if (answer === undefined) return { deployed: false, reason: "timed out" };
  if (answer.status !== "answered" || answer.optionId !== "approve") {
    return { deployed: false, reason: "rejected" };
  }
  return { deployed: true, url: await applyDeploy(plan) };
}
```

One request stays on the channel the whole time. `sleep` is the deadline, `pageOnCall` is a step,
and returning withdraws the request.

### Wait for an external system to call back

```ts title="agent/tools/render_video.ts"
import { defineWorkflowTool } from "eve/tools";
import { createWebhook, FatalError } from "workflow";
import { z } from "zod";
import { submitRender } from "../lib/render";

export default defineWorkflowTool({
  description: "Render a video. Returns the URL once the render farm finishes.",
  inputSchema: z.object({ projectId: z.string() }),
  async execute({ projectId }) {
    "use workflow";
    const done = createWebhook();
    const jobId = await submitRender(projectId, done.url);
    const callback = await done;
    const { status, url } = await callback.json();

    if (status !== "ok") throw new FatalError(`Render ${jobId} failed: ${status}`);
    return { url };
  },
});
```

`createWebhook` mints a URL under `/.well-known/workflow/v1/webhook/` that eve serves. The external
system posts to it when it is done. Nothing runs in between. Webhook tokens are generated for
you; use `createHook` with `resumeHook` if you need a deterministic token. To customize the HTTP
response, pass `respondWith: new Response(...)` to `createWebhook`.

### Ask now, act when answered

```ts title="agent/tools/refund_order.ts"
import { defineWorkflowTool } from "eve/tools";
import { z } from "zod";
import { issueRefund } from "../lib/refunds";

export default defineWorkflowTool({
  description: "Request approval to refund an order, then issue the refund once approved.",
  inputSchema: z.object({ orderId: z.string(), amount: z.number() }),
  async execute({ orderId, amount }, ctx) {
    "use workflow";
    const decision = await ctx.ask({
      prompt: `Refund $${amount} on order ${orderId}?`,
      display: "confirmation",
      options: [
        { id: "approve", label: "Refund", style: "primary" },
        { id: "deny", label: "Deny" },
      ],
    });

    if (decision.status !== "answered" || decision.optionId !== "approve") {
      return { refunded: false };
    }
    return { refunded: true, receipt: await issueRefund(orderId, amount) };
  },
});
```

The call returns a receipt, and the approval card appears on the channel. The task shows
`input_required` while the workflow waits without holding compute, and the turn stays open; in an
interactive root session, it shows a waiting boundary so the conversation can continue. Unrelated
messages do not cancel the request. When it is answered, the refund runs and the model receives the
outcome in the same turn.

## Semantics

One piece of work, one result. An attached call resolves once, with the return value, the error,
or a cancellation. A detached call resolves once with its receipt, and its task delivers each
generation's result once. A resumable task's sends each get one result.

Every workflow tool call is a [task](/docs/concepts/tasks). Each generation emits `task.started`
with `kind: "workflow"`, the tool `name`, `mode` (`"attached"` or `"detached"`), `resumable`, and
no `child`, then one `task.settled` with its first outcome; a run that fails to start settles with
`error.code` `START_FAILED`. The task emits `task.ended` once: right after the only generation of a
non-resumable tool, and when a resumable task's body returns or its session ends. Progress stays on
`action.partial`, and an attached call's result is on `action.result`. Agent calls emit the same
events with `kind: "agent"`, so filter `task.*` events by `kind` and `name`. See
[Task stream events](/docs/concepts/tasks#task-stream-events) for the fields.

A steering message from the turn's principal never stops a detached call. It cancels an attached
call, after a pending question has had the chance to take it as an answer or be dismissed. A message
with `turnPolicy: "queue"`, or from another principal, waits until the turn ends. Input responses
never steer. `session.cancel()` cancels every working run, which withdraws its requests.

Errors follow the SDK. A thrown error in a step retries per the step's policy; `FatalError` does
not. An error that escapes the body fails the tool invocation.

Starting a workflow tool can also be retried. If dispatch is interrupted after starting a run, its
retry starts another run, but only one of them executes the body: each run first claims a command
hook derived from the call's task, and a run that finds the hook taken exits without running the
body or reporting. Steps inside the body still retry per their own policy, so use an application
idempotency key for side effects that must happen only once.

The workflow id derives from the executor's module path and function name. Inline executors use
the tool module and the name `execute`; imported executors use their declaring module and name.
Renaming or moving that function creates a new workflow. Runs in flight finish on the deployment that started them; a run that
resumes on a deployment without its tool fails with an error naming the missing workflow.
