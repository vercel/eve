Summary

On the hosted stress fixture a warm follow-up turn takes about one second end to end while the mock model takes seven milliseconds. The rest is transport: one queue hop and roughly twenty serial-or-near-serial requests to the workflow server, split across two steps. The eve side of that path is already lean (eight operations on the holder's streams, zero reads at ingress); what remains is the Workflow SDK's per-step and per-hook protocol, plus a second step boundary for finalization.

Architecture

A session is two kinds of workflow run. The holding workflow is created once, claims the session's addresses, creates two streams, publishes a small immutable descriptor, starts the first turn, then parks on its control hook. It never reads a snapshot or runs the model. Each accepted message starts a turn workflow, a terminating candidate that claims the session-wide hook eve:turn:<sessionId>. The winner hydrates from the snapshot stream, runs the model inside one step, appends events to the holder's event stream, commits a checkpoint, and finalizes in a second step. A loser forwards its message to the winner and follows the winner's receipt.

Hooks are the coordination primitive: a hook claim is mutual exclusion, and every owner (holder, turn, tool body, task) has exactly one receiving hook wrapped as an inbox. Streams are the storage primitive: independent runs write to the holder's streams by reference, which the SDK patch makes possible.

What a primitive costs

Two servers sit under the SDK. The workflow server stores runs, events, hooks, and streams. Inside a queue-driven invocation, single event writes ride a WebSocket channel opened once per invocation; from an ordinary request handler (where start() and resumeHook() usually run) they are plain HTTPS POSTs. Stream reads and writes and run metadata are always HTTPS. The queue service (VQS) delivers each workflow or step invocation as an HTTP POST to the deployment's flow route, which is a fresh function invocation each time. The producer pays one publish; the consumer pays one lease ack (and a lease extension every 60 s for long bodies).

Paths A–G

Each path is drawn as a sequence with time flowing down. Lanes are the places code runs. Arrows are requests, colored by which server answers them; a paired mark means the two requests were issued in parallel. Boxes on a lane are compute. Measured phase labels come from the hosted sample's native run and step timestamps.

A

New session over HTTP

The handler starts the holder and returns 202 without waiting. The holder claims its control hook, then runs one bootstrap step that performs six serial storage requests, then a second step that starts the first turn. The turn arrives with resources inlined, so it skips descriptor discovery, but its head read returns the seed and it must also start the session-timeout workflow before the first model call. Two queue hops sit on the critical path.

B

Follow-up on an idle session over HTTP

This is the path the stress fixture measures. The handler mints an event id and starts a candidate with only the session id: no descriptor, owner, or snapshot read. The candidate claims the turn hook, hydrates inside its first step, runs the model, commits, then finalizes in a second step. The client sees completion when finalize's event batch lands, which is why client latency (1,035 ms) runs below the native run duration (1,177 ms).

C

Steer or interrupt while a turn is active

The candidate loses the claim, disposes its hook, and in a step resumes the owner's hook with the submission, then long-polls the owner's run status. The resume publishes a queue message, so a second invocation of the owner run starts while the owner's first invocation is still inside its execute step. That second invocation replays, feeds the envelope to the inbox, finds the execute step owned by a live lease, arms a delayed backstop wake, and exits. A plain steer therefore lands only when the first invocation's step completes and replays with the delta. An interrupt is different: replay calls controller.abort(), which writes an abort packet to the run's abort stream, and the real-time reader inside the live step cancels the model call.

E

First Slack message: competing holders and the rekey exchange

A miss on the alias lookup leads to session recovery (Slack conversations.replies plus two more by-token lookups), then a holder start with initialToken. Unlike Path A the handler blocks on the descriptor read until the holder publishes it, so the holder's bootstrap is on the response path. The holder makes two serial hook claims (control, then alias). If the alias is already owned, the loser runs a redirect step: read the winner's descriptor, start the turn against the winner, publish the winner's descriptor under its own run id so the blocked handler resolves to the winning session.

Then the first turn pays a cost no later turn pays. After its execute step, progress.continuationToken is set but claimedContinuationToken is not, so the turn sends a rekey to the holder's control hook and suspends waiting for the reply. That is two steps, two hook resumes, and two queue hops (holder wake, turn wake) inserted between execute and finalize.

Soundness

Things the trace confirms hold, and things it shows are still open.

Holds

  • Claim before read. Every path reads mutable state only inside the first execute step after the hook claim succeeds. Ingress never preflights. The stale-revision race in the research doc cannot occur.
  • Two hooks share one activation. The inbox hook and the abort hook are created in the same suspension and the first step_started lands in the same invocation (native test asserts both). The patch's in-process replay is what makes this one hop instead of two.
  • Steer is step-boundary steering. A second owner invocation cannot touch a step owned by a live lease; it arms a backstop and exits. The envelope is applied when the live step completes and replays with the delta. This matches the documented DEFAULT_TURN_POLICY.
  • Interrupt reaches a live step. The abort packet travels by stream, not by replay, so the model call is cancelled without waiting for the boundary. This depends on the abort reader staying open for the whole step.
  • Losers follow the actual owner. The candidate long-polls the run it resumed into and re-claims if the receipt does not name its event, so an owner change between conflict and resume is handled by the loop.

Open

  • Second owner invocations are pure overhead. Each steer, cancel, tool report, or ask wakes the owner run with a full log preload only to buffer an envelope. Long tool-heavy turns will see the owner's event log grow and every wake pays to read it.
  • Backstop wakes. When the second invocation finds a live lease it arms a delayed publish. If the first invocation's step completes normally, that delayed message is a wasted invocation later. The count per turn under load is not measured.
  • Concurrent tail. Second turns in the concurrent scenario show 1,345 ms p50 but 4,272 ms p95. Contended claims turn into forwards and polls; the tail is where Path C's extra hop and preload show up.
  • Release gates from the research doc remain. Fencing after hard cancellation, recovery of a failed candidate without new input, and the Slack post-to-rekey race are implementation gates, not properties this trace can establish.
  • Patch drift. Five local SDK amendments carry the round-trip savings. Upstream beta.48 has its own in-process hook settle but none of the stream-reference, metadata-cache, or lone-step scheduler changes.

Recommendations

Addendum by Pranay Prakash · proposed, not implemented

The new-session path is three functions in a chain: handler, holder, turn. Each link is a queue hop, and inside each link every request waits for the previous one. The holder sits in the middle doing bookkeeping the turn does not need before it can call the model. The turn needs three things: the claim on its hook, a durable marker that effects began, and the first message, which is already in its input. So the goal is to run the turn in parallel with the holder rather than after it.

  1. Start the holder and the first turn from the handler, in parallel. The holder run id is generated client-side before start(), the deployment id is in the environment, and same-deployment keys derive locally, so the handler can build the resources without the holder's metadata read and pass them into both starts. The turn hops once and claims while the holder bootstraps; its head read waits, bounded, for the seed. Token-bearing sessions keep the serial path, or wait on the alias outcome, because the turn must not begin effects before the alias claim is known.
  2. Let the first turn write index zero. The initial entered marker already embeds full state. An early follow-up that wins the claim and finds an empty log defers to the initial event's candidate through the existing predecessor mechanism. This changes the first-input-precedence contract and must be written down with it.
  3. Move the session-timeout start off the path. From the holder's bootstrap step, or after the model call.
  4. Overlap the entered marker with model request assembly. Issue the PUT, build the request, await the PUT before the first external effect.
  5. Trim holder bootstrap. Derive the stream reference locally, drop tail probes on fresh streams, fold the descriptor close into its write, merge the two bootstrap steps. Fourteen requests become about eight. This is what the fifty-session concurrent scenario is paying for.
  6. Hook-claim reads belong upstream. Rather than moving the turn's AbortController out of the claim suspension, generalize the SDK: when a suspension posts several guarded events from the same base cursor, the longest event suffix any of them returns contains every event the suspension wrote, so the runtime can continue inline replay from it with no read. A pull request against vercel/workflow is in progress. eve keeps two hooks per turn.

Method

Request counts come from reading the SDK sources in the workflow monorepo (core, world, world-vercel) at beta.48 and diffing against eve's pinned beta.47 patch, then walking eve's session, turn, inbox, and channel modules on this branch. Where a native test fixes a count (the holder storage budget of 10 cold / 8 cached, the two-hook single-activation claim, the 2-read 4-write snapshot transaction), the static count was checked against it and agrees. Path A's holder bootstrap and the rekey exchange have no native counter and are static counts only.

Timings come from the CI artifact workflow-stress-performance of run 34271267671: client durations from the eval, native phases from scripts/workflow-turn-profile.mjs reading run and step timestamps through the Workflow API. Medians of phases do not sum exactly to the median run. Checkpoint history is from the research document's hosted table.

Not counted: Slack API calls, OpenTelemetry attribute writes (backgrounded via waitUntil), model provider requests, and VQS lease extensions on bodies over 60 seconds.
